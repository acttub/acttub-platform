# 기존 화면의 Gemini 직접 영상 코칭

운영 `main`을 기준으로 Gemini 코치 변경만 반영한다. 계정 1.0.0, 새 인증·동의 게이트,
웹·앱 화면 변경, DB 마이그레이션은 이번 배포에 포함하지 않는다.

기존 화면에서 장면 정보를 비워 영상만 올리는 새 연습은 기존 `three_layers_v1` 계약으로 생성한다.
`ACTTUB_DIRECT_VIDEO_ENABLED=true`일 때 분석 작업은 영상 길이와 업로드 무결성만 확인하고,
1층 영상 분석·받아쓰기 모델을 부르지 않는다. 코치가 소유한 원본 영상과 현재 세션 대화 원문을
Gemini에 직접 전달한다. 응답 프롬프트는 공통 원칙과 서비스가 고른 작업 지침으로 조합한다.

API와 화면, 대화 저장·재개·멱등 요청·10회 제한·종료·3층 노트는 기존 것을 사용한다.
별도 실험 페이지나 임시 세션 API는 배포하지 않는다. 구조화된 영상 관찰은 생성하지 않으며,
코치의 자유 형식 응답을 확정된 배우 의도·실행 기록으로 바꾸지 않는다.
매 턴의 Gemini 파일은 응답 뒤 정리한다. 원본 재전송으로 지연이 추가될 수 있다.

## 응답 분류와 지침 선택 (2026-09-22)

첫 응답은 전체 인상 → 가장 크게 보완할 점과 영상 속 근거 → 개선 방향으로 제공한다.
장면 전체의 자연스러움·전달력에 영향을 주는 문제를 최대 두 개 우선하며, 부족함을 억지로 만들지 않는다.
반복되는 문제는 여러 구간으로 뒷받침하고 화면 밖 상대의 답변·표정을 사실이나 진단 근거로 지어내지 않는다.
기본은 서너 개의 짧은 문단이며 공통의 한두 문장 제한을 없앴다. 끝의 질문은 필요한 경우에만 한다.
후속 분류와 각 작업 지침은 유지하며, 기존 진단과 배우의 최신 말을 이어서 다룬다.
기초 연기 용어는 사용하되 이해하기 쉬운 문장으로 설명하고, 근거 없이 새 결점을 늘리지 않는다.

첫 응답은 코드에서 `opening`을 선택한다. 후속 답은 별도 Gemini 텍스트 호출이
직전 코치 발화와 실제 대화 원문을 보고 `intention`, `correction`, `unsure`, `method`,
`acknowledgement`, `other` 신호로 분류한다. 분류에는 영상을 보내지 않는다.
분류 JSON과 지침 목록은 코칭 모델·사용자 대화에 섞지 않는다.

`DirectVideoRouting`이 선택하고 `coaching/direct-video/` 아래 텍스트 파일을 조합한다.
정정, 이해 어려움, 방법 요청, 의도, 수긍 순서로 우선하며 정정+이해 어려움 또는
정정+방법 요청에는 두 작업만 붙인다. 예상 밖의 질문·사실·감정·화제 전환이나 확신하기 어려운 답은
명시적인 기타(`other`)로 받아 최신 말에 직접 답하고 기존 대화 흐름에 억지로 맞추지 않는다.
빈 신호 배열도 `other`로 받는다. `other`가 다른 신호와 함께 오면 구체적인 신호를 우선하되 단순 수긍보다 우선한다.
기타는 정상 분류이며, 분류 실패 시 사용하는 `general` 및 실패 기록과 구분한다.
‘응’도 직전 의도 확인 질문에 대한 답이면 의도 정보로 분류할 수 있게 문맥을 전달한다.

단순 수긍은 `acknowledgement`로 짧게 받아주되 세션을 닫지 않는다.
기존 종료 판정과 10회 제한만 `closing`을 선택하고 세션 종료를 결정한다.
임시 dev 세션도 같은 분류·선택 코드를 사용하고 명시적 종료 시 `finished`가 된다.

분류 호출 제한은 15초, 출력 제한은 1024토큰이다. 후속 응답에는 분류 호출 비용과 지연이 추가된다.
모르는 라벨·중복·잘못된 형식 또는 제공자 실패는 원인을 보고하고 `general`로 답한다.
취소·작업 점유권 상실은 기본 답변으로 숨기지 않는다. `coach.route`와 `coach.turn`을
별도로 기록하며 실제 선택과 폴백 여부는 내부 코칭 호출 메타데이터에 남긴다.
공개 API·DB·화면과 기존 비-Gemini 코칭 경로는 변경하지 않는다.

검증은 실제 SDK 요청의 텍스트 전용 분류, 선택된 지침만 전달됨, 복합 응답 우선순위,
잘못된 분류의 폴백, 수긍과 종료 구분, 대화 저장·실패 시 보존을 대상으로 한다.
스텁 테스트는 실제 모델의 한국어 분류 정확도를 보장하지 않으므로 실사용 대화로 별도 확인한다.

배포 워크플로는 `DEPLOY_THREE_LAYERS_ENABLED=true` 및 `DEPLOY_DIRECT_VIDEO_ENABLED=true`를
전달한다. 배포 스크립트는 release.env에 기록하고 API 컨테이너에 실제 반영됐는지 대조한다.
애플리케이션은 직접 영상 플래그가 명시되지 않으면 기존 경로를 유지한다.
기존 GEMINI_API_KEY와 GEMINI_MODEL을 사용하며 새 계정용 키나 SITE_URL 설정을 요구하지 않는다.

롤백은 동일 이미지에서 두 플래그를 false로 명시하거나 직전 운영 이미지로 재배포한다.
분석을 생략한 테스트 세션은 기존 코치 경로로 이어갈 수 없으므로 새 영상을 올린다.
DB 마이그레이션이 없으므로 기존 운영 데이터 구조는 바뀌지 않는다.

## dev 연습 루프 (2026-09-24, SOMA-508)

dev(`SITE_URL=https://dev.acttub.com`)의 직접 영상 코칭은 분류·지침 조합 대신
`coaching/direct-video/practice-loop.txt` 하나로 대화 전체를 이끈다. 운영은 위의 분류·지침 경로를 그대로 쓴다.
`ACTTUB_DIRECT_VIDEO_PRACTICE_LOOP=true|false`를 명시하면 환경과 무관하게 그 값을 따른다.

목표는 세션 뒤 배우가 "오늘도 연습을 했다"고 느끼는 것이다. 첫 응답은 대사 인용과 동작, 그 대사가 상대에게
어떻게 들리는지, 테이크에 없는 반대 방향 의도를 짚고 "인물은 상대가 A길 바랄까요, B길 바랄까요?"로 묻는다.
이후 고르기 → 과제(고른 의도로 두 번, 반대로 한 번) → 달라진 점(배우의 말로) → 다음 순간 → 마무리
(해 본 횟수와 연습 노트 한 줄) 순서로 진행한다.

모델은 첫 응답에 `<설계>`·`<코치>`를, 이후 응답마다 맨 앞에 `<상태>` 한 줄을 쓴다.
`DirectVideoPracticeLoop`가 코치 본문만 대화에 저장·표시하고, 설계와 상태는 `coaching_state.practice_loop`
(`design`, 코치 턴 순서의 `statuses`)에 둔다. 다음 턴에는 모델에 넘기는 기록에만 둘을 다시 붙인다.
상태 줄의 둘째 칸이 `마무리2`·`끝`이면 세션을 닫는다(`interrupted`). 배우의 종료 요청과 10회 제한은
기존 판정을 따르되 응답은 연습 루프 프롬프트가 쓴다. 루프 이전에 열린 세션은 기존 경로로 이어간다.
공개 API·DB 스키마는 바뀌지 않는다. 프롬프트 실험 기록은 SOMA-508 코멘트에 있다.
