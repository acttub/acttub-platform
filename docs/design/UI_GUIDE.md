# UI 디자인 가이드

이 문서는 Acttub에만 필요한 UI 판단 기준을 적는다. 색상값, 컴포넌트 수치, 타이포그래피 스케일, motion 값처럼 Toss 디자인 시스템이 이미 정한 것은 여기로 옮겨 적지 않고 원문을 직접 참조한다(ADR-012).

- 상세 레퍼런스: `docs/design/Toss-DESIGN.md`
- 랜딩·인터뷰 화면 구조 참고: `docs/design/telta-interview-pro.md`
- 화면에 쓰는 말: 루트 `CONTEXT.md`가 정본이다(ADR-013)

우선순위:

1. Acttub 제품 정체성과 금지 표현은 이 문서가 우선한다.
2. 시각 스타일, 토큰, 컴포넌트 수치는 `docs/design/Toss-DESIGN.md`를 참조한다.
3. Toss와 Acttub 맥락이 충돌하면 Toss를 그대로 복제하지 않고 Acttub 제품 의도에 맞게 낮춰 적용한다.

## 지금 만드는 화면

연습 하나는 **Practice Stage** 여섯을 지난다. 이름은 `CONTEXT.md`가 정본이다.

```text
준비 -> 막힘 선택 -> 업로드 -> 분석 -> 대화 -> 연습 노트
```

- **웹**은 이 여섯이 **라우터 네비게이션 없이** 같은 컴포넌트 안에서 바뀐다(`features/workspace/workspace-state.ts`의 `WorkspaceScreen`). `/home`·`/practice/new`·`/practice/history` 셋이 같은 `WorkspaceApp`을 렌더한다. 화면이 바뀔 때 주소는 `history.replaceState`로 갈아끼운다 — `router.replace`를 쓰면 `useSearchParams`를 감싼 Suspense가 다시 걸려 흰 화면이 깜빡인다. 로그인·로그아웃처럼 화면을 실제로 옮기는 이동만 `router`를 쓴다.
- **모바일**은 라우트로 나뉘지만 **라우트 이름이 Practice Stage와 1:1이 아니다.** `app/upload`이 준비 화면이고, 실제 업로드는 `analyzing`에서 분석과 함께 돈다:
  `app/upload`(준비) → `blockage`(막힘 선택) → `analyzing`(업로드·분석) → `coach`(대화) → `report`(연습 노트).

준비 화면 안에서 사람이 채우는 순서는 **Setup Step**이고(`CONTEXT.md`), 화면이 바뀌지 않고 같은 자리에서 진행되므로 Practice Stage와 다른 층이다. 진행 표시를 만들 때 둘을 섞지 않는다.

**Scene Context는 선택 입력이다**(ADR-021). 화면이 그 사실을 말해야 하고, 세 칸이 모두 빈 상태에서만 건너뛰기가 나타난다. 한 번 건너뛴 연습에서는 다시 묻지 않는다 — 나중에 채우는 경로를 화면에 만들지 않는다.

> **관찰 확인(맞음/아님/모르겠음) 화면과 배우가 직접 쓰는 자기 정리 문장은 없다.** ADR-014가 제거했고, 그 역할은 코치와의 대화와 연습 노트의 `self_discovery`가 대신한다. 옛 문서를 근거로 이 두 화면을 만들지 않는다.

## 디자인 원칙

1. 도구처럼 보여야 한다. 마케팅 페이지가 아니라 배우가 매일 영상을 올리고 질문을 이어가는 연습 도구여야 한다.
2. 평가표처럼 보이면 실패다. 코치와의 대화가 핵심 표면이고, 연습 노트는 그 대화가 남긴 결과다.
3. 신뢰는 장식이 아니라 명료함에서 나온다. 흰 배경, 강한 타이포 위계, 충분한 여백, 낮은 shadow를 사용한다.
4. 모바일 우선이다. 375px 폭에서도 영상 업로드, 장면 입력, 대화가 막힘없이 이어져야 한다.
5. 한국어 가독성을 우선한다. 긴 문장을 줄이고, 한 화면에는 한 가지 결정만 요구한다.
6. 코치가 판정자로 보이지 않는다. 배우가 주인이고, 코치는 질문 경로를 돕는 상대다.
7. 감정적으로 안전해야 한다. 카피와 상태 메시지는 배우를 평가하거나 몰아붙이는 느낌을 주지 않는다.

## 하지 않는 것

| 하지 않는 것 | 이유 | 이것은 해당하지 않는다 |
|---|---|---|
| glass morphism 카드·패널 | AI 템플릿 느낌이 강하고 도구 UI의 명료함을 해친다. | 스크롤 헤더의 반투명 처리(`app/landing-client.tsx`) |
| gradient로 칠한 글자 | AI SaaS 랜딩처럼 보이며 연습 도구의 신뢰감을 떨어뜨린다. | — |
| 배경에 떠 있는 gradient orb | 연습 도구보다 홍보용 랜딩처럼 보인다. | 랜딩·다운로드의 히어로 배경, 랜딩의 영상 목업 배경, 코치 아바타 원형 |
| "Powered by AI" 배지 | 기능이 아니라 장식이다. 배우의 과업에 도움이 되지 않는다. | — |
| box-shadow 글로우 애니메이션 | 네온 글로우는 평가·AI 데모 느낌을 만든다. | — |
| 보라·인디고 AI 팔레트 | "AI = 보라색" 클리셰를 피한다. | — |
| 화면 전체를 같은 radius로 도배 | 정보 위계가 흐려지고 템플릿처럼 보인다. | 웹이 자리에 따라 radius를 갈라 쓰는 것 |
| 점수 원형 차트, 레이더 차트 | 평가 서비스처럼 보인다(ADR-005). | — |
| 강점·약점·개선점 카드 | 폐기된 피드백 카드 프레이밍으로 회귀한다. 웹은 아래 가드가 이 세 단어를 막는다. | — |
| 코치가 판정을 내리는 아바타 UI | 배우가 평가받는 느낌을 받는다. | — |
| 과한 confetti, sparkles, emoji | 연기 고민을 다루는 안전한 공간의 톤과 맞지 않는다. | — |

오른쪽 칸은 **혼동하기 쉬운 실물**을 예로 든 것이지 전부를 센 목록이 아니다. 문자열만 보고 위반으로 판정하지 말고 무엇을 하는 코드인지 먼저 본다.

## 색상

세부 색상값은 `docs/design/Toss-DESIGN.md`의 token과 color palette를 참조한다. Toss 팔레트는 이미 웹 전반에 적용돼 있다 — 새 화면을 만들 때 색을 새로 고르지 말고 옆 화면이 쓰는 값을 가져온다.

Acttub 적용 규칙:

- 밝은 배경, 중립 회색, 파란 액션 컬러를 기본으로 한다.
- Acttub 브랜드 컬러가 확정되면 semantic token만 교체하고 역할은 유지한다.
- 주 액션 컬러는 CTA, 링크, 선택 상태, 현재 Setup Step에 사용한다.
- 성공·오류 색은 상태 전달에만 사용하고 장식 색으로 쓰지 않는다.
- 대화 화면에서 코치 발화를 파란 카드로 과하게 강조하지 않는다. 파란색은 배우의 주요 액션에 남겨둔다.
- "좋음/나쁨"처럼 평가를 암시하는 색상 매핑은 금지한다(ADR-005).

## 컴포넌트

세부 버튼, 입력, 카드, badge, tab, toast, dialog, toggle 규격은 `docs/design/Toss-DESIGN.md`의 component section을 참조한다.

Acttub 적용 규칙:

- 카드 안에 또 다른 카드 구조를 넣지 않는다.
- 대화 전체를 큰 장식 카드로 감싸지 않는다.
- 반복되는 관찰, 질문, 입력 그룹처럼 명확히 묶어야 하는 단위에만 카드 스타일을 쓴다.
- 버튼은 주요 행동 하나가 가장 강하게 보이게 한다.
- 잠긴 버튼은 문구만 바꾸지 말고 눌리지 않는 모습도 함께 준다(웹은 `disabled:` 변형, 모바일은 비활성 스타일). 눌리지 않는 이유가 보여야 한다.
- 대화 입력은 마지막 질문 아래 또는 하단 action 영역에 두고, 전송 동작을 명확히 한다.
- 웹은 아직 아이콘 라이브러리를 쓰지 않는다. 도입한다면 `lucide-react`를 우선 검토한다. (모바일은 `@expo/vector-icons`의 Feather를 이미 쓰고 있고, 이 권고는 웹 이야기다.)
- 아이콘은 기능을 보조해야 하며, 의미가 불명확하면 tooltip 또는 `aria-label`을 제공한다.

## 카피

용어 정본은 `CONTEXT.md`이고, 화면 문장은 한국어 존댓말("~해요")로 쓴다.

`apps/web`은 `tests/product-language-guard.test.mjs`가 `pnpm --filter web test` 안에서 금지어를 막는다. **`src` 전체를 훑으므로 주석과 변수 이름도 걸린다** — 점수·등급·평가·약점·개선점·피드백 카드, 그리고 **"리포트"** 가 여기 들어간다. 화면에서든 코드에서든 그 산출물은 **연습 노트**다. `apps/mobile`에는 같은 가드가 없으니 손으로 지킨다.

지금 화면이 쓰는 말(고칠 때는 실물을 먼저 확인한다):

- "질문 받기" — 준비를 마치고 대화로 들어가는 주 액션. 웹·모바일이 같은 말을 쓴다
- "장면 없이 시작" · "적지 않았어요" — Scene Context를 건너뛸 때
- "새 연습" · "이 연습에 이어서 새 연습" — 시작과 이어하기
- "연습 마치기" — 대화를 끝낼 때

쓰지 않는 말:

- "평가 받기" · "점수 확인" · "약점 보기" · "정답 보기" · "AI 피드백 받기"
- 연습 화면 안에서 코치를 "AI"라고 부르지 않는다. 배우와 마주 앉은 상대는 "코치"다.
  - 다만 **유입 표면은 아직 갈린다** — 웹 랜딩(`app/landing-client.tsx`)과 앱 홈 카드(`app/(tabs)/index.tsx`), 스토어 리스팅이 "AI"를 쓴다. 어느 쪽으로 모을지는 정해지지 않았으니, 새 화면을 만들 때는 그 화면이 속한 쪽을 따른다.

## 레이아웃

- 첫 화면은 히어로 랜딩보다 바로 영상 업로드와 장면 입력이 보여야 한다.
- 대화 화면은 한 번에 하나의 질문과 하나의 주요 액션만 눈에 띄게 한다.
- 분석 대기 화면은 spinner만 두지 말고 현재 상태를 짧은 한국어 문장으로 표시한다.
- 연습 노트 화면은 배우가 대화에서 스스로 말한 것을 가장 강하게 보여주고, 나머지는 보조 정보로 둔다.
- 모바일 375px 기준에서 모든 주요 CTA 텍스트가 어색하게 잘리지 않아야 한다. 제목과 나란히 놓는 요소는 이 폭에서 먼저 밀린다.
- 터치 대상은 Toss 레퍼런스의 모바일 기준을 따른다.
- 데스크톱에서는 영상·장면 보조 패널과 대화 메인 패널을 나눌 수 있다.

## 타이포그래피

세부 font stack과 hierarchy는 `docs/design/Toss-DESIGN.md`의 typography section을 참조한다.

Acttub 적용 규칙:

- 한국어 가독성을 우선한다.
- 질문 본문은 보조 설명보다 확실히 강해야 한다.
- 배우가 대화에서 한 말은 연습 노트에서 가장 중요한 텍스트로 취급한다.
- viewport width에 따라 font-size를 직접 scale하지 않는다.
- letter spacing은 기본 0으로 둔다.
- Toss Product Sans 사용 가능 여부가 확정되지 않았으면 `Pretendard`, `SF Pro KR`, `Apple SD Gothic Neo`, `Noto Sans KR`, system sans-serif 계열을 우선 검토한다.

## 애니메이션

세부 motion 값은 `docs/design/Toss-DESIGN.md`의 motion section을 참조한다.

Acttub 적용 규칙:

- 상태 변화 이해를 돕는 데만 사용한다.
- 코치가 "대단한 결과를 생성했다"는 느낌의 연출을 피한다.
- 분석 대기 시간이 길어질 수 있으므로 진행 문구와 취소·나가기 상태를 명확히 둔다.
- glow pulse, gradient background animation, dramatic reveal은 사용하지 않는다.

## 아이콘

세부 SVG·icon 규칙은 `docs/design/Toss-DESIGN.md`의 iconography section을 참조한다.

Acttub 적용 규칙:

- 업로드, 재생, 일시정지, 전송, 닫기, 뒤로가기, 체크, 경고처럼 익숙한 기능에는 익숙한 심볼을 사용한다.
- 아이콘 색은 `currentColor`를 상속하게 한다.
- 아이콘을 둥근 배경 박스에 반복적으로 넣어 장식하지 않는다.
- AI, magic, sparkle 아이콘은 사용하지 않는다.
