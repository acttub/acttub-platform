# 이슈 트래커: Jira (프로젝트 `SOMA`)

이 레포의 **이슈 정본은 Jira 프로젝트 `SOMA`** 입니다. GitHub Issues는 정본이 아닙니다.
**이슈를 만들고 본문을 쓰는 것은 사람입니다** — 에이전트는 초안만 넘깁니다. 왜 그렇게
정했는지와 그 대가는 **ADR-022**에 있습니다.

| | 어디에 | 누가 쓰나 | 무엇을 담나 |
|---|---|---|---|
| 이슈 | Jira `SOMA` | 사람 | 배경 / 원하는 상태 / 완료 조건 |
| 실행 계획 | `.scratch/<이슈키>.md` | 에이전트 | 그 이슈를 어떻게 굴리는가 |

둘을 **이슈**와 **계획**으로 갈라 부릅니다 — 한쪽을 "티켓"이라 부르면 다른 쪽도 그렇게 읽혀
어느 것을 말하는지 매번 헷갈립니다.

## 접근 수단

**에이전트는 Jira에 쓰지 않습니다** — 정책입니다(ADR-022). 그리고 **Atlassian MCP가 등록돼
있지 않아 읽지도 못합니다** — 사실입니다. 우회로를 찾더라도 앞의 정책은 그대로입니다.
이슈 번호나 본문을 **추측하지 마세요** — 모르면 사용자에게 묻습니다.

붙여야 할 일이 생겼다면(ADR-022의 "되돌릴 근거"에 해당하는 경우):

```
claude mcp add --scope user --transport http atlassian https://mcp.atlassian.com/v1/mcp/authv2
```

인증은 세션에서 `/mcp` → `atlassian` → 브라우저 OAuth이고 각자 한 번씩 해야 합니다.
`claude mcp get atlassian`이 `✔ Connected`여야 붙은 것입니다.

## 스킬이 "이슈 트래커에 발행하라"고 할 때

1. **초안을 세 절로 씁니다** — 배경 / 원하는 상태 / 완료 조건(체크리스트). 근거·조사 기록·설계 서술은 **본문에 넣지 않습니다**(필요하면 참고 경로 한 줄까지). 그것들은 계획 파일에 둡니다.
2. 사용자가 Jira에 이슈를 만들고 **키를 알려줍니다.** 여러 건이면 우선순위 순으로 정리해 한 번에 보고하고, **초안이 5건을 넘을 상황이면 쓰기 전에 목록만 먼저 보여주고 승인을 받습니다** — 한 번에 여럿을 올리면 보드가 지저분해져 무엇부터 할지 고르기 어려워집니다. 그것이 이 규칙이 있는 이유입니다.
3. 키를 받으면 그 키로 브랜치를 팝니다.

사용자가 Jira에서 채울 것 — **스프린트**와 **에픽**을 비우면 백로그에만 있고 보드에 안 뜹니다.
백엔드·인프라 에픽은 `SOMA-371`이고, 어디 붙일지 애매하면 비슷한 기존 이슈의 에픽을 따릅니다.
**담당자는 비워 둡니다**(누가 잡을지는 사람이 정합니다).

## 실행 계획 파일

한 이슈를 여러 세션에 걸쳐 굴릴 때 쓰는 자리입니다.

- **`.scratch/<이슈키>.md` 파일 하나**입니다. 길이나 형식에 제약은 없습니다 — 사람이 아니라 다음 세션의 에이전트가 읽는 글입니다.
- 단계를 나눴다면 **단계 하나 = 커밋 하나**로 잡고, 선행 관계가 있으면 그 자리에 적습니다. 순서가 있는데 안 적으면 뒤 단계가 앞 단계의 수정을 조용히 삼킵니다.
- **착수 전에 계획이 센 숫자를 다시 셉니다.** 계획이 적게 세는 일이 반복됐습니다.
- **끝나도 옮기거나 지우지 않습니다.** `.scratch/`는 `.gitignore`에 있어 저장소에 영향이 없습니다.

## 끝난 뒤 옮기는 것

계획 파일은 그대로 두고, **살아남아야 할 것만** 옮깁니다.

- **앞으로 지킬 규칙이 된 것** → 저장소 문서(`docs/ADR.md`·`CLAUDE.md`·`CONTEXT.md`)
- **새로 발견한 버그·미처리 이월** → Jira (초안을 넘기고 사람이 이슈를 만듭니다)

**안 옮기면 그대로 묻힙니다** — 계획 파일은 `.gitignore`에 있어 저장소 어디에도 흔적이 없고,
이 머신을 벗어나지 않습니다.

## 스킬이 "해당 이슈를 가져오라"고 할 때

1. 현재 브랜치명·PR 제목에서 키를 뽑습니다 — `git branch --show-current`, `gh pr view --json title`. 브랜치 규칙이 `feat/SOMA-123-<slug>`이라 대개 여기서 나옵니다.
2. `.scratch/<이슈키>.md`가 있으면 그것을 읽습니다. **`.scratch/`는 `.gitignore`에 있어 `git grep`으로는 안 보입니다** — 경로를 직접 엽니다.
3. 없으면 Jira 본문이 필요한 것이므로 **사용자에게 묻습니다.** 비슷한 제목으로 검색해 추정한 이슈를 정답처럼 쓰지 마세요.

## 쓰기 작업의 경계

에이전트가 Jira에 쓰지 않으므로, 아래는 **사람에게 무엇을 요청해도 되는지**의 선입니다.

- **상태 전이(`In Progress` / `검토 중` / `Done`)를 요청하지 않습니다.** GitHub 연동이 브랜치 생성·PR 오픈·머지에 맞춰 자동으로 굴립니다. `보류 중`도 사람 전용입니다.
- **이슈 삭제를 요청하지 않습니다.** 잘못 만들었으면 알리고 판단을 받습니다.
- **남의 이슈 본문을 갈아엎자고 하지 않습니다.** 추가 정보는 코멘트로 답니다.

## 브랜치·PR 규칙 (Jira 자동화가 여기에 걸려 있음)

`CLAUDE.md`의 "이슈 추적 (Jira 연동)" 절이 정본이며, 요약하면:

- 브랜치명에 **대문자** 키를 포함: `feat/SOMA-123-exit-review-modal` (타입 뒤, 설명 앞)
- PR 제목: `SOMA-123 <한국어 요약>`
- 커밋 메시지에는 키를 넣지 않습니다(Conventional Commits 그대로).

키가 빠진 브랜치는 Jira 연결이 끊깁니다. 브랜치를 새로 만들 때는 키를 먼저 확인하고,
모르면 만들기 전에 물어봅니다.

## GitHub Issues의 위치

GitHub Issues는 **외부 제보용 인박스**입니다. 정식 작업은 Jira로 옮겨 진행하므로,
에이전트는 GitHub Issue를 참고 자료로 읽을 수는 있어도(`gh issue view <n> --comments`)
거기에 작업 계획을 쌓지 않습니다. 제보가 진짜 작업이 되면 Jira 이슈로 옮기고,
GitHub Issue 쪽에는 옮긴 곳을 코멘트로 남깁니다.

## PR을 요청 접수 창구로 쓰는가

**아니오.** 외부 PR은 트리아지 큐에 넣지 않습니다.

## Wayfinding 운영

`/wayfinder`의 map/child 구조도 위와 같은 갈래를 씁니다.

- **map**: Jira Epic 하나(사람이 만듭니다). Notes / Decisions-so-far / Fog는 `.scratch/<에픽키>.md`에 둡니다.
- **child**: 그 파일 안의 항목. 종류를 함께 적습니다(research / prototype / grilling / task).
- **blocking**: 항목 옆에 선행 관계를 적습니다. 블로커가 전부 닫히면 풀린 것으로 봅니다.
- **claim**: 담당자 지정은 사람이 합니다. 에이전트는 "다음에 뭘 잡으면 되는지"만 제시합니다.
- **resolve**: 답을 그 파일의 Decisions-so-far에 한 줄 추가합니다. Epic을 닫는 것은 사람이 합니다(상태 전이 금지 규칙과 같은 이유).
