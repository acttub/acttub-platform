# 이슈 트래커: Jira (프로젝트 `SOMA`)

이 레포의 이슈·스펙 정본은 **Jira 프로젝트 `SOMA`** 입니다. GitHub Issues는 정본이 아닙니다.

> **중요**: 이 환경에는 Jira CLI(`jira`, `acli`)도 Atlassian MCP 서버도 설치돼 있지 않습니다.
> 에이전트는 Jira를 **직접 읽거나 쓸 수 없습니다.** 아래 절차는 전부 "에이전트가 초안을 만들고,
> 사람이 Jira에 반영한다"를 전제로 합니다. 도구가 없는데 있는 척 추측으로 티켓 번호를
> 지어내지 마세요.

## 스킬이 "이슈 트래커에 발행하라"고 할 때

Jira 티켓을 새로 만드는 대신, **붙여넣기 가능한 티켓 초안**을 대화에 출력합니다. 형식:

```
[SOMA] <제목 — 한국어 한 줄>

## 배경
...

## 원하는 상태
...

## 완료 조건
- [ ] ...

## 참고
- 파일: apps/web/src/... , apps/api/src/...
- 관련 문서: docs/ADR.md ADR-0NN
```

여러 건이면 티켓 하나당 위 블록 하나씩, 우선순위 순으로 출력합니다.
사용자가 Jira에 만든 뒤 키(`SOMA-123`)를 알려주면, 그때부터 그 키로 부릅니다.

`/to-tickets`처럼 여러 티켓을 쏟아내는 스킬은 마지막에 "이 중 Jira에 올릴 것을 골라주세요"로
끝냅니다. 임의로 GitHub Issue를 만들어 대체하지 않습니다.

## 스킬이 "해당 티켓을 가져오라"고 할 때

에이전트가 Jira를 조회할 수 없으므로 다음 순서로 확보합니다.

1. 현재 브랜치명·PR 제목에서 키를 추출합니다: `git branch --show-current`, `gh pr view --json title`.
   브랜치 규칙이 `feat/SOMA-123-<slug>`이므로 키는 여기서 거의 항상 나옵니다.
2. 티켓 본문이 필요하면 **사용자에게 붙여넣기를 요청**합니다.
   ("SOMA-123 본문을 붙여주세요" — 한 번의 왕복으로 끝나게 요청 범위를 좁힐 것.)
3. 본문 없이도 코드·문서로 충분히 추론되는 부분은 먼저 진행하고, 티켓 본문이 있어야만
   갈리는 판단만 물어봅니다.

## 브랜치·PR 규칙 (Jira 자동화가 여기에 걸려 있음)

`CLAUDE.md`의 "이슈 추적 (Jira 연동)" 절이 정본이며, 요약하면:

- 브랜치명에 **대문자** 키를 포함: `feat/SOMA-123-exit-review-modal` (타입 뒤, 설명 앞)
- PR 제목: `SOMA-123 <한국어 요약>`
- 커밋 메시지에는 키를 넣지 않습니다(Conventional Commits 그대로).
- 자동 전이: 브랜치 생성 → `In Progress`, PR 오픈 → `검토 중`, PR 머지 → `Done`.
  `보류 중`은 사람이 수동으로만 넣고 뺍니다. 에이전트가 상태를 바꾸려 하지 마세요.

키가 빠진 브랜치는 Jira 연결이 끊깁니다. 브랜치를 새로 만들 때는 키를 먼저 확인하고,
모르면 만들기 전에 물어봅니다.

## GitHub Issues의 위치

GitHub Issues는 **외부 제보용 인박스**입니다(현재 열린 것 소수). 정식 작업은 Jira로 옮겨
진행하므로, 에이전트는 GitHub Issue를 참고 자료로 읽을 수는 있어도(`gh issue view <n> --comments`)
거기에 작업 계획을 쌓지 않습니다.

## PR을 요청 접수 창구로 쓰는가

**아니오.** 외부 PR은 트리아지 큐에 넣지 않습니다.

## Wayfinding 운영

`/wayfinder`가 쓰는 map/child 구조는 Jira 티켓(Epic ↔ 하위 작업)으로 표현합니다.
에이전트가 Jira에 쓸 수 없으므로, map과 child는 **대화 안의 초안 + 사용자가 Jira에 반영**
방식으로만 운영합니다. 트리 규모가 커져 왕복이 비싸지면, 그 세션 한정으로
`.scratch/<feature>/`에 map을 두고 확정된 것만 Jira로 승격하세요.
