# 도메인 문서

엔지니어링 스킬들이 이 레포를 탐색할 때 도메인 문서를 어떻게 읽어야 하는지 정합니다.

## 배치: 단일 컨텍스트

`apps/web`(Next.js) · `apps/api`(Spring Boot) · `apps/mobile`(Expo)로 앱은 여러 개지만,
제품 도메인 용어(연습·씬·노트·리포트 등)는 셋이 **공유**합니다. 그래서 용어집은 하나로 둡니다.

```
/
├── CONTEXT.md      ← 용어집 (/domain-modeling이 용어가 확정될 때 채웁니다)
├── docs/
│   └── ADR.md      ← 아키텍처 결정 기록 (단일 파일, ADR-001~ 번호)
└── apps/
```

## 탐색 전에 읽을 것

- 루트 **`CONTEXT.md`** — 있으면 읽습니다.
- **`docs/ADR.md`** — 손대려는 영역과 닿는 ADR을 읽습니다.
  이 레포는 `docs/adr/` 디렉토리가 아니라 **단일 파일**을 씁니다. 스킬 템플릿이
  `docs/adr/`를 말하면 `docs/ADR.md`로 읽으세요.
- 앱별 상세는 각 앱 디렉토리의 문서를 따릅니다(`apps/api/AGENTS.md` 등).

없는 파일은 **조용히 넘어갑니다.** 부재를 지적하거나 미리 만들자고 제안하지 마세요.
`/domain-modeling`(→ `/grill-with-docs`, `/improve-codebase-architecture` 경유)이
용어나 결정이 실제로 확정될 때 지연 생성합니다.

## 용어집의 어휘를 쓸 것

출력물이 도메인 개념을 지칭할 때(티켓 제목, 리팩터 제안, 가설, 테스트 이름)
`CONTEXT.md`에 정의된 용어를 그대로 씁니다. 용어집이 피하는 동의어로 흘러가지 마세요.

필요한 개념이 용어집에 없다면 그건 신호입니다 — 프로젝트가 쓰지 않는 언어를 지어내고 있거나
(재고할 것), 진짜 빈칸이거나(`/domain-modeling`을 위해 적어둘 것) 둘 중 하나입니다.

## ADR 충돌은 드러낼 것

출력이 기존 ADR과 어긋나면 조용히 덮어쓰지 말고 명시적으로 꺼냅니다.

> _ADR-003(임시 API는 `/api/v1/*` REST 계약)과 어긋납니다 — 다만 다시 열어볼 만한 이유는…_

새 ADR을 추가할 때는 `docs/ADR.md` 끝에 다음 번호로 이어 붙이고, 기존 항목의
**결정 / 이유 / 트레이드오프** 세 줄 구조를 그대로 따릅니다.
