# SOMA-520: Prometheus·Grafana Cloud 모니터링 명세

상태: 대화에서 확정한 요구와 상세 설계의 구현 제안을 종합한 명세다. 코드·DB·Cloud 설정의 적용이나 운영 검증 완료를 뜻하지 않는다.

## Problem Statement

운영 담당자는 dev와 운영의 상태, 요청량, 오류율, 응답시간을 한곳에서 확인할 수 없다.
영상 분석이 대기 중인지, 코치·리포트 요청이 오래 걸리는지, 서버 자원이나 DB·백업에 문제가 있는지 각각 조사해야 한다.
현재 공개 health 응답은 DB 연결까지 확인하지 않고, 배포 사이에 발생하는 장애를 지속 감시하는 구성도 없다.

Sentry와 Langfuse는 상세 조사에 도움이 되지만 반복 보고 억제와 수신 누락 가능성이 있어 실제 실행량·실패율을 대신할 수 없다.
같은 홈서버에 감시 기능을 전부 두면 전원·회선 장애 때 알림도 함께 멈춘다.
추가 월 비용 없이 이 빈틈을 줄이면서, 운영 담당자 3명이 자신의 권한으로 상태를 확인할 수 있어야 한다.

## Solution

홈서버의 Prometheus가 dev·운영의 API, External Operation, 호스트, DB 연결, 백업 지표를 30초마다 수집해 30일 보관한다.
Grafana Cloud Free는 PDC라는 사설 데이터 소스 보안 연결을 통해 이를 조회하고 대시보드와 Slack 알림을 제공한다.
홈서버에 Grafana를 설치하지 않으며, 화면은 개인별 Cloud 계정으로 접속한다.

운영 담당자는 서비스 전체, 분석·코치, 서버·DB·백업의 세 화면에서 상태를 확인한다.
이상이 있으면 오류 상세는 Sentry, AI 호출 상세는 Langfuse로 이동한다.
별도의 Cloud 외부 점검이 두 환경의 공개 접근을 1분마다 확인해 홈서버 전체 장애도 감지한다.

| 사용자에게 제공할 결과 | 확정 내용 |
|---|---|
| 환경·사용자 | dev·운영 모두, 개인 계정 3명, 관리자 1명·조회 전용 2명 |
| 보관 | 로컬 운영 지표 30일, Cloud 외부 점검 지표 14일 |
| 통지 | 두 환경 모두 24시간 Slack #서비스-장애, 초기 대응 담당은 사용자 본인 |
| 반복·복구 | 같은 장애를 묶어 최초·1시간마다 재알림·조건 해소 통지 |
| 운영 방식 | 저장소 파일로 설정 변경·적용, 계획 점검은 종료 시각이 있는 일시 중지 |
| 비용·복구 | 추가 월 비용 없이 시작, 일반 재시작 때 기록 유지, 디스크 손실 때 과거 지표 손실 수용 |

## User Stories

1. 운영 담당자로서 서비스 전체 상태를 한 화면에서 보고 싶다. 이상이 생긴 환경과 대상을 빠르게 찾기 위해서다.
2. 운영 담당자로서 dev와 운영을 선택해 같은 지표를 보고 싶다. 개발 중 문제를 운영 장애와 혼동하지 않기 위해서다.
3. 운영 담당자로서 API 요청량을 시간대별로 보고 싶다. 서비스 사용량과 부하 변화를 파악하기 위해서다.
4. 운영 담당자로서 API의 오류 건수와 오류율을 함께 보고 싶다. 소수 요청에서 생긴 비율 변화와 반복 장애를 구분하기 위해서다.
5. 운영 담당자로서 일반 API 응답시간과 p95를 보고 싶다. 응답이 느려지는 추세를 발견하기 위해서다.
6. 운영 담당자로서 진행 중인 코치·리포트 요청의 경과 시간을 보고 싶다. 아직 응답하지 않아 완료 지표에 잡히지 않은 지연을 찾기 위해서다.
7. 운영 담당자로서 활성 알림과 마지막 지표 갱신 시각을 보고 싶다. 대시보드의 정보가 현재 상태를 반영하는지 판단하기 위해서다.
8. 운영 담당자로서 요청 없음·수집 전·수집 실패를 구분해 보고 싶다. 데이터가 비어 있다는 이유만으로 정상이나 장애를 잘못 판단하지 않기 위해서다.
9. 운영 담당자로서 분석·코치·리포트의 기능별 실행량을 보고 싶다. 어떤 기능이 사용되고 부하를 만드는지 알기 위해서다.
10. 운영 담당자로서 새 External Operation과 멱등 응답 재사용을 구분하고 싶다. 같은 요청의 재전송으로 기능 사용량이 부풀려지지 않게 하기 위해서다.
11. 운영 담당자로서 고유 External Operation 수와 실제 외부 호출 수를 구분하고 싶다. 재시도로 발생한 추가 시도를 파악하기 위해서다.
12. 운영 담당자로서 분석을 기다리는 External Operation 수를 보고 싶다. 분석 수요가 처리 능력을 넘는지 판단하기 위해서다.
13. 운영 담당자로서 가장 오래 기다린 분석의 대기 시간을 보고 싶다. 오랫동안 시작되지 않는 분석을 놓치지 않기 위해서다.
14. 운영 담당자로서 분석의 대기·실행·전체 경과 시간을 구분하고 싶다. 지연이 생긴 구간을 좁히기 위해서다.
15. 운영 담당자로서 영상 길이와 실제 분석 처리 시간을 구분하고 싶다. 다른 의미의 숫자로 성능을 잘못 해석하지 않기 위해서다.
16. 운영 담당자로서 새 분석의 대기와 재시도를 기다리는 상태를 구분하고 싶다. 실패로 인한 대기가 일반 대기열에 가려지지 않게 하기 위해서다.
17. 운영 담당자로서 현재 처리 흐름에서 확정된 실패와 자동 재시도 중 상태를 구분하고 싶다. 아직 회복을 시도하는 흐름을 종료된 실패로 알리지 않기 위해서다.
18. 운영 담당자로서 실패했던 External Operation이 재개돼 성공한 사실을 구분하고 싶다. 고유 실행 수와 성공·실패 종료 사건을 올바르게 해석하기 위해서다.
19. 운영 담당자로서 Expected Rejection을 장애 알림에서 제외하고 싶다. 정상적인 입력 거절에 대응 시간을 쓰지 않기 위해서다.
20. 운영 담당자로서 External Failure와 Unexpected Failure의 분류를 재시도 뒤에도 확인하고 싶다. 외부 의존 문제와 코드·설정 문제의 조사 방향을 정하기 위해서다.
21. 운영 담당자로서 원인 분류가 남지 않은 종료 실패를 별도로 보고 싶다. 정보 누락을 정상적인 거절로 오인하지 않기 위해서다.
22. 운영 담당자로서 Lease를 잃어 거부된 완료를 실제 성공과 구분하고 싶다. 중복 실행이나 늦은 응답이 처리 실적을 왜곡하지 않게 하기 위해서다.
23. 운영 담당자로서 Grafana에서 Sentry의 오류 상세로 이동하고 싶다. 지표에서 발견한 이상을 예외 정보와 연결해 조사하기 위해서다.
24. 운영 담당자로서 Grafana에서 Langfuse의 AI 호출 상세로 이동하고 싶다. 분석·코치·리포트의 모델 호출을 조사하기 위해서다.
25. 운영 담당자로서 AI 호출 기록과 토큰 정보의 누락 가능성을 알고 보고 싶다. 관측치를 완전한 비용 정산 결과로 오인하지 않기 위해서다.
26. 운영 담당자로서 호스트 CPU 사용률을 보고 싶다. 분석과 다른 서비스가 공유하는 자원 압박을 확인하기 위해서다.
27. 운영 담당자로서 호스트의 사용 가능한 메모리를 보고 싶다. 메모리 부족으로 서비스가 불안정해지는 상황에 대응하기 위해서다.
28. 운영 담당자로서 데이터 디스크 여유를 보고 싶다. 서비스 데이터와 모니터링 기록의 저장 공간 부족을 발견하기 위해서다.
29. 운영 담당자로서 API의 JVM 메모리·GC·DB 연결 풀을 보고 싶다. 호스트 부하와 API 내부 자원 문제를 구분하기 위해서다.
30. 운영 담당자로서 API가 실제로 DB에 연결할 수 있는지 보고 싶다. 공개 health 응답만 정상인 DB 장애를 발견하기 위해서다.
31. 운영 담당자로서 환경별 마지막 백업 성공과 미해결 실패를 보고 싶다. 복구 가능한 시점이 오래되는 상황을 알기 위해서다.
32. 운영 담당자로서 백업 상태 파일의 누락·파손·목적지 불일치를 구분하고 싶다. 읽지 못한 상태를 백업 성공으로 오인하지 않기 위해서다.
33. 운영 담당자로서 공유 호스트 자원이 한 번만 집계되기를 원한다. dev와 운영의 합계에서 같은 자원을 중복 계산하지 않기 위해서다.
34. 운영 담당자로서 홈서버 바깥에서 두 환경의 공개 접속을 1분마다 점검하고 싶다. 실제 인터넷 경로를 통한 접근 가능 여부를 확인하기 위해서다.
35. 운영 담당자로서 집의 전원이나 회선이 끊겨도 외부에서 알림을 받고 싶다. 홈서버 안의 감시가 함께 멈추는 상황을 놓치지 않기 위해서다.
36. 운영 담당자로서 Prometheus·PDC 연결과 필수 수집 지표가 끊겼을 때 알림을 받고 싶다. 서비스가 정상이어도 모니터링이 중단된 상태를 알기 위해서다.
37. 운영 담당자로서 로컬 지표를 30초 간격으로 수집해 30일간 보고 싶다. 최근 운영 변화와 장애 전후 추이를 비교하기 위해서다.
38. 운영 담당자로서 외부 점검 지표의 Cloud 보관 기간을 구분해 보고 싶다. 무료 플랜의 14일 기록을 로컬의 30일 기록과 혼동하지 않기 위해서다.
39. 운영 담당자로서 일반 재시작 뒤에도 기존 지표를 조회하고 싶다. 재배포 때마다 조사에 필요한 기록이 사라지지 않게 하기 위해서다.
40. 운영 담당자로서 디스크 손실 뒤에는 설정을 복구해 수집을 다시 시작하고 싶다. 합의한 과거 지표 손실 범위 안에서 모니터링을 복원하기 위해서다.
41. 운영 담당자로서 수집 공백과 다시 수집하기 시작한 시각을 알고 싶다. 기록이 없는 기간을 정상 운영 기간으로 해석하지 않기 위해서다.
42. 관리자로서 홈서버에 Grafana를 추가 설치하지 않고 Cloud에서 화면과 알림을 운영하고 싶다. 직접 관리할 서비스 수를 줄이기 위해서다.
43. 관리자로서 지표를 로컬에 보관하면서 Cloud에서 안전하게 조회하고 싶다. 30일 보관과 사설 데이터 소스 접근을 함께 유지하기 위해서다.
44. 관리자로서 추가 월 비용 없이 필요한 모니터링을 운영하고 싶다. 합의한 운영 예산을 유지하기 위해서다.
45. 관리자로서 Cloud의 사용자 수와 외부 점검 사용량을 확인하고 싶다. 무료 한도를 넘기는 설정 변경을 발견하기 위해서다.
46. 관리자로서 세 운영 담당자가 개인별 Cloud 계정으로 접속하게 하고 싶다. 공유 계정 없이 접근 주체와 권한을 구분하기 위해서다.
47. 관리자로서 한 명만 설정을 변경하고 나머지 두 명은 조회하게 하고 싶다. 운영 설정의 변경 권한을 통제하기 위해서다.
48. 조회 담당자로서 설정을 바꾸지 않고 대시보드와 알림 상태를 보고 싶다. 운영 상황을 파악하면서 설정을 실수로 변경하지 않기 위해서다.
49. 관리자로서 PDC가 Prometheus에만 접근하게 하고 싶다. Cloud의 조회 연결이 DB와 다른 내부 서비스까지 닿지 않게 하기 위해서다.
50. 관리자로서 관리용 지표와 점검 경로에 접근 제어를 두고 싶다. 공개 서비스 경로로 내부 관측 정보가 노출되지 않게 하기 위해서다.
51. 운영 담당자로서 민감한 원문과 사용자 식별자가 지표에 들어가지 않기를 원한다. 운영에 필요한 집계만 공유하기 위해서다.
52. 장애 대응 담당자로서 dev와 운영의 알림을 모두 24시간 Slack에서 받고 싶다. 시간대와 관계없이 상태 변화를 확인하기 위해서다.
53. 장애 대응 담당자로서 같은 장애는 최초 통지 후 1시간마다 다시 알림을 받고 싶다. 알림 폭주를 줄이면서 해결되지 않은 문제를 잊지 않기 위해서다.
54. 장애 대응 담당자로서 정상 관측이 돌아오면 복구 통지를 받고 싶다. 계속 대응할 필요가 있는지 판단하기 위해서다.
55. 장애 대응 담당자로서 실패 발생 조건의 해제와 해당 External Operation의 성공을 구분하고 싶다. 시간창에서 실패가 사라진 것을 실제 성공으로 오인하지 않기 위해서다.
56. 장애 대응 담당자로서 알림에 환경·대상·조건·관측값·시각·확인 링크가 함께 나오기를 원한다. 별도 검색을 줄이고 조사에 착수하기 위해서다.
57. 장애 대응 담당자로서 계획 점검의 알림을 종료 시각까지 일시 중지하고 싶다. 예정된 작업의 알림을 줄이면서 감시 재개를 잊지 않기 위해서다.
58. 장애 대응 담당자로서 초기 알림 기준을 첫 일주일 관측 후 조정하고 싶다. 실제 서비스의 지연과 오류 빈도에 맞춰 운영하기 위해서다.
59. 관리자로서 대시보드·알림 설정을 저장소 파일로 변경하고 적용하고 싶다. 변경 이력과 복구 기준을 남기기 위해서다.
60. 관리자로서 설정 적용 전 차이를 확인하고 같은 설정을 안전하게 재적용하고 싶다. 대시보드·알림·채널이 중복되거나 다른 설정이 덮이지 않게 하기 위해서다.
61. 관리자로서 시크릿을 선언 파일과 로그에서 분리하고 싶다. 설정 공유와 자동화 과정에서 자격증명이 노출되지 않게 하기 위해서다.
62. 배포 담당자로서 앱을 배포해도 모니터링이 재시작되지 않기를 원한다. 배포 전후의 상태를 계속 관찰하기 위해서다.
63. 배포 담당자로서 모니터링이 중단돼도 앱을 배포할 수 있기를 원한다. 관측 장애가 서비스 복구를 막지 않게 하기 위해서다.
64. 배포 담당자로서 실패 분류를 보존하는 스키마가 이전 앱과도 호환되기를 원한다. 앱 복구 때 DB 데이터를 되돌리지 않아도 되게 하기 위해서다.
65. 운영 담당자로서 dev와 격리 환경에서 장애·복구 알림을 실제로 검증하고 싶다. 운영 데이터를 변경하지 않고 감시가 동작한다는 근거를 얻기 위해서다.
66. 운영 담당자로서 연속된 공개 접속 장애의 알림을 5분 이내에 확인하고 싶다. 장애를 늦게 알아차리는 시간을 줄이기 위해서다.
67. 개발자로서 기존 API·PostgreSQL·Compose 테스트 경계에서 관측 결과를 검증하고 싶다. 새로운 테스트 전용 구조를 늘리지 않고 회귀를 잡기 위해서다.
68. 서비스 이용자로서 모니터링 추가 뒤에도 기존 인증·업로드·분석·코치 기능이 같은 계약으로 동작하기를 원한다. 운영 개선 작업이 연습 흐름을 바꾸지 않게 하기 위해서다.

## Implementation Decisions

### 구성과 책임

1. Prometheus는 로컬 지표 수집·저장을, PDC agent는 사설 조회 연결을, Grafana Cloud는 대시보드·규칙 평가·통지를 담당한다.
   로컬 Grafana, 별도 Alertmanager, 로컬 지표의 Cloud Metrics 복제 저장은 초기 구성에 포함하지 않는다.
2. Cloud는 로컬 Prometheus를 직접 조회한다. 따라서 로컬 30일 보관은 Cloud 저장소의 14일 제한과 별개다.
   홈서버·회선·PDC가 끊기면 과거 로컬 기록의 조회와 서비스 지표 평가도 실패하므로 연결 오류와 외부 접속 점검을 따로 감시한다.
3. API 관측 계층에는 Actuator·Micrometer 기반 요청량·HTTP 상태·시간, JVM·GC·DB 연결 풀 지표를 추가한다.
   기존 실패 보고와 Sentry의 반복 억제 동작은 유지한다.
4. 분석·코치·리포트 계측은 기존 애플리케이션 서비스와 External Operation 원장의 성공한 상태 전이를 사용한다.
   재시도·Lease·멱등성의 기존 계약을 변경하지 않는다. 집계 조회는 JPA와 기존 영속 어댑터 경계를 따른다.
5. 내부 DB 연결 점검기는 API의 인증된 DB health를 제한 시간 안에 확인한다.
   node exporter는 호스트 CPU·가용 메모리·데이터 디스크를, 백업 상태 exporter는 환경별 마지막 성공·미해결 실패·목적지 일치·읽기 성공을 제공한다.
6. 백업 상태 exporter는 상태 볼륨만 읽기 전용으로 접근하고 AWS·DB 자격증명을 받지 않는다.
   기존 파일 접근 권한을 확인해 읽기 권한을 구성한다. 누락·파손·목적지 불일치는 성공이나 정상값으로 숨기지 않는다.
7. 호스트 수집은 필요한 경로를 읽기 전용으로 관찰하는 구성으로 제한하고 실제 Linux 호스트 수치와 대조한다.
   모든 컨테이너 자원 수집을 위한 cAdvisor·Docker socket 접근은 추가하지 않는다.

### 네트워크·접근·배포

1. 앱이 환경별 수집 네트워크를 만들고 API를 기존 기본망과 자기 환경의 수집망에 연결한다.
   모니터링 프로젝트는 두 수집망을 참조하므로 앱 기동이 모니터링의 존재에 의존하지 않는다.
2. Prometheus와 내부 DB health 점검기는 환경별 수집망에 연결한다. 환경별로 고유한 API 별칭을 사용해 대상이 혼동되지 않게 한다.
   PDC는 Prometheus와의 조회망에만 연결하고 목적지를 Prometheus의 조회 포트로 제한한다.
3. DB·웹·터널·백업의 기존 기본망과 dev·운영 데이터 경계를 유지한다.
   내부 DB health 점검기에 DB 기본망 연결이나 DB 비밀번호를 제공하지 않는다.
4. API 관리 경로는 일반 API와 분리한 관리 포트에서 필요한 metrics·DB health만 제공한다.
   환경별 수집 자격증명과 명시적 접근 제어를 두고 기존 사용자 인증과의 충돌을 확인한다.
   관리 포트·Prometheus·exporter에 호스트 공개 포트를 추가하지 않는다.
5. 기존 공개 API·health 응답·웹 프록시 계약을 유지한다.
   공개 health는 웹·터널·API 접근을 확인하는 용도로 사용하며 DB 연결과 실제 분석 성공은 별도 지표로 판단한다.
6. 모니터링은 앱과 다른 Compose 프로젝트·버전·적용 명령으로 운영한다.
   일반 앱 배포가 모니터링을 재생성하지 않고, 모니터링이 중단돼도 앱 배포가 성공해야 한다.
   환경 전체 철거 때는 모니터링의 수집망 연결을 먼저 정리한다.
7. 화면은 Cloud 계정 로그인으로 접근한다. 초기 Tailscale 전용 화면 접근 결정은 이 방식으로 대체했고,
   Tailscale은 서버 관리·배포에 유지한다. PDC는 브라우저 접속을 Tailscale로 제한하는 기능이 아니다.
8. 사람 계정은 관리자 1명·조회 전용 2명으로 구성하고 초기 관리자는 사용자 본인이다.
   자동화 자격증명은 사람의 로그인 계정과 분리한다.

### 지표 의미와 실패 분류 보존

1. HTTP 요청 수에는 폴링·재요청·멱등 응답 재사용을 포함한다.
   기능 실행 수는 새로 접수된 고유 External Operation 기준이고 실제 외부 호출·재시도 수는 각 시도 기준이다.
   실행 시도는 선점 뒤 첫 외부 호출에 진입한 횟수이며, 외부 호출 수는 모델·분석·음성·스토리지 Port의 호출마다 센다.
   같은 실행 안의 모델 재생성은 외부 호출 수를 늘리지만 고유 실행 수나 실행 시도 수를 늘리지 않는다.
   SDK 내부의 전송 재시도나 네트워크 패킷 수까지 집계하는 지표는 아니다.
2. 최종 실패는 현재 서버 처리 흐름에서 자동 재시도로 다시 대기 중인 상태와 구분해 failed로 확정한 종료 사건이다.
   같은 External Operation이 나중에 재개될 수 있으므로 영구 실패를 뜻하지 않는다.
   고유 실행 수와 성공·실패 종료 사건 수는 상호 배타적인 합계가 아니다.
3. 분석의 최초 대기, 재시도 대기, 실제 실행, 최초 접수부터의 전체 경과 시간을 구분한다.
   기존 행의 갱신 시각 차이나 영상 길이를 실제 처리 시간으로 해석하지 않는다.
4. 코치·리포트의 60초 지연 기준은 서버에서 관찰하는 HTTP 요청 시작부터 응답 처리 종료까지다.
   모델 호출 시간·멱등 응답 대기·DB의 running 나이를 같은 값으로 취급하지 않는다.
   브라우저 취소 뒤 서버 처리가 계속될 수 있고, 프로세스 종료 뒤 남은 running 행은 상태·Lease 지표로 다룬다.
5. 계측은 성공한 상태 전이를 기준으로 한다. 중복 요청이나 Lease를 잃어 거부된 완료를 다시 세지 않는다.
   관측 카운터의 재시작·수집 공백 한계를 표시하고 현재 대기·실행 상태는 DB에서 다시 읽는다.
6. Expected Rejection은 장애 알림에서 제외하고 External Failure·Unexpected Failure는 기존 분류를 유지한다.
   Sentry 이벤트 수를 실제 실패율로 사용하지 않으며 Langfuse 수치를 완전한 비용 정산 자료로 취급하지 않는다.
7. 상세 설계에서 도출한 구현안으로, External Operation 원장에 마지막 실패 분류를 담는 비워둘 수 있는 메타데이터를 추가한다.
   기존 세 분류를 text와 CHECK 제약으로 제한하고 실패·재큐 상태 전이의 같은 트랜잭션에서 기록해 재시도 소진까지 보존한다.
   종료 계측에 이 값을 전달한다. 공개 응답과 Lease·재시도 횟수 계약은 유지한다.
8. 원인을 복구할 수 없는 기존 행·비정상 종료는 분류 미확인으로 표시한다.
   이를 Expected Rejection으로 추정하지 않고 새로운 종료 사건에 대해 관측 정보 누락 경고로 구분한다.
   네 번째 도메인 실패 종류를 만들거나 도입 전에 끝난 실패를 소급 통지하지 않는다.
9. 추가 메타데이터는 이전 앱이 무시해도 동작하는 형태로 확장한다.
   앱 복구 때 추가 컬럼을 즉시 삭제하지 않으며 이전 앱과 확장 스키마의 호환성을 검증한다.
10. 지표 구분값인 label은 환경·서비스·라우트 템플릿·HTTP 상태·External Operation 종류·실패 분류처럼 범위가 정해진 값으로 제한한다.
    사용자·세션·External Operation UUID, 원문 URL 경로, 토큰, 프롬프트·영상 내용, 백업 객체 키·해시는 넣지 않는다.

### 화면과 알림

| 대시보드 | 내용 |
|---|---|
| 서비스 전체 | 외부 접속 상태, API 요청량·5xx·응답시간, 활성 알림, 지표 갱신 상태 |
| 분석·코치 | 고유 실행·성공·실패 종료·재시도, 분석 대기 건수·최장 대기·전체 시간, 코치·리포트 처리 시간 |
| 서버·DB·백업 | 호스트 CPU·메모리·디스크, API JVM·DB 연결 풀, DB 연결 가능 여부, 마지막 백업 성공·실패 |

환경·기간 선택을 제공하고 기본 시간은 한국 시간·최근 1시간으로 둔다.
공유 호스트 자원은 한 번만 집계한다. 요청 없음·아직 수집 전·수집 실패를 구분하고 상세 조사 링크에는 환경과 기간을 안내한다.

Cloud 규칙은 1분마다 평가한다. 다음 값은 실측 성능이 아니라 합의한 초기 운영 기준이며 첫 7일의 실제 분포와 대응 결과로 조정한다.

| 대상 | 초기 조건 |
|---|---|
| 외부 접속 | 해당 환경의 최근 5분 점검 중 3회 실패 |
| Prometheus·PDC·필수 수집 | 연결·조회 실패 또는 필수 수집 중단 2분 지속 |
| API 오류 | 환경별 최근 5분 5xx 3건 이상이면서 요청 대비 5xx 비율 5% 이상 |
| 분석·코치·리포트 최종 실패 | External Failure·Unexpected Failure로 끝난 최종 실패 1건부터 발생 통지 |
| 분석 지연 | 1분부터 화면 표시, 대기열 3분 초과 또는 최초 접수 후 미완료 5분 초과 시 Slack |
| 코치·리포트 지연 | 서버에서 관찰하는 진행 중 HTTP 요청이 60초 초과 |
| 일반 API 지연 | 최근 5분 요청 20건 이상이고 p95가 2초를 넘는 상태가 5분 지속 |
| CPU | 호스트 사용률 90% 이상이 10분 지속 |
| 메모리 | 호스트 가용 메모리 10% 미만이 5분 지속 |
| 디스크 | 데이터 디스크 여유 15% 미만이 5분 지속, 5% 미만은 즉시 심각 상태 |
| DB | 내부 DB 연결 점검 실패가 2분 지속 |
| 백업 | 마지막 성공 후 26시간 초과 또는 미해결 실패 상태가 5분 지속 |

p95는 응답시간을 빠른 순서로 놓았을 때 95% 지점이다.
일반 API 지연에는 health·metrics 점검과 분석·코치·리포트의 장시간 처리 경로를 섞지 않는다.

최종 실패 발생 규칙은 최근 5분의 새 종료 사건을 평가한다.
해제는 “새 최종 실패 발생 조건 해소”로 통지하며 해당 External Operation이 성공했다는 의미로 쓰지 않는다.
가용성 규칙은 정상 관측이 돌아온 뒤 복구를 통지하고, 해제 후 재발은 새 장애로 최초 통지한다.

알림은 두 환경 모두 24시간 #서비스-장애로 보내고 환경·대상·조건·관측값·시각·대시보드·확인 절차를 포함한다.
같은 장애는 최초 통지 후 1시간마다 재알림하고 정상 관측 뒤 복구를 알린다.
환경·공유 호스트·데이터 소스를 기준으로 묶어 같은 원인의 알림 폭주를 줄인다.
운영의 긴급 장애를 우선 처리하며 계획 점검에는 종료 시각이 있는 일시 중지를 제공한다.

요청이 없을 때 카운터는 0, p95는 표본 없음으로 표시한다.
필수 대상의 부재·수집 실패·집계 갱신 중단은 전용 규칙으로 감지한다.
PDC·Prometheus 조회의 Error·No Data를 2분 지속 시 알리는 전용 규칙을 검증한 뒤,
개별 서비스 규칙은 전체 데이터 소스 단절 때 직전 상태를 유지해 거짓 복구를 막는다.
직전 상태 유지 설정만 두고 연결·필수 지표 감시를 생략하지 않는다.

### 외부 점검·무료 한도·설정 복구

1. Cloud 외부 위치 1곳에서 dev·운영의 공개 health를 각각 1분마다 HTTP 점검한다.
   제한 시간은 10초이고 HTTP 200과 정상 health 응답을 확인한다.
   31일 계획량은 89,280회로 무료 월 100,000회 안에 들어간다.
2. 실제 Free 플랜·활성 사용자 3명·외부 점검 사용량을 확인하고 추가 위치·주소·수동 점검의 영향을 계산한다.
   무료 한도 초과 때 정확한 중단·재개 동작은 미확인이므로 한도를 넘지 않게 운영한다.
   Cloud에 복제하지 않는 로컬 지표와 Cloud 외부 점검의 보관·한도를 구분한다.
3. Cloud 데이터 소스·대시보드·규칙·통지 정책의 선언 파일과 적용 도구를 저장소에 둔다.
   현재 Cloud가 지원하는 공식 API를 사용하고 적용 전 차이를 보여 준다.
   소유한 리소스만 갱신하며 반복 적용으로 중복을 만들지 않는다.
4. Cloud·PDC·수집·Slack 자격증명은 별도로 공급하고 로그·선언 파일·대시보드에 남기지 않는다.
   설정은 저장소에서, 시크릿은 기존 보호 사본에서 복구한다.
5. Prometheus는 영속 볼륨에 30일 보관하고 실제 수집량의 30일 예상치·버퍼·여유 공간을 충족하는 용량 상한을 둔다.
   용량 제한이 먼저 걸리면 보관 기간이 짧아질 수 있으므로 실제 보관량을 확인한다.
   일반 재시작에는 기록을 유지하고 디스크 자체 손실에는 과거 지표 손실을 수용한다.
6. 최초 적용은 환경별 API 계측·수집망 준비, 상태 볼륨 확인, 모니터링 기동, PDC 연결, Cloud 설정 적용, 검증 순서다.
   모니터링은 앱과 별도로 버전을 고정하고 직전 설정으로 되돌릴 수 있어야 한다.
   앱 계측을 되돌릴 때는 기존 앱 복구 절차를 사용하며 모니터링 복구에 DB 복원·지표 볼륨 삭제를 섞지 않는다.

## Testing Decisions

### 테스트 경계

주요 판정 경계는 **서비스 행동을 발생시킨 뒤 실제 응답·영속 상태·노출 지표·알림 결과를 관찰하는 흐름**이다.
구동은 기존 API 통합 테스트와 실제 배포 스모크를 확장한다.
개별 계측 메서드의 호출 횟수나 내부 자료구조를 테스트 계약으로 고정하지 않는다.
모든 계층을 대체하는 새 공통 테스트 프레임워크는 만들지 않는다.

- API·External Operation: 기존 Spring Boot·MockMvc·실제 PostgreSQL 경계를 사용한다.
  외부 모델·스토리지처럼 제어할 필요가 있는 I/O는 기존 Port나 제공자 경계에서만 대체한다.
- 배포·수집: 기존 Compose 스모크처럼 실제 배포 명령으로 환경을 세워 접근·수집·영속·배포 독립성을 확인한다.
  SQL 원자성과 이전 앱 호환성은 실제 PostgreSQL 테스트로 보완한다.
- Cloud·Slack: 로컬·CI 결과와 별도로 실제 설정 조회·권한·알림 수신을 확인한다.
  로컬 대체 환경이 Cloud의 API 지원·무료 한도·통지 성공까지 검증한 것으로 기록하지 않는다.

### 검증할 외부 행동

| 검증 대상 | 관찰할 완료 결과 |
|---|---|
| HTTP·계측 | 정상·5xx·Expected Rejection·재요청을 구분하고 기존 응답·인증·폴백 유지 |
| 실행·재시도 | 고유 External Operation·실제 시도·재큐·소진·실패 후 재개를 구분하고 중복 완료·Lease 상실을 과대 집계하지 않음 |
| 실패 분류 | 재큐·소진·재시작 뒤 분류 보존, 미분류 처리, 단 한 건의 새 종료 실패 통지, 과거 이력 소급 통지 방지 |
| 스키마 호환 | 기존 데이터가 확장 스키마에서 보존되고 이전 앱이 동작하며 빈 DB·기존 DB 모두 마이그레이션 가능 |
| 시간 | 분석 대기·실행·전체 시간과 서버 HTTP 경과 시간 구분, 영상 길이·잔류 running 행을 처리 시간으로 오인하지 않음 |
| 접근·환경 | 두 환경의 수집 대상 구분, 관리 경로 인증, 공개 metrics 접근 차단, PDC의 DB·다른 목적지 접근 차단 |
| 호스트·백업 | 실제 호스트 수치 대조, 백업 정상·실패·목적지 불일치·누락·파손 구분 |
| 화면·권한 | 세 화면의 정상·무사용·지연·실패·수집 공백, 실제 관리자 1명·조회 전용 2명 권한 확인 |
| 알림 경계 | 조건 직전·충족·지속·해제·재발, 표본 없는 상태, 낮은 요청량, 그룹화·1시간 재알림·일시 중지 검증 |
| 감지 시간 | 연속 공개 접속 장애를 5분 이내 통지, 다른 규칙은 조건과 지속 시간 충족 후 2분 이내 최초 통지 |
| 단절·복구 | PDC·Prometheus 중단·필수 지표 누락 시 경고, 정상 관측 재개 후 복구, 잘못된 정상 표시 방지 |
| 배포 독립성 | 모니터링 중단 중 앱 배포 성공, 일반 앱 배포 전후 모니터링 컨테이너 유지 |
| 영속·재적용 | 재시작 후 기존 지표 조회, 선언 재적용 시 중복 없음, 직전 설정으로 복구 가능 |
| 비용·용량 | 실제 Free 플랜·3명·외부 점검 사용량, 로컬 30일 예상 저장량·여유 확인 |

알림의 1시간 반복이나 26시간 백업 경계를 검증하기 위해 모든 자동 테스트를 실제 시간만큼 대기시키지 않는다.
제어한 시간·표본 입력을 규칙 평가 경계에 제공하고, 실제 Cloud 수신 시험으로 배선과 전송을 별도로 검증한다.
공유 PDC·Prometheus 중단은 두 환경의 관측에 영향을 주므로 격리 환경에서 먼저 시험하고,
실제 공유 구성 시험은 영향과 알림 범위를 정한 점검 시간에 수행한다.

### 기존 테스트의 선례

- CoachReportEndpointIT·ReportEndpointIT: MockMvc와 실제 PostgreSQL, 외부 생성기 경계의 제어된 응답으로 HTTP 계약 확인.
- ExternalOperationIT·PostgresAnalysisStoreIT: 실제 PostgreSQL에서 상태 전이·Lease·동시성·원자성 확인.
- AnalysisWorkerTest·FailureClassifierTest·SentryFailureReporterTest: 기존 실행 흐름과 실패 분류·보고 동작의 좁은 회귀 검사.
- AnalysisWorkerWiringIT·HealthAndBootIT: 실제 애플리케이션 부팅에서 조건부 구성과 설정을 확인하는 선례.
- FlywayForwardMigrationTest·스키마 지문 검사: 기존 DB와 신규 DB의 마이그레이션 경로 및 스키마 일치 확인.
- 기존 홈서버 배포 스모크·복원·백업 검증: 실제 컨테이너와 배포 명령으로 결과를 관찰하고 외부 저장소 I/O만 제어하는 선례.

가장 좁은 관련 검증 후 현재 CI의 API·배포·복원·백업 검증 범위를 실행한다.
이 명세 작성 단계에서는 애플리케이션 테스트나 실제 Cloud·Slack 수신 시험을 실행한 것으로 기록하지 않는다.

## Further Notes

### 합의 상태와 외부 확인

요구 범위·Cloud 구성·접근 인원·보관·알림 기준은 대화에서 확정했다.
실패 분류 보존을 위한 API·DB 메타데이터는 해당 요구를 실현하기 위해 상세 설계에서 도출한 구현안이다.
명세 작성과 ready-for-agent 적용안은 코드·DB·Cloud 변경이나 배포를 실행했다는 의미가 아니다.

호스트 여유 자원은 Tailscale 추가 인증 요구로 실측하지 못했다.
실제 Cloud Free 계정·PDC 연결·사용자 3명·Slack 연결·Sentry와 Langfuse 접근은 구현 때 확인한다.
초기 알림 값은 정상 성능의 실측치가 아니며 첫 7일 관측 후 조정한다.
무료 한도 초과의 정확한 중단·재개 동작은 미확인이다.
홈서버 단절 동안 로컬 과거 지표 조회도 불가능하며 Cloud·Slack의 가용성은 각 제공자에 의존한다.

### 이슈 전달

Jira SOMA가 이슈의 정본이다. 저장소의 사람 작성 원칙에 따라 이 문서는 상세 명세로 두고,
Jira에는 배경·원하는 상태·완료 조건으로 구성한 초안과 이 명세의 참조 한 줄을 전달한다.
적용할 트리아지 라벨은 ready-for-agent이며, 현재 이슈 본문·기존 라벨·실제 게시 여부는 조회하거나 변경하지 않았다.
