# Architecture Decision Records

## 철학
MVP 핵심 기능의 정상 작동을 목표로 빠르게 개발한다. 단, AI 출력처럼 신뢰할 수 없는 경계는 코드로 검증·재계산한다.

유지하는 핵심 가치관:

- 근거 있는 질문으로 배우가 스스로 생각을 채우게 돕는다. 점수, 등급, 4축 평가는 사용자 표면에 두지 않는다.
- 영상 분석은 세션 시작 시 한 번 수행하고, 이후 대화는 분석 결과와 대화 이력에 근거한다.
- 사용자에게 보존을 약속하는 데이터는 플랫폼 DB가 정본이다.
- 향후 Spring Boot, React Native, 공유 패키지로 확장할 수 있게 경계를 유지한다.

> 📌 **경로 표기에 관하여.** 아래 기록 중 일부는 `apps/api-java`를 가리킨다. 그 디렉토리는
> `SOMA-403` 5단계에서 **`apps/api`가 됐고**, 같은 이름이던 FastAPI 트리는 사라졌다. 결정
> 시점의 이름이라 본문은 그대로 두었으니, 경로를 따라갈 때는 `apps/api`로 읽는다. 이관
> 자체의 사양·기록은 `docs/archive/soma287/`에 있다.

## 플랫폼

### ADR-001: pnpm 모노레포를 프로젝트 루트 구조로 사용한다
**결정**: `acttub-platform`은 pnpm workspace 기반 모노레포로 유지한다. 활성 앱은 `apps/web`이며, `apps/api`, `apps/mobile`, `packages/*`는 필요 시 확장한다.
**이유**: 현재는 웹 MVP가 개발 중심이지만, 장기적으로 Spring Boot 백엔드와 React Native 앱이 들어올 가능성이 높다. 루트에 문서, workspace script, lockfile을 두면 제품 요구사항과 API 계약을 앱별 구현보다 상위에서 관리할 수 있다.
**트레이드오프**: 초기에는 단일 Next.js 앱보다 디렉토리 구조가 조금 무겁다. 대신 앱/패키지 경계가 초기에 명확해지고, API/DTO/문서가 특정 앱 하위에 갇히지 않는다.

### ADR-002: 초기 웹 구현은 Next.js App Router로 진행한다
**결정**: 초기 제품 화면은 `apps/web`의 Next.js App Router, TypeScript, Tailwind CSS로 만든다.
**이유**: 현재 저장소에 이미 Next.js 앱이 준비되어 있고, 영상 입력, 분석 대기, 인터뷰, 리포트 화면을 빠르게 검증하기에 적합하다. Server Component를 기본으로 두고 상호작용이 필요한 영역만 Client Component로 분리할 수 있다.
**트레이드오프**: 장기 백엔드가 Spring Boot인 상황에서 Next route handler에 비즈니스 로직이 커질 위험이 있다. 이를 막기 위해 UI는 `src/lib/api/*`를 통해 API를 호출하고, route handler는 얇게 유지한다.

### ADR-003: 임시 API는 `/api/v1/*` REST 계약으로 작성한다
> **개정 (2026-08-08)**: 원래 결정은 "Next.js Route Handler를 임시 API로 사용할 수 있다"였다. 현재 `apps/web`의 하드 룰은 "서버 로직을 여기 두지 않는다"이며, API는 전부 `apps/api` 소관이고 웹은 화면 렌더와 `/v2/*` 프록시만 담당한다. 예전에는 정적 export 빌드가 깨지는 것이 이 경계를 물리적으로 강제했지만, 그 모드를 걷어내면서 지금은 Route Handler를 만들어도 빌드가 통과한다 — 경계를 지키는 것은 규칙뿐이므로 이 ADR만 읽고 Route Handler를 만들지 않는다. versioned REST 계약을 선호한다는 취지 자체는 `apps/api`의 `/v2/*` 계약으로 이어졌다.

**결정**: Spring Boot가 들어오기 전까지 Next.js Route Handler를 임시 API로 사용할 수 있으며, path는 `/api/v1/*` 형태의 versioned REST 계약을 선호한다.
**이유**: 제품 초기에는 프론트엔드와 서버 흐름을 빠르게 검증해야 한다. 하지만 향후 `apps/api`로 이전할 때 프론트엔드 호출부를 크게 바꾸지 않으려면 HTTP path, method, DTO, status code가 안정적이어야 한다.
**트레이드오프**: Next.js 내부 기능에 더 강하게 붙으면 빠를 수 있지만, 백엔드 이전 비용이 커진다. REST 계약을 먼저 고정하면 초기 구현이 약간 더 엄격해진다.

### ADR-004: 질문 기반 UX를 핵심 제품 표면으로 채택한다
**결정**: acttub의 핵심 화면은 질문을 하나씩 이어가는 인터뷰 화면이다. AI는 판단을 확정하지 않고 관찰과 장면 맥락을 바탕으로 질문을 이어간다.
**이유**: 배우에게 표정/동작 같은 결과만 고치라고 하면 심리와 행동이 분리되어 연기가 굳을 수 있다. acttub은 결과를 처방하기보다 결과를 만든 생각, 심리, 상황, 관계, 목표, 서브텍스트를 묻는 도구여야 한다.
**트레이드오프**: 사용자에게 즉시 “결과를 받았다”는 느낌은 약해질 수 있다. 대신 제품의 차별점은 질문 대화에서 나오고, 세션 종료 리포트(ADR-014)가 결과 확인 욕구를 보완한다.

### ADR-005: 점수·등급·4축 평가를 사용자 표면에서 제거한다
> **개정 (2026-07-13)**: 원래 결정은 “피드백 카드·결과지 전면 폐기”였다. ADR-014에 따라 세션 종료 리포트는 허용하되, 점수·등급·4축 평가 금지는 유지한다.

**결정**: 사용자 표면에서 점수, 등급, 레벨, 랭킹, 4축 평가, 평가표를 사용하지 않는다.
**이유**: 제품 방향은 평가 서비스가 아니라 질문 기반 연습 파트너다. 점수화된 화면은 사용자가 AI를 연습 파트너가 아니라 심판으로 느끼게 만든다.
**트레이드오프**: 기존에 구상한 평가 UI/데이터 구조 일부는 버리거나 내부 도구로만 제한해야 한다.

### ADR-006: MVP 범위는 분석 → 인터뷰 → 리포트까지로 제한한다
> **개정 (2026-07-13)**: 원래 범위는 “관찰 확인 + 질문 대화 + 자기 정리 문장 저장”이었다. ADR-014에 따라 관찰 확인과 자기 정리 문장을 제거하고 리포트를 범위에 포함했다.

**결정**: MVP는 영상/맥락 입력, 1회 분석, AI 인터뷰, 세션 리포트 생성·이전 리포트 열람까지를 범위로 한다.
**이유**: 먼저 검증해야 할 것은 “질문을 통해 배우가 놓친 생각을 스스로 발견하고, 그 과정이 근거 있는 리포트로 남는가”다. retake, 전/후 영상 비교가 들어오면 검증 변수가 늘어난다.
**트레이드오프**: 완성형 코칭 서비스처럼 보이는 기능은 줄어든다. 대신 1차 검증 범위를 작게 유지한다.

### ADR-007: 전/후 영상 비교는 후속 범위로 미룬다
> **참고 (2026-07-13)**: 리포트 간 텍스트 비교(`comparison`)는 acting-api 리포트 기능으로 MVP에 포함된다 (ADR-AI-006). 이 ADR이 미루는 것은 영상 단위의 전/후 비교다.

**결정**: 첫 촬영 잠금, 같은 장면 재촬영, 전/후 영상 비교, 보호자 결제 설득용 결과는 MVP에서 제외한다.
**이유**: 전/후 비교는 장기적으로 유용하지만, 알파에서는 인터뷰와 리포트 흐름 자체의 유용성을 먼저 검증해야 한다.
**트레이드오프**: 사용자에게 개선 결과를 시각적으로 보여주는 힘은 약하다. 대신 MVP 구현 범위와 검증 범위를 작게 유지한다.

### ADR-008: 플랫폼이 소유한 데이터는 DB를 정본으로 삼는다
> **개정 (2026-07-13)**: 원래 결정은 “모든 세션/대화 상태를 DB 정본으로 삼아 새로고침/이어하기를 보장한다”였다. 인터뷰 라이브 세션이 acting-api 인메모리로 옮겨지면서(ADR-AI-006) 이어하기 보장은 철회하고, 보존 대상은 복제 저장(ADR-015)으로 좁혔다.

**결정**: 사용자, 영상, 세션 메타, SceneSummary, 대화 turn 복제본, 리포트는 플랫폼 DB에 저장하고 DB를 정본으로 삼는다. 인터뷰 라이브 세션은 acting-api가 소유하며 휘발을 수용한다.
**이유**: 사용자에게 보존을 약속하는 데이터(리포트, 연습 기록)는 서버 메모리나 클라이언트 state만으로는 부족하다.
**트레이드오프**: 인메모리 세션이 소멸하면(404) 인터뷰는 처음부터 다시 시작해야 한다.

### ADR-009: 영상은 세션 시작 시 한 번 분석한다
**결정**: 영상은 세션 시작 시 한 번 분석하고 결과(SceneSummary)를 저장한다. 이후 인터뷰 turn은 저장된 분석 결과와 대화 이력을 바탕으로 진행한다.
**이유**: 매 turn마다 영상을 다시 읽으면 비용, 지연, 결과 불안정성이 커진다. (acting-api 쪽 동일 결정: ADR-AI-003)
**트레이드오프**: 초기 분석 품질이 낮으면 이후 질문 품질도 제한된다.

### ADR-010: 초기에는 멀티모달 파인튜닝을 하지 않는다
**결정**: MVP에서는 멀티모달 파인튜닝을 하지 않는다. API 모델, 프롬프트/스키마 설계, guardrail을 우선한다.
**이유**: 멀티모달 파인튜닝은 비용과 리소스 부담이 크고 초기 검증의 핵심 병목이 아니다. (acting-api 쪽 동일 결정: ADR-AI-001)
**트레이드오프**: 특정 연기 도메인에 최적화된 모델 성능은 초기부터 확보하기 어렵다.

### ADR-011: YouTube 참고 영상은 공식 임베드만 허용한다
**결정**: MVP에서 YouTube 참고 영상은 공식 YouTube iframe 또는 IFrame Player API로만 보여준다. 영상 원본, 오디오, 프레임, 자막은 저장, 캐싱, 백업, 자체 서버 보관, RAG 인덱싱하지 않는다.
**이유**: 저작권과 플랫폼 정책 리스크를 줄이기 위해 YouTube와 권리자의 통제 범위 안에서만 참고 영상을 보여준다.
**트레이드오프**: YouTube 콘텐츠를 직접 분석하거나 검색 품질을 높이는 기능은 제한된다. 표현도 “비슷한 프로 배우 영상”이 아니라 “참고할 수 있는 장면 예시”로 낮춰야 한다.

### ADR-012: UI 레퍼런스는 Toss 디자인 문서를 기준으로 삼는다
**결정**: UI 구현은 `docs/design/Toss-DESIGN.md`를 상세 레퍼런스로 삼고, `docs/design/UI_GUIDE.md`에서 Acttub 전용 적용 규칙을 관리한다. 랜딩/인터뷰 UI 구조는 `docs/design/telta-interview-pro.md`를 참고한다.
**이유**: Acttub MVP는 신뢰감, 명료함, 모바일 사용성, 한국어 가독성이 중요하다. Toss 스타일의 흰 배경, 강한 타이포 위계, 파란 액션 컬러, 절제된 shadow, 명확한 컴포넌트 상태는 질문형 연습 도구와 잘 맞는다.
**트레이드오프**: Toss 브랜드를 그대로 복제하면 Acttub만의 정체성이 약해질 수 있다. 따라서 색상과 컴포넌트 규칙은 레퍼런스로 사용하되, 카피와 제품 표면은 연기 연습 도메인에 맞춘다.

### ADR-013: 내부 용어 사전을 문서와 UI 카피의 기본 기준으로 사용한다
**결정**: 제품 문서, 티켓, 프롬프트, UI 카피는 내부 용어 사전의 표현을 우선 사용한다.
**이유**: “평가”, “점수” 같은 단어는 제품을 평가 서비스처럼 보이게 한다. “질문”, “관찰”, “다시 생각해볼 지점”처럼 낮춘 표현을 쓰면 제품 정체성이 유지된다.
**트레이드오프**: 일부 용어는 아직 v0.1 검토 상태이므로 확정 표현처럼 과도하게 반복하면 나중에 수정 비용이 생긴다. 미확정 용어는 문서에서 열린 결정으로 표시한다.

## 연기 연습 분석

현행 계약은 `apps/api/CONTRACT.md`를 참조한다. 여기에는 결정과 이유만 기록한다.

### ADR-AI-001: Gemini 2.5 Flash + Files API로 영상을 직접 분석
**결정**: 영상 분석은 `gemini-2.5-flash`에 Files API로 영상을 업로드해 모델이 직접 보게 하고, 구조화 JSON(`response_schema`)으로 받는다. 멀티모달 파인튜닝은 하지 않는다.
**이유**: 프레임 추출·STT 등 자체 전처리 파이프라인 없이 대사·표정·움직임을 한 번에 관찰할 수 있고, MVP 단계에서 프롬프트/스키마 반복 개선이 가장 빠르다.
**트레이드오프**: 모델 관찰 품질을 직접 제어할 수 없다. 외부 API 의존으로 비용·지연이 발생한다.

### ADR-AI-002: 영상 분석을 플랫폼 밖 별도 서비스로 분리
> **개정 (2026-08-24)**: **별도 서비스라는 전제가 사라졌다.** 분석을 맡던 Python 서비스는 `SOMA-287` 이관과 `SOMA-403`으로 없어졌고, 지금 영상 분석은 **Spring Boot 백엔드(`apps/api`) 안**에서 돈다 — 도메인은 `feature/analysis`, Gemini 호출은 `integration/observation` 어댑터다. `/summarize`는 이제 없는 경로이고, `HealthAndBootIT.legacyV1PathsAreNotFound`가 v1 경로 다섯을 GET으로 밟아 404를 고정한다. "분석 서비스는 제품 DB에 연결하지 않는다"도 함께 깨졌다 — 같은 프로세스이고 같은 DB다. **취지 둘은 방식을 바꿔 남았다** — 웹이 분석을 하지 않는다는 경계는 그대로고(웹은 화면 렌더와 `/v2/*` 프록시뿐 — ADR-003 개정), 요청-응답 시간 밖에서 돌려야 한다는 요구는 별도 서비스가 아니라 같은 프로세스 안 워커가 받는다(`AnalysisWorkerScheduler`). **이유는 두 갈래였고 둘 다 성립하지 않는다** — "Vercel 함수 timeout"은 웹을 Vercel에 배포하지 않게 되면서 제약 자체가 없어졌고(`apps/web/next.config.ts:67` — EC2 + systemd다), "재시도·교체·독립 배포가 쉽다"는 프로세스를 합치면서 잃었다.

**결정**: 영상 분석을 플랫폼(Next.js) 안에서 하지 않고 별도 Python 서비스(acting-api의 `POST /summarize`)로 분리한다. 플랫폼이 영상 파일과 장면 맥락을 multipart로 전달하고, 분석 서비스는 제품 DB에 연결하지 않는다.
**이유**: 영상 분석은 압축·업로드·모델 처리로 수 분이 걸릴 수 있어 Vercel 함수 timeout을 초과한다. 분리하면 재시도·교체·독립 배포가 쉽다.
**트레이드오프**: 서비스가 둘이 되어 계약 관리 비용이 생기고, 대용량 영상 업로드 동안 클라이언트 타임아웃을 길게 잡아야 한다.

### ADR-AI-003: 영상은 세션 시작 시 1회만 분석
**결정**: 관찰 추출은 세션당 1회다. 이후 질문 turn은 저장된 관찰과 대화 이력만 사용하고 영상을 재분석하지 않는다.
**이유**: turn마다 영상을 재분석하면 비용·지연이 커지고 turn 간 관찰이 흔들려 대화 상태 관리가 불안정해진다.
**트레이드오프**: 최초 분석 품질에 세션 전체가 의존한다.

### ADR-AI-004: 관찰 스키마를 6축 + 이상 구간으로 고정
**결정**: 관찰은 timeline + 6축(대사·템포·높낮이·움직임·표정·감정) + extra로 세분화하고, 이상징후는 구간(start~end, 최소 8초)·what·whyOdd·likelyCause·impactOnIntent의 자기완결 구조로 받는다.
**이유**: 다음 단계 챗 LLM이 영상 없이 이 JSON 하나만 읽고 질문을 만들 수 있어야 한다. 축을 고정해야 관찰 누락과 표현 흔들림이 줄어든다.
**트레이드오프**: 스키마가 커서 프롬프트가 길고, 축에 안 맞는 관찰은 extra로 우회해야 한다.

### ADR-AI-005: severity는 모델 출력을 믿지 않고 코드로 재계산
**결정**: 이상징후의 우선순위(severity)는 모델이 낸 등급을 버리고, 모델의 사실 판단 3개(keyMoment 겹침 / keyDimension 해당 / intentImpact)로부터 점수 공식으로 코드가 재계산하고 재정렬한다. 모델 호출도 temperature 0 + seed 고정이다.
**이유**: 같은 영상에 같은 결과가 나와야 사용자 신뢰와 테스트가 가능하다. LLM은 산술·정렬을 자주 틀린다.
**트레이드오프**: 점수 공식이 코드에 박혀 있어 우선순위 정책을 바꾸려면 배포가 필요하다.

## AI 인터뷰·리포트

### ADR-AI-006: 세 AI 서비스를 acting-api 게이트웨이 하나로 통합 배포
> **개정 (2026-08-24)**: **전제가 통째로 사라졌다.** FastAPI 게이트웨이는 `SOMA-287` 이관과 `SOMA-403`으로 없어졌고, 지금 세 기능은 전부 Spring Boot 백엔드(`apps/api`) 안의 도메인이다(`feature/analysis`·`feature/coach`·`feature/report`). 백엔드에 `X-API-Key`는 남아 있지 않다 — 인증은 사용자 액세스 토큰이고(`platform/security`), 옛 경로 `/coach/start`·`/coach/reply`·`/report`·`/report/history/*`는 전부 404다. **무엇보다 "인터뷰 세션은 인메모리, 리포트 이력은 JSON 파일"이 아니다** — 둘 다 Postgres가 정본이다(`coach_sessions`·`coach_turns`·`reports` 테이블). 그 휘발성을 근거로 세운 것 둘이 함께 근거를 잃었다 — ADR-008(2026-07-13 개정의 이어하기 보장 철회, 그리고 결정·트레이드오프에 아직 남은 "인터뷰 라이브 세션은 acting-api가 소유하며 휘발을 수용한다"·"인메모리 세션이 소멸하면(404)")과 ADR-015(복제 저장, 아래 개정 참조)다. **남은 것은 "단일 Base URL·단일 배포"라는 취지뿐이고**, 그것을 이루는 것은 이제 `/v2/*` 계약 하나다.
> **개정 (2026-08-08)**: "세 서비스의 라우터를 마운트한다"는 서술은 실제 구조와 달랐다. 게이트웨이는 `include_router` 10개를 전부 `acting_api.*`에서 직접 만들고, 서브패키지에서 가져오는 것은 engine·schema뿐이다 — `app.mount()`로 붙는 서브 앱은 없다(`StaticFiles` 마운트만 있다). 서브패키지가 각자 들고 있던 독립 FastAPI 앱은 배포된 요청이 닿을 수 없는 잔해였고, 이 개정과 같은 PR에서 지웠다. **단일 Base URL·단일 `X-API-Key`·단일 배포라는 결정 자체는 그대로 유지된다** — 바뀐 것은 그 하나의 앱을 만드는 방식에 대한 서술뿐이다.

**결정**: summary·coach·report 세 서비스의 라우터를 하나의 FastAPI 앱(acting-api)에 in-process로 마운트해 단일 Base URL과 단일 `X-API-Key` 인증으로 제공한다. 인터뷰 세션은 게이트웨이 인메모리에, 리포트 이력은 JSON 파일에 저장한다.
**이유**: MVP 단계에서 배포·운영 대상을 하나로 줄이고(Render 단일 인스턴스), 클라이언트 연동을 단일 키·단일 주소로 단순하게 유지한다.
**트레이드오프**: 서버 재시작·재배포 시 인터뷰 세션이 소멸하고 리포트 이력도 휘발될 수 있다. 사용자에게 보존을 약속하는 데이터는 플랫폼 DB 복제 저장으로 보완한다 (ADR-015).

### ADR-AI-007: coach와 report는 영상을 보지 않는다
**결정**: 영상 입력은 summary만 받는다. coach는 SceneSummary·대화 이력만, report는 여기에 인터뷰 결과와 같은 사용자의 이전 리포트(비교용)를 더한 것만 입력으로 받는다.
**이유**: 영상 재분석은 비용·지연이 크고 turn 간 관찰이 흔들린다(ADR-AI-003). 후속 단계가 영상에 접근할 수 없어야 분석 1회 원칙이 구조적으로 지켜진다.
**트레이드오프**: 최초 분석이 놓친 것은 대화·리포트 단계에서 복구할 수 없다. 인터뷰에서 배우가 직접 말하는 답이 보완 장치다.

## 통합 (2026-07-13)

### ADR-014: 세션 산출물을 근거 기반 리포트로 확정한다
**결정**: 세션은 acting-api가 생성하는 리포트(headline, biggest_problem, evidence, self_discovery, encouragement, next_step, comparison)로 끝난다. 이전 문서의 “관찰 확인(맞음/아님/모르겠음)” 단계와 “actor-authored 자기 정리 문장”은 제거한다.
**이유**: MVP는 acting-api 계약(`apps/api/CONTRACT.md`)에 의존하며, acting-api에는 관찰 확인·자기 정리에 대응하는 API가 없다. 관찰의 사실 확인과 배우의 자기 발견은 coach 인터뷰 대화 안에서 이루어지고, 그 결과가 리포트의 `self_discovery`로 남는다.
**트레이드오프**: 배우가 관찰을 명시적으로 거절하는 안전장치와 자기 손으로 쓰는 정리 문장이 사라진다. 인터뷰 답변이 그 역할을 대신하며, 필요성이 검증되면 acting-api 계약 확장으로 재도입을 검토한다.

### ADR-015: acting-api의 휘발성 데이터를 플랫폼 DB에 복제 저장한다
> **개정 (2026-08-24)**: **복제할 원본이 없어졌다.** 이것은 acting-api가 외부 서비스이던 시절의 결정이고, 지금 대화 turn과 리포트는 백엔드가 **처음부터 자기 DB에 쓴다**(ADR-AI-006 개정). 쓰기 경로 이중화도, `GET /report/history`와 플랫폼 DB 중 무엇을 읽을지의 선택도 없다 — 그 경로는 404다. `comparison`이 재배포 후 비어 있을 수 있다는 트레이드오프도 같이 사라졌다. **"사용자에게 보존을 약속하는 데이터는 DB가 정본"이라는 취지는 ADR-008에 그대로 살아 있고**, 이 ADR이 그 위에 얹었던 복제 장치만 없어진 것이다.

**결정**: 대화 turn은 매 turn 진행 시, 리포트는 생성 즉시 플랫폼 DB에 복제 저장한다. 이전 리포트 목록 조회는 acting-api `GET /report/history`가 아니라 플랫폼 DB를 사용한다.
**이유**: acting-api의 인터뷰 세션은 인메모리, 리포트 이력은 휘발성 JSON 파일이다(ADR-AI-006). 사용자에게 보존을 약속하는 연습 기록과 리포트는 플랫폼이 보관해야 한다.
**트레이드오프**: 쓰기 경로가 이중화된다. 복제된 turn으로 소멸된 인메모리 세션을 복원할 수는 없고, 리포트 `comparison`은 acting-api 내부 이력에 의존하므로 acting-api 재배포 후에는 비교가 비어 있을 수 있다.

## 백엔드 이관 (2026-08-15)

### ADR-016: api-java를 단일 Gradle 모듈로 유지한다
**결정**: `apps/api-java`를 Gradle 멀티 모듈로 쪼개지 않는다. 패키지 의존 방향은 모듈 경계가 아니라 ArchUnit의 순환 금지 검사로 강제하고, 공유 타입은 커널 패키지를 새로 만들지 않고 각자 제 역할의 패키지에 둔다.
**이유**: 멀티 모듈이 주는 것은 의존 방향의 컴파일 타임 강제 하나인데, 대가로 프로젝트 디렉토리 기준 상대경로(`build.gradle.kts`의 `../api/acting-api/*` 리소스 복사, `AlembicSchema`, `application-contract.yml`, `regen-fingerprint.sh`)와 배포 산출물 경로(`deploy/upload-api-java.sh`), CI 리포트 경로가 동시에 깨진다. **그 예시 넷 중 셋은 그 뒤 사라졌다** — 파이썬 트리(`../api/acting-api/*`)와 `AlembicSchema`는 `SOMA-403` 5단계가, `application-contract.yml`은 계약 하네스와 함께 4단계가 걷어냈다. 남은 것은 `apps/api/scripts/regen-fingerprint.sh`와 배포·CI 경로다. 무엇보다 `@ComponentScan`·`@EntityScan`·`@EnableJpaRepositories`가 하나도 없어 스캔이 순수 패키지 관례에 얹혀 있고, Schema Entity가 스캔 범위를 벗어나면 `ddl-auto: validate`가 **검증 대상 0개로 조용히 통과**한다.
**트레이드오프**: 층 규칙이 컴파일 타임이 아니라 테스트로만 강제되므로, 검사를 지우면 아무도 막지 못한다. 두 번째 배포 산출물이 필요해지거나(워커 분리 등) 순환이 계속 새어나오면 재검토한다.

### ADR-017: api-java를 도메인별 헥사고날로 재편한다
**결정**: `apps/api-java`의 패키지를 비즈니스(`feature`)·배관(`platform`)·외부 연동(`integration`) 세 묶음으로 가르고, 각 비즈니스 도메인 안을 네 층으로 세운다 — `domain`(규칙을 담은 **Domain Model**, 프레임워크 import 금지), `app`(서비스와 **Port** 선언), `adapter`(`web`·`db`·`storage`·`media`·`sched`·`resource`, 그리고 어느 하위에도 속하지 않는 것 — 여럿을 조립하는 배선, 기동 러너 — 은 그 층의 루트), `schema`(**Schema Entity**). 도메인끼리 직접 import하지 않고, 필요한 것은 쓰는 쪽이 자기 `app`에 포트로 선언한다. 이관이 진행 중이므로 한 번에 한 도메인씩 옮기며, 첫 타자는 `practice`다(SOMA-397).
**이유**: 지금 구조는 사고가 아니라 이관 전략의 결과다. 성공 기준이 "FastAPI 계약을 재현한다"였으므로 파이썬 모듈 경계를 그대로 옮기는 것이 옳았다. 그러나 이관이 끝나면 api-java가 정본이 되고 이 형태를 물려받는다 — 엔드포인트 하나를 고치려 400~640줄짜리 컨트롤러를 읽어야 하고, 규칙 하나를 시험하려 스프링 컨텍스트와 Postgres 컨테이너를 띄워야 하며, `auth`를 여덟 도메인이·`operation`을 다섯 도메인이 통째로 의존해 한 도메인을 이해하려면 다른 도메인까지 따라 읽어야 한다. **그때 서둘렀던 이유는 계약 하네스가 아직 살아 있어서였다** — 옛 FastAPI 트리가 사라진 뒤에는 "행동이 그대로인가"를 기계적으로 확인할 수단이 없기 때문이다. 재편은 그 창 안에서 끝났고(13단계), 하네스는 `SOMA-403` 4단계에 폐기됐다.
**트레이드오프**: 계약이 매핑을 두 번 통과한다(행 → Domain Model → DTO). 어긋날 지점이 한 곳에서 두 곳으로 늘고, 웹은 FastAPI 스펙으로 타입을 생성하므로 그 어긋남을 컴파일 타임에 잡지 못한다 — 그래서 계약 하네스의 CI 관문화가 재편의 선행 조건이었다. (**둘 다 지나간 조건이다** — 웹 타입은 이제 자바가 낸 `apps/api/spec/openapi.json`에서 생성하고[`apps/web/package.json`의 `generate:v2-schema`], 하네스는 `SOMA-403` 4단계에 폐기됐다.) 서브패키지로 갈리면서 저장소 클래스를 막아주던 package-private 보호가 옅어지고, 구조를 지키는 장치는 ArchUnit 검사만 남는다. 포트가 늘어난 만큼 유지보수 대상인 인터페이스도 늘고, 매핑이 한 단계 늘어 미세하게 느려진다. SOMA-394 운영 컷오버와 기간이 겹치므로, 재편 중 장애가 나면 원인 후보에서 구조 변경을 배제하기 어렵다.
**전개 순서**: 묶음 이사는 둘로 갈렸다 — 배관과 외부 연동(`platform`·`integration`)은 갈래 분해가 끝나는 대로 옮겼고(8단계), **`feature`는 도메인 배치가 끝난 뒤의 마지막 이사였다**(13단계, 완료). 그 전까지 도메인은 제자리(`com.acttub.actingapi.<도메인>`)에서 네 층만 세웠다 — 파일럿 하나 때문에 최상위를 먼저 흔들면 아직 안 옮긴 도메인이 두 형태 사이에 걸치기 때문이다. **층 규칙을 강제하는 ArchUnit 규칙도 파일럿이 머지된 뒤에 들어왔다**(5단계). 그때까지 층은 관례일 뿐이었고, `domain`이 스프링을 import해도 초록이었다.

**최상위는 이제 셋이다** — `feature`(비즈니스 13) · `platform`(배관 8) · `integration`(외부 연동 5). 루트에 남는 것은 스캔 기점 `ActingApiApplication` 하나다. (13단계를 끝냈을 때는 12 · 9 · 5였다 — 그 뒤 `feature/push`가 생겼고, `platform/harness`가 `SOMA-403` 4단계에 사라졌다.)

⚠ **그런데 "Schema Entity는 도메인별로 이사한다"가 끝까지 가지는 않는다.** 공용 `schema` 스물여섯 중 도메인으로 간 것은 `@Entity` 하나(`ReportEntity`)뿐이고, **enum 열아홉은 못 간다.** `PgEnumCatalogVerifier`가 `pg_enum` 카탈로그를 **맵 전체 equals**로 대조하느라 열아홉을 전부 정적으로 참조하는데, 그 검증기가 배관에 있으므로 enum을 도메인 `schema`로 흩으면 배관 → 도메인 간선이 생긴다. 도메인은 반대로 `PgEnumJdbcType`·`AppGeneratedUuidEntity`를 쓰므로 양방향이 되어 순환이고, `schemaEntitiesAreNeverCalled`에도 걸린다. 4단계가 `PracticeStatus`를 공용에 남긴 것이 이 이유였다. → **`platform/schema`는 "배관이 소유한 스키마 + 어느 도메인의 것도 아닌 어휘"다**(PgEnum 배관 4 · `AppGeneratedUuidEntity` · 공유 enum 19 · 도메인을 가로지르는 원장 `ExternalOperationEntity`). 교환 타입을 중립 지대에 두는 아래 ⚠와 같은 논리이며, 다른 점은 그 자리가 코드가 아니라 **스키마 어휘**라는 것뿐이다.

🔎 **이 문단의 근거는 ADR-023에서 사라졌다** — Postgres enum 타입을 걷어내면서 `PgEnumCatalogVerifier`와 `PgEnumJdbcType`이 함께 은퇴해, 열아홉을 배관에 묶어 두던 정적 참조가 없어졌다. 결론(`platform/schema`가 남는다)은 그대로지만 **이유가 "흩으면 순환이라서"가 아니라 "흩을 이유가 아직 없어서"로 바뀌었다.**

⚠ **원장 구현은 그 교환 타입 옆에 못 산다.** `operation`은 13단계에서 `platform/operation`으로 갔다 — 엔드포인트가 없고(아래 ADR-020의 갈림길), `external_operations` 한 테이블이 analyze·memory_update·coach·report를 함께 담는 도메인 횡단 인프라이며, 교환 타입은 6단계에 이미 `ledger`로 올라가 있었다. **그런데 `platform/ledger` 안에 넣으면 순환이다** — 구현이 도메인의 포트를 구현하고(`platform.ledger → coach`) 도메인은 반대로 교환 타입을 쓰므로(`coach → platform.ledger`) 간선이 양방향이 된다. 실제로 합쳐 돌려 순환 여섯을 확인했다. **같은 묶음 안에서도 조각이 갈리는 이유가 이것이고, 그 경계는 순환 검사가 지킨다.**

**갈래를 가르는 것은 묶음 이사보다 먼저다**: 한 패키지 안에 성격이 다른 것이 섞여 있으면 그 패키지를 어느 묶음에 넣을지 자체가 정해지지 않는다. `auth`가 그랬다 — 요청 필터는 배관이고 OIDC 검증은 외부 연동이며 로그인은 비즈니스라, 통째로는 어디에도 못 간다. 그래서 **갈래를 먼저 가르고**(7단계) 묶음 이사는 나중에 한다(8단계). 그 사이 동안 `security`·`oidc`·`ledger`가 **최상위에 임시로 살았고**, 8단계가 각각 `platform/security`·`integration/oidc`·`platform/ledger`로 보냈다 — 접두어를 붙이면 아래 ⚠ 그대로 순환 검사가 조용히 0이 되므로, 접두어와 슬라이스 할당 수정을 같은 커밋에 뒀다. 이 임시 배치는 위 "최상위를 먼저 흔들지 않는다"의 예외가 아니라 그 이유의 연장이다 — 흔들면 안 되는 것은 **도메인의 자리**이고, 갈라져 나온 배관은 애초에 도메인이 아니다.

**도메인 목록에 있다고 도메인인 것은 아니다**: 갈래를 가를 필요조차 없는 경우가 있다 — 패키지 안이 통째로 한 성격이면 그대로 묶음에 넣는다. `observation`이 그랬다(11단계). 티켓의 `feature` 목록에 올라 있었지만 열두 파일 전부가 Gemini로 영상을 관찰하는 어댑터였고, 엔드포인트도 저장소도 Schema Entity도 없었다 — 네 층을 세우려면 `domain`과 `schema`에 넣을 것을 지어내야 하는 형태다. 그래서 `integration/observation`으로 통째로 옮겼다. **포트와 교환 타입이 외부 연동 쪽에 사는 것은 이미 이 레포의 관례다** — `integration/storage/ObjectStorage`·`integration/llm/TextGenerator`가 그렇고, 간선은 소비자(`analysis`) → `integration` 한 방향이라 7단계처럼 방향을 뒤집을 이유도 없다. 이름을 `gemini`가 아니라 `observation`으로 둔 것도 관례를 따른 것이다(`llm`·`storage`·`media`·`oidc` 어느 것도 벤더 이름이 아니다). **판별 기준은 "네 층에 넣을 것이 실재하는가"이고, 그것이 안 서면 그 패키지는 도메인이 아니다.**

**⚠ 포트를 요구하는 쪽이 배관일 수도 있다**: "쓰는 쪽이 선언한다"의 쓰는 쪽은 feature만이 아니다. 요청 필터·동의 게이트는 배관이면서 사용자를 조회해야 하는데, 그렇다고 배관이 `auth`를 import하면 배관 → feature 간선이 생긴다. **방향을 뒤집어 배관이 포트를 선언하고 feature가 그것을 구현한다** — SOMA-397 7단계에서 `security`가 `AccessTokenVerifier`·`AuthenticatedUsers`를 선언하고 `auth`의 `JwtService`·`AuthStore`가 직접 구현했다(위임 어댑터 없이). 교환 타입 `AuthenticatedUser`도 같은 이유로 `security`에 산다 — 이것이 `auth`에 있으면 요청 주체를 받는 것만으로 여덟 도메인이 전부 `auth`를 import하게 되어, 포트를 어디에 선언하든 간선이 남는다.
**⚠ 포트가 제공자의 타입을 주고받으면 끊기지 않는다**: 포트를 쓰는 쪽에 선언해도, 그 시그니처에 제공자 패키지의 타입(교환 record·예외)이 들어가면 **소비자 → 제공자 간선이 그대로 남는다.** 그러면 제공자가 그 포트를 구현하는 순간 순환이 되어, 구현을 소비자 쪽에 두는 수밖에 없어진다 — 위 결정("구현은 제공하는 쪽에")이 지켜지지 않는 형태다. **교환 타입은 어느 도메인의 것도 아닌 자리에 둔다.** SOMA-397 6단계에서 `SyncOperationBegin`·`SyncOperationClaim`·`LeaseOwnershipException`을 `operation`에서 `ledger`(배관, 8단계에 `platform/ledger`로 간다)로 올려 이 매듭을 풀었고, 그 결과 위임만 하던 어댑터 셋이 사라지고 `SyncOperationService`가 소비자 포트를 직접 구현한다. **포트를 새로 만들 때 시그니처에 제공자 패키지 이름이 보이면 아직 안 끊긴 것이다.**

**⚠ 도메인이 네 층을 다 갖지는 않는다**: "각 도메인 안을 네 층으로"는 층에 넣을 것이 실재할 때의 이야기다. `memory`에는 Schema Entity가 없고(11단계), `admissions`·`admin`은 `domain`과 `schema` 둘 다 없이 선다(12단계). 지어낸 층은 규칙을 담지 않고, 네 층을 전제로 쓴 검사는 층이 없는 도메인에서 두 방향으로 조용히 무너진다. → **ADR-020**.

**⚠ 한 포트는 한 쪽만 구현한다 — 소유가 갈리면 포트도 갈린다**: 배관이 선언한 포트라도 그 안의 질문들이 서로 다른 도메인의 데이터를 물으면 한 구현으로 답할 수 없다. `security/AuthenticatedUsers`가 그랬다 — 사용자 조회는 `auth`의 것인데 동의 여부는 `consent`의 것이라, `auth`가 동의 테이블을 직접 읽는 형태로 버티고 있었다(12단계에서 `PendingConsentGate`로 갈랐다). **포트를 나누는 축은 부르는 쪽의 편의가 아니라 답하는 쪽의 소유다.**

**⚠ 포트가 실패를 알리는 방법은 이 결정이 정하지 않는다**: 포트를 어디에 선언하고 무엇을 주고받는지는 여기서 정했지만, 없음·충돌을 `null`로 알릴지 예외로 알릴지는 포트마다 갈린다 — `practice`(4단계)와 `community`(10단계)가 서로 다르게 갔다. → **ADR-018**.

**⚠ 두 도메인이 서로를 소비하면 이 결정이 그대로 서지 않는다**: "쓰는 쪽이 포트를 선언한다"를 양쪽에 적용하면 구현하는 쪽이 인터페이스를 import하므로 간선이 양방향이 되어 순환이다. `coach`↔`report`가 그랬다(9단계). 그때는 한쪽만 포트로 뒤집어 간선을 한 방향으로 정렬하고, 반대쪽은 상대의 `app` 층만 참조한다. → **ADR-019**.

**⚠ 묶음 이사 때 함께 고쳐야 하는 것**: `PackageCycleTest`의 `slices().matching("com.acttub.actingapi.(*)..")`는 **첫 하위 패키지 하나로만** 슬라이스를 가른다. 접두어가 붙으면 그 묶음 아래 조각들이 슬라이스 하나로 뭉쳐(도메인 열셋을 `feature` 아래 넣으면 그 열셋이 한 슬라이스가 된다), 조각 사이의 순환이 슬라이스 내부가 되어 검사에서 사라진다 — 테스트는 그대로 초록이다. ADR-016이 순환 금지를 유일한 방어선으로 삼았으므로, 함께 고치지 않으면 그 방어선이 조용히 0이 된다. → **8단계에서 매처를 버리고 `SliceAssignment`로 묶음 접두어를 한 겹 벗겨** 재편 전과 같은 단위(`platform.web`·`analysis`)로 가른다. 묶음이 늘면 목록에 이름을 더하는 것이 전부다.

🔥 **그 목록을 빠뜨리는 것이 진짜 실패 모드이고, 순환 검사는 그것을 못 잡는다.** 뭉친 묶음이 도메인과 **양방향** 간선을 가질 때만 사이클이 되므로, `integration`처럼 앱 안으로 나가는 간선이 없는 묶음은 뭉쳐도 **조용히 초록**이다(실측했다 — 8단계 리뷰의 두 축이 독립적으로 짚었다). 그래서 순환에 기대지 않는 검사를 따로 뒀다: **층(`domain`·`app`·`adapter`·`schema`)이 아닌 하위 패키지를 거느린 최상위가 목록에 없으면 실패한다.** 재편이 끝난 도메인은 층만 거느려 통과하고, 묶음은 그렇지 않아 걸린다. 🔥 **13단계 `feature` 이사가 정확히 이 자리에 걸렸다 — 실측했다.** 목록을 안 고친 채 돌리면 그때의 도메인 열둘이 한 슬라이스로 뭉치는데도 순환 검사는 **초록**이었고(`platform/config`·`platform/harness`가 도메인으로 *들어가는* 간선만 가져 사이클이 못 된다 — `harness`는 그 뒤 사라졌다), 빨간불을 낸 것은 이 검사 하나뿐이었다.

🔎 **묶음 자체를 슬라이스로 삼는 안은 버렸다.** 그렇게 하면 `platform ↔ analysis` 같은 순환이 셋 잡히는데, 전부 `platform/harness`가 도메인을 참조하는 데서 온다 — 하네스 대체 구현은 진짜 구현을 대신하므로 도메인을 알아야 하고(위 "대체 구현은 진짜 구현 옆에"), 도메인은 반대로 `platform/ledger`의 교환 타입을 쓴다. 둘 다 의도된 간선이다. **그 예시는 `SOMA-403` 4단계에 사라졌지만 판단은 그대로 선다** — 같은 형태를 `platform/security`·`platform/operation`이 갖는다(`PackageCycleTest` 주석에 적어 뒀다). **묶음 사이의 간선은 금지 대상이 아니다** — 금지 대상은 feature끼리의 직접 import이고, 그 규칙은 한정이 풀린 13단계에 `PackageLayerTest`의 `featuresSeeOnlyEachOthersAppLayer`로 들어왔다(상대의 `app`만 허용 — 아래 ADR-019).

🔎 **"한정 해제"는 규칙을 넓히는 일이 아니라 목록에서 빠진 것을 잡는 일이었다.** 층 표를 도는 검사는 표에 **없는** 도메인을 영원히 못 본다 — 재편 기간에는 그것이 의도된 대가였지만(안 옮긴 도메인이 빨간불을 내지 않게 하려는 한정), 끝난 뒤에는 방어선의 구멍이다. `everyFeatureIsInTheTable`이 `feature` 아래 실물과 표를 대조해 그 구멍을 막는다. 위 `everyBundleIsInTheList`와 같은 부류다.

### ADR-018: 포트가 실패를 알리는 방법은 포트 단위로 정한다
**결정**: 포트가 없음·충돌을 `null`·`boolean`으로 알릴지 예외로 알릴지는 **포트 하나를 단위로** 정하고, 그 포트에서 **갈래가 가장 많은 연산**이 방식을 결정한다. 예외로 가는 포트는 예외 타입을 쓰는 쪽의 `app`에 선언하고 제공하는 어댑터가 던진다. 대상이 없다는 사실은 한 예외로 묶어 **부르는 자리가 뜻을 정하게** 하되, **한 연산이 그 예외를 두 경로로 던져서는 안 된다** — 불변식이 깨진 자리는 "없음"이 아니므로 다른 예외(`IllegalStateException`)로 낸다.
**이유**: `practice`의 포트는 실패 모드가 하나여서 `null`로 충분했다(SOMA-397 4단계). `community`의 `updatePost`는 "없다"와 "내 것이 아니다" 둘이 갈리고, 그 판정이 **같은 트랜잭션·같은 잠금 안에서** 일어나야 한다 — 조회와 쓰기를 서비스가 나눠 부르는 형태로 가르면 그 경계가 깨지고, 행을 먼저 읽어 와 자바에서 비교하면 남의 글이 존재한다는 사실이 응답 시간에 샌다. 단위를 연산이 아니라 포트로 잡는 이유는, 한 포트 안에서 방식이 둘이면 부르는 쪽이 연산마다 어느 쪽인지 기억해야 하기 때문이다(그래서 `getPost`처럼 갈래가 하나인 연산도 같은 포트에 있으면 예외를 쓴다). 예외를 `app`에 두는 것은 ADR-017의 층 규칙과 어긋나지 않는다 — 방향이 `adapter → app`이고, 제공자와 소비자가 같은 도메인이라 "포트가 제공자의 타입을 주고받으면 끊기지 않는다"에도 걸리지 않는다.
**트레이드오프**: 도메인마다 포트 호출 관례가 달라져, 한 도메인을 읽고 다른 도메인을 짐작할 수 없다 — SOMA-397이 "파일럿에서 나온 형태가 나머지의 본이 된다"고 한 것을 이 항목에서만 완화하는 셈이다. 예외로 가는 쪽은 서비스 메서드 상당수가 `try/catch` 변환기가 되는 대가를 치른다. 🔥 **그리고 예외를 합치는 순간 "한 연산이 두 경로로 던지는" 자리가 생기는데, 계약 하네스는 이것을 못 잡는다** — 10단계에서 `createPost`·`updateComment`가 정확히 그랬고(500이던 응답이 404로 바뀌어 멀쩡한 분류를 탓하는 형태였다), 하네스 6회 diff 0을 통과한 것을 `/code-review` 두 축이 독립적으로 잡았다. 도달하려면 파손된 데이터가 필요해 시나리오로는 닿지 않는다.

### ADR-019: 서로를 소비하는 두 도메인은 간선을 한 방향으로 정렬한다
**결정**: 두 feature가 **서로의 것을 필요로 할 때는** ADR-017의 "쓰는 쪽이 포트를 선언한다"를 양쪽에 적용하지 않는다. 한쪽 요구만 포트로 뒤집어 간선을 **한 방향**으로 세우고, 반대쪽은 상대의 **`app` 층을 직접 참조**한다. 참조가 허용되는 것은 `app`뿐이며 `adapter`·`domain`·`schema`는 여전히 금지다 — 13단계에서 "feature끼리 직접 import 금지"를 ArchUnit으로 걸 때 이 형태로 표현한다. 상대 도메인이 알아야 하는 타입(교환 record, 공개 스키마)은 그래서 `app`에 산다.
**이유**: `coach`는 성적표를 만들어야 하고 `report`는 코치 세션에서 원본을 읽어야 한다 — 둘 다 실재하는 요구다(SOMA-397 9단계). ADR-017을 문자 그대로 양쪽에 적용하면 `coach/app`이 성적표 생성 포트를 선언해 `report`가 구현하고, `report/app`이 소스 조회 포트를 선언해 `coach`가 구현한다. **구현하는 쪽이 인터페이스를 import하므로 간선이 양방향이 되어 `PackageCycleTest`가 빨간불이다.** 교환 타입을 중립 지대로 올리는 6단계의 해법은 여기서 듣지 않는다 — 그때는 소비 방향이 한쪽뿐이었고 원장은 배관이라 올릴 자리가 있었지만, 성적표 생성은 배관이 아니다. 두 도메인을 합치는 안도 검토했으나 티켓의 feature 목록과 엔드포인트 경계를 바꾸는 결정이라 택하지 않았다. 남은 길은 한 방향으로 정렬하는 것이고, 방향은 **`coach → report`**다(성적표가 코치를 모르는 편이 자연스럽다 — 성적표는 코칭이 끝난 뒤의 산출물이고, `/v2/reports`가 필요로 하는 코치 데이터는 `ReportSourceProvider` 포트로 뒤집어 코치 어댑터가 구현한다).
**트레이드오프**: "한 도메인만 읽으면 된다"가 절반만 성립한다 — `report`는 혼자 읽히지만 `coach`를 읽으려면 `report/app`을 함께 봐야 한다. 그리고 `app` 참조를 허용하는 순간 그 층이 사실상 공개 API가 되어, 도메인 내부 사정으로 시그니처를 바꿀 자유가 준다. 완화하는 장치는 **참조 폭을 세는 것** 하나다(9단계 종료 시점 아홉 심볼). 늘어나면 그것이 곧 두 도메인을 합쳐야 한다는 신호다.

### ADR-020: 도메인이 갖는 층은 넣을 것이 실재하는 만큼이다
**결정**: ADR-017의 "각 비즈니스 도메인 안을 네 층으로 세운다"를 **모든 도메인에 문자 그대로 적용하지 않는다.** 어떤 층을 세울지는 그 층에 넣을 것이 실재하느냐로 정하고, 없으면 만들지 않는다 — 지어낸 층은 규칙을 담지 않으므로 읽는 사람을 속인다. 그 대신 **어느 도메인이 어느 층을 갖는지를 목록으로 못박고**(`PackageLayerTest`의 `FEATURE_LAYERS` — 13단계 전 이름은 `MIGRATED_FEATURES`였다), 층별 규칙은 그 목록에서 대상을 끌어온다. 목록과 실물이 어긋나면 `everyRuleActuallyHasSomethingToCheck`가 양방향으로 잡고, 목록에서 아예 빠진 도메인은 `everyFeatureIsInTheTable`이, 층이 아닌 하위 패키지는 `everyFeatureSubpackageIsALayer`가 잡는다(13단계).
**이유**: 네 층을 전제로 쓴 검사는 층이 없는 도메인에서 **두 방향으로 조용히 무너진다.** `that()`으로 대상을 좁힌 규칙(`domainKnowsNoFramework`)은 ArchUnit이 대상 0을 실패로 쳐서 빨간불이 나고, 그렇지 않은 규칙(`schemaEntitiesAreNeverCalled`)은 반대로 대상 0으로 **통과**한다. 어느 쪽도 원하는 답이 아니다. 층이 없는 도메인은 예외가 아니라 흔하다 — `memory`는 Schema Entity가 애초에 없었고(11단계, → SOMA-398), 12단계에서는 `admissions`와 `admin`이 `domain`과 `schema` 둘 다 없이 섰다. 요강은 바깥에서 통째로 들어오는 문서라 그것에 걸리는 행위 규칙이 없고, 운영 지표는 도메인을 가로질러 세는 일이라 자기 테이블이 없다. 둘 다 **집계하거나 읽어 온 것이 곧 응답**이라 형태가 `app`에 산다(`report/app/PublicReport`와 같은 자리) — 중간 표현을 따로 두면 필드 수십 개를 두 벌로 관리하게 되고, 그 어긋남을 웹은 컴파일 타임에 잡지 못한다.
**ADR-017의 판별 기준("네 층에 넣을 것이 실재하는가")과의 관계**: 그 기준은 11단계에서 **"그 패키지는 도메인이 아니다"**의 근거로 쓰였다(`observation` → `integration`). 이 결정은 같은 기준의 **다른 결론**이다 — 엔드포인트가 실재하면 도메인이고, 그때는 묶음으로 보내는 것이 아니라 **가진 층만으로 세운다.** 갈림길은 엔드포인트다.
**트레이드오프**: "도메인 폴더를 열면 네 하위 폴더가 있다"는 예측 가능성이 깨진다 — 열어 봐야 몇 층인지 안다. 그리고 층 목록이 손으로 관리하는 표라, 검사가 그 표를 믿는 만큼만 정확하다(표가 실물과 어긋나는 것은 검사가 잡지만, 표를 **고칠지 말지**는 사람이 정한다). 애초에 규칙이 빈약한 도메인에 나중에 규칙이 생겨도 층이 늘지 않을 수 있고, 그때는 `app`이 계속 두꺼워진다.

### ADR-021: Scene Context는 선택 입력이고, 건너뛴 것은 채우지 않는다
**결정**: 연습을 시작할 때 **Scene Context**(상황·인물·목표)는 적지 않아도 된다. 화면이 그 사실을 말하고, 세 칸이 모두 빈 상태에서만 건너뛰기 버튼이 나타난다. 건너뛴 값은 **빈 문자열**로 저장하며 "없음"을 뜻하는 별도의 값(`null`)을 두지 않는다. **한 번 건너뛴 Scene Context는 그 세션에서 다시 채우지 않는다** — 수정 경로를 만들지 않고 코치도 되묻지 않는다. 값이 빈 세션의 프롬프트는 그 칸을 만들지 않고 "배우가 적지 않았다"를 명시하며, 관찰과 코치가 같은 규칙을 쓴다. **막힘은 건너뛸 수 없다** — 대신 세 화면을 한 화면으로 줄이고 하위 갈래·상세를 선택으로 만든다.
**이유**: 적을 것이 없어서가 아니라 **마찰 때문에 이탈한다**(즉흥·자유 연기처럼 "해당 없는 연습"은 근거가 아니다). 그런데 웹은 이미 선택 입력이었다 — 진행 조건이 `ready: video !== null` 하나뿐이라 세 칸이 비어도 다음으로 간다. 아무도 그 사실을 몰랐던 이유는 화면에 안내가 한 글자도 없었기 때문이고, 대신 `fillBlankScene`이 빈 칸을 `"."`로 채워 보내고 있었다(서버가 `minLength: 1`을 강제해 422가 났고, 그 주석에 실사용자 4명이 여기서 이탈한 기록이 남아 있다). 그 점 하나가 헤더·목록·아바타·장면 패널·프롬프트로 새고 있었다. 즉 **만들 기능이 아니라 드러내야 할 기능이었고, 드러내기 전에 닫아야 할 누출이었다.**
`null`이 아니라 빈 문자열인 이유는 "안 적었다"와 "빈 칸"을 갈라서 할 일이 지금 없기 때문이다 — `null`로 가면 마이그레이션·NPE 가드 다섯·응답 스키마·동결 스냅샷 일곱이 따라오는데 그 대가로 얻는 구분을 쓰는 곳이 없다. 반대로 빈 문자열은 웹의 표시 폴백 일곱 군데가 이미 falsy로 처리하므로 `.`을 없애는 것만으로 전부 되살아난다.
다시 채우지 않는 이유는 **영상을 세션 시작 시 한 번만 분석하기 때문이다**(ADR-AI-003). 나중에 채운 Scene Context는 관찰에 반영될 수 없어서, 채울 수 있게 하면 "적었는데 왜 분석은 그대로냐"를 화면에서 설명해야 한다. 수정 엔드포인트가 애초에 없다는 사실이 이 결정을 싸게 만든다.
프롬프트에서 칸을 **빼는** 이유는 빈 제목만 남기면 모델이 그 자리를 지어내기 때문이다 — `CoachPrompt`의 `priorContextBlock`이 같은 이유로 이미 그렇게 하고 있고, 시스템 프롬프트가 "가능하면 이 정보가 제공된다"고 선언하고 있어 부재를 말해 주지 않으면 모델이 채운다.
막힘을 건너뛸 수 없는 이유는 **값이 동작을 가르기 때문이다.** `blockage_kind`가 `"분석"`일 때만 전사가 돌고, `"표현"`이면 코치 v3 프롬프트가 뜨고, 리포트 템플릿도 여기서 갈린다. 중립값 `"그 외"`를 자동으로 넣으면 전사가 **조용히** 꺼진다. 동기가 마찰이지 "고를 게 없다"가 아니므로, 답은 값을 없애는 것이 아니라 고르는 횟수를 줄이는 것이다(3탭 → 1탭).
**트레이드오프**: 건너뛴 세션의 코칭 품질이 낮다 — ADR-004는 "관찰과 장면 맥락을 바탕으로 질문을 이어간다"고 했는데 그 절반이 없는 세션이 생기고, 보완 장치인 인터뷰마저 첫 발화가 막힘 대분류 한 단어로 시작한다. **되돌릴 수 없다** — Scene Context 없는 세션이 쌓인 뒤에 "역시 필수로 하자"로 돌아가도 과거 세션은 비어 있다. 하위 갈래를 안 고른 사람과 `"그 외"`를 고른 사람이 데이터에서 구분되지 않는다(프롬프트에 양쪽 모두에게 참인 "특정하지 않음"을 적는 것이 완화책이지만, "이 갈래들 중 어디도 아니다"라는 명시적 선택의 정보는 잃는다). 웹과 모바일의 정책이 갈린다 — 서버가 `minLength`를 떼도 모바일은 자기 검증 때문에 안 깨지므로 배포는 안전하지만, 두 앱을 같은 제품으로 설명하기 어려워진다(별도 티켓). 기존 `"."` 세션은 그대로 두므로 **목록에서는 `.`, 이어하기에서는 빈 값**으로 보이는 어긋남이 굳는다(`continueFromCurrent`에만 방어가 있다).
**되돌릴 근거를 남긴다**: 건너뛰기 클릭을 별도 이벤트로, 그리고 세션 제출 이벤트에 건너뜀 여부를 속성으로 기록한다. 이탈이 줄었는지, 건너뛴 사람의 완주율이 어떤지를 보지 않으면 이 트레이드오프를 재검토할 수 없다.

### ADR-022: 에이전트는 Jira 이슈를 만들지 않고, 자기 계획은 저장소 밖 파일 하나에 둔다
**결정**: **Jira 이슈를 만들고 본문을 쓰는 것은 사람이다.** 에이전트는 초안을 넘길 뿐 직접 만들지 않는다. 같은 이유로 Atlassian MCP도 등록하지 않는다 — 붙여 두면 다시 만들게 된다. Jira는 이슈 정본으로 남고 브랜치·PR의 키 규칙도 그대로다.
**이슈 본문은 세 절뿐이다** — 배경 / 원하는 상태 / 완료 조건(체크리스트). 근거·조사 기록·설계 서술은 본문에 쓰지 않는다(필요하면 참고 경로 한 줄까지).
**에이전트가 그 이슈를 굴리는 계획은 `.scratch/<이슈키>.md` 파일 하나**에 둔다. 추적하지 않으므로 저장소에는 남지 않고, 길이나 형식에 제약을 두지 않는다 — 에이전트가 자기 세션을 잇기 위해 쓰는 글이다. 끝나도 옮기거나 지우지 않는다.
끝난 뒤 **살아남아야 할 것만 자리를 옮긴다** — 앞으로 지킬 규칙이 된 것은 저장소 문서로(되돌리기 어려운 결정은 `docs/ADR.md`, 에이전트가 지킬 규칙은 `CLAUDE.md`, **제품 도메인** 용어는 `CONTEXT.md`), 새로 발견한 버그와 미처리 이월은 Jira로(사람이 이슈를 만든다).
**이유**: 에이전트가 Jira에 직접 쓰던 동안 **이슈를 과하게 많이 만들고 본문을 너무 크게 썼다.** 2026-08-18 아키텍처 리뷰 한 번으로 여덟(`SOMA-406`~`413`)을 만들었는데, 첫 하나(`c35e23b`)를 하고 나니 셋(`407`·`408`·`410`)이 불필요해져 닫히고 대신 없던 하나(`414`)가 생겼다 — **미리 만든 계획의 절반이 틀렸다.** 2026-08-24에 사용자가 Atlassian MCP 등록을 지운 것이 그 대가였고, 이 결정은 그 조치를 규칙으로 세우는 것이다.
그 비용은 두 가지다. **보드가 지저분해 무엇부터 할지 고르기 어렵고**, **본문이 길어 읽히지 않는다.** 그래서 답도 두 갈래다 — 만드는 주체를 사람으로 옮겨 개수를 막고, 본문 구조를 세 절로 고정해 길이를 막는다.
에이전트의 계획을 따로 두는 이유는 **읽는 사람이 다르기 때문**이다. 이슈는 사람이 보드에서 읽고, 계획은 다음 세션의 에이전트가 읽는다. 둘을 한곳에 두면 사람이 읽을 것에 에이전트가 쓴 분량이 섞여 방금 막은 "안 읽힌다"가 그대로 돌아온다. 계획에 길이 제약을 두지 않는 것도 같은 이유다 — 사람이 읽지 않는 글에 길이를 재는 것은 규칙만 늘린다.
**파일 하나인 이유**는 앞선 안이 실패했기 때문이다. 처음에는 `.scratch/<이슈키>/`에 `00-context.md`와 단계 파일들을 두고 끝나면 `.scratch/done/`으로 옮기게 했는데, 규칙을 세운 그 세션 안에서 세 곳이 지켜지지 않았다 — 옮길 대상이 이미 지워져 있었고, 이월은 Jira로 안 갔으며, 이 결정을 담은 브랜치가 키 없이 서 있었다(뒤에 `SOMA-443`으로 합쳤다). **지켜지지 않는 절차는 규칙이 아니라 부채다.**
**트레이드오프**: **계획이 저장소에 없다.** `CLAUDE.md`가 경로를 가리키므로 *어디를 열지*는 알 수 있지만 *무엇이 진행 중인지*는 그 파일을 열어야 안다. **리뷰를 받지 못한다** — 계획이 틀려도 PR 리뷰가 잡지 못한다. **한 머신에만 있다** — 팀도, 같은 저장소의 다른 체크아웃도 보지 못한다. **그리고 실제로 사라진다** — 이 결정을 만드는 동안에만 저장소 밖 파일을 두 번 잃었다(커밋 전 재작성 하나, 앞선 티켓 디렉토리의 백업 하나). 끝난 계획을 옮기지 않으므로 `.scratch/`에는 낡은 파일이 쌓인다 — 치우는 규칙을 두지 않은 것은 그 규칙이 안 지켜지는 것을 이미 봤기 때문이고, 대신 파일 하나씩이라 쌓여도 읽는 데 방해가 적다. **이슈 본문을 세 절로 묶는 대가**도 있다 — 왜 그렇게 정했는지가 이슈에 안 남아 나중에 이유를 물으면 답할 자리가 없다. 그것이 되돌리기 어려운 결정이면 ADR이 받고, 아니면 잃는다.
⚠ **이 결정이 아직 갚지 않은 것** — 앞선 `SOMA-443`이 남긴 미처리 이월 둘 중 하나(온보딩이 없는 버튼 이름을 안내하던 것)는 같은 브랜치에서 고쳤지만, **앱이 ADR-021을 두 자리에서 어기는 것**은 위 "새로 발견한 버그는 Jira로"를 아직 못 지켰다. 건너뛴 막힘 선택이 `'그 외'`로 전송되어 `SummaryAnalyzer`가 전사를 건너뛰는데, 고치려면 서버 분기 셋과 `blockage_kind`의 `@NotNull` 계약이 함께 걸려 설계 결정이 먼저다. 그때까지 그 하나의 기록처는 에이전트 메모리이고 저장소에는 없다.
**되돌릴 근거를 남긴다**: 사람이 만드는 것이 병목이 되어 이슈가 아예 안 만들어지거나, 저장소 밖 계획을 잃어 같은 일을 두 번 하게 되면 되돌린다. MCP 재등록 절차는 `docs/agents/issue-tracker.md`에 남겨 두었다.

## 스키마 (2026-08-31)

### ADR-023: 값 목록은 Postgres enum이 아니라 text + CHECK로 표현한다
**결정**: 네이티브 Postgres enum 19종을 전부 `text` 컬럼 + `CHECK (col = ANY (ARRAY[…]))`로 바꾼다(`V4__enum_columns_to_text.sql`). 값 무결성은 애플리케이션으로 옮기지 않고 **DB에 남긴다** — 그릇만 바꾸고 규칙은 그대로다. 제약 이름은 이 저장소의 기존 규칙 `ck_<table>_<col>`을 따른다. **정렬 순서에 뜻이 실린 곳은 `ORDER BY CASE`로 옛 순서를 못박는다**(동의 문서 목록·배우 기억 항목 두 곳). Java enum 19개와 `AttributeConverter`는 **남긴다** — 모르는 값을 읽을 때 던지는 예외가 CHECK 다음의 두 번째 그물이다. 값을 실제로 걷어낸 것은 셋이다: `users.status`의 `suspended`, `practice_sessions.status`의 `created`(둘 다 만드는 경로가 없고 운영·dev 0건 실측), 그리고 `users.signup_*` 9컬럼과 그 유일한 소비처였던 `/v2/admin/stats`.
**이유**: **Postgres는 enum 값 삭제를 지원하지 않는다**(`dropping an enum value is not implemented`). 계정 정지 기능이 코드 어디에도 없다는 것을 확인하고 `user_status_t`의 `suspended` 하나를 빼려다 여기서 막혔다 — 죽은 값 하나를 걷어내려면 타입을 새로 만들고 컬럼을 갈아끼우는 수술이 필요하고, 그 수술은 19종 전체를 한 번에 하는 것과 비용이 크게 다르지 않다. 더 근본적인 이유는 **값 목록이 바뀌는 것이 이 도메인에서는 정상**이라는 것이다. 코치 마감 사유·연습 상태·기억 칸은 제품이 답을 찾아가며 늘고 준다. 값 추가만 싸고 삭제는 불가능한 그릇은 그 움직임과 맞지 않는다. 그리고 **이 저장소는 이미 text + CHECK를 쓰고 있었다** — `ck_practice_reports_report_type`·`ck_coaching_handoffs_branch_kind`·`ck_practice_sessions_blockage_branch`가 그것이고, enum은 파이썬 세대(SQLAlchemy `sa.Enum`)의 잔재였다. 이 전환은 새 패턴을 들이는 것이 아니라 **둘로 갈려 있던 것을 하나로 모으는** 쪽이다. PR을 쪼개지 않은 것은 배포 구조 때문이다 — 백엔드가 인스턴스 한 대이고 배포가 `systemctl restart`라 옛 jar와 새 jar가 공존하지 않는다. "배포 중간 상태에서 옛 코드가 새 스키마를 친다"는 사고가 이 구조에서는 일어나지 않는다.
**트레이드오프**: 🔥 **성공한 배포는 되돌릴 수 없다.** 옛 jar의 SQL은 `'running'::operation_status_t` 같은 캐스팅을 갖고 있어 컬럼이 text가 된 순간 깨진다 — enum 타입만 남겨 둬도 `ddl-auto: validate`만 통과할 뿐 쿼리는 깨지므로 `DROP TYPE`을 빼도 얻는 것이 없다. 복구는 앞으로 굴리는 것뿐이고, 그 보험으로 역마이그레이션 초안을 저장소 밖에 둔다. (마이그레이션이 **실패**한 경우는 오히려 안전하다 — 한 파일 = 한 트랜잭션이라 스키마가 온전하다.) **정렬이 조용히 바뀐다** — enum은 정의순, text는 사전순이고 19종 중 18종이 갈린다. 예외도 오류도 없이 순서만 뒤집히므로 `CASE`를 빠뜨린 자리는 아무도 모른다. **기동할 때 Java enum과 `pg_enum` 카탈로그를 통째로 대조하던 그물(`PgEnumCatalogVerifier`)을 잃는다** — 대조할 카탈로그가 없어졌다. 이제 Java 쪽 목록과 DB 쪽 CHECK가 어긋나도 기동은 통과하고, 그 값을 실제로 읽을 때 컨버터가 던진다. **마이그레이션이 기동의 일부라 다운타임이 기동 시간만큼 있다** — 20컬럼 재작성 + CHECK 22개가 배포 스크립트의 90초 상한 안에 들어야 하고, 넘으면 성공한 배포가 빨간불이 된다(전 테이블 수백 행 이하라 데이터량이 아니라 기동 자체가 위험 요인이다). **`signup_*`은 소급 복구가 안 된다** — 지우기 전 운영 값을 CSV로 아카이브하는 것이 그 대가의 유일한 완화책이고, 나중에 유입 분석 화면을 만들어도 과거 가입자의 출처는 GA4(세션 단위)에만 남는다.
**되돌릴 근거를 남긴다**: CHECK가 실제로 값을 막는 일이 잦아지면(운영에서 제약 위반이 관측되면) 그것은 값 목록이 코드보다 빨리 움직인다는 뜻이고, 그때는 무결성을 DB에 두는 이 결정 자체를 다시 본다. 반대로 CHECK를 고치는 마이그레이션이 늘어나는 것은 되돌릴 근거가 아니다 — **그 잦은 변경이 애초에 enum을 버린 이유다.**
