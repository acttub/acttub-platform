# Architecture Decision Records

## 철학
acttub은 빠르게 검증 가능한 MVP를 만들되, 제품 정체성과 안전 가드레일은 초기에 강하게 고정한다.

핵심 가치관:

- 질문 기반 연습 파트너가 제품 정체성이다.
- AI는 배우를 평가하지 않는다. 배우가 스스로 생각을 채우게 돕는다.
- 결과 카드보다 질문 대화가 핵심 화면이다.
- 점수, 등급, 판정, 4축 평가, 강점/약점 카드는 사용자 표면에서 제거한다.
- 영상 분석은 한 번 수행하고, 이후 대화는 저장된 관찰과 대화 이력에 근거한다.
- DB가 세션 상태와 대화 상태의 정본이다.
- 초기에는 작동하는 HTTP 계약과 검증 루프를 우선한다.
- 외부 의존성, 파인튜닝, 복잡한 인프라는 실제 필요가 생긴 뒤 도입한다.
- 향후 Spring Boot, React Native, 공유 패키지로 확장할 수 있게 경계를 유지한다.

---

### ADR-001: pnpm 모노레포를 프로젝트 루트 구조로 사용한다
**결정**: `acttub-platform`은 pnpm workspace 기반 모노레포로 유지한다. 활성 앱은 `apps/web`이며, `apps/api`, `apps/mobile`, `packages/*`는 필요 시 확장한다.

**이유**: 현재는 웹 MVP가 개발 중심이지만, 장기적으로 Spring Boot 백엔드와 React Native 앱이 들어올 가능성이 높다. 루트에 문서, workspace script, lockfile을 두면 제품 요구사항과 API 계약을 앱별 구현보다 상위에서 관리할 수 있다.

**트레이드오프**: 초기에는 단일 Next.js 앱보다 디렉토리 구조가 조금 무겁다. 대신 앱/패키지 경계가 초기에 명확해지고, API/DTO/문서가 특정 앱 하위에 갇히지 않는다.

### ADR-002: 초기 웹 구현은 Next.js App Router로 진행한다
**결정**: 초기 제품 화면은 `apps/web`의 Next.js App Router, TypeScript, Tailwind CSS로 만든다.

**이유**: 현재 저장소에 이미 Next.js 앱이 준비되어 있고, 영상 입력, 분석 대기, 질문 대화, 세션 종료 화면을 빠르게 검증하기에 적합하다. Server Component를 기본으로 두고 상호작용이 필요한 영역만 Client Component로 분리할 수 있다.

**트레이드오프**: 장기 백엔드가 Spring Boot인 상황에서 Next route handler에 비즈니스 로직이 커질 위험이 있다. 이를 막기 위해 UI는 `src/lib/api/*`를 통해 API를 호출하고, route handler는 얇게 유지한다.

### ADR-003: 임시 API는 `/api/v1/*` REST 계약으로 작성한다
**결정**: Spring Boot가 들어오기 전까지 Next.js Route Handler를 임시 API로 사용할 수 있으며, path는 `/api/v1/*` 형태의 versioned REST 계약을 선호한다.

**이유**: 제품 초기에는 프론트엔드와 서버 흐름을 빠르게 검증해야 한다. 하지만 향후 `apps/api`로 이전할 때 프론트엔드 호출부를 크게 바꾸지 않으려면 HTTP path, method, DTO, status code가 안정적이어야 한다.

**트레이드오프**: Next.js 내부 기능에 더 강하게 붙으면 빠를 수 있지만, 백엔드 이전 비용이 커진다. REST 계약을 먼저 고정하면 초기 구현이 약간 더 엄격해진다.

### ADR-004: 질문 기반 UX를 핵심 제품 표면으로 채택한다
**결정**: acttub의 핵심 화면은 결과지나 피드백 카드가 아니라 질문 대화 화면이다. AI는 판단을 확정하지 않고 관찰과 장면 맥락을 바탕으로 질문을 이어간다.

**이유**: 배우에게 표정/동작 같은 결과만 고치라고 하면 심리와 행동이 분리되어 연기가 굳을 수 있다. acttub은 결과를 처방하기보다 결과를 만든 생각, 심리, 상황, 관계, 목표, 서브텍스트를 묻는 도구여야 한다.

**트레이드오프**: 사용자에게 즉시 “결과를 받았다”는 느낌은 약해질 수 있다. 대신 제품의 차별점과 안전성은 질문 대화에서 나온다.

### ADR-005: 4축 평가와 피드백 카드 프레이밍을 폐기한다
**결정**: 사용자 표면에서 점수, 등급, 4축 평가, 피드백 카드, 강점/약점/개선점 카드, audience verdict, aligned/gap_bucket 같은 내부 라벨을 사용하지 않는다.

**이유**: 현재 제품 방향은 평가 서비스가 아니라 질문 기반 연습 파트너다. 평가처럼 보이는 화면은 사용자가 AI를 연습 파트너가 아니라 심판으로 느끼게 만든다.

**트레이드오프**: 기존에 만들었거나 구상한 평가 UI/데이터 구조 일부는 버리거나 내부 도구로만 제한해야 한다. 마케팅 메시지도 “정확한 피드백”보다 “생각을 다시 묻는 연습 파트너” 쪽으로 바뀐다.

### ADR-006: MVP 범위는 질문 대화와 자기 정리까지로 제한한다
**결정**: MVP는 영상/맥락 입력, 1회 분석, 관찰 확인, 5~10개 질문, actor-authored filled-thought sentence 저장까지를 범위로 한다.

**이유**: 먼저 검증해야 할 것은 “점수나 처방 없이도 배우가 질문을 통해 놓친 생각을 자기 말로 발견하는가”다. retake, before/after, 성장 리포트가 들어오면 검증 변수가 늘어난다.

**트레이드오프**: 완성형 코칭 서비스처럼 보이는 기능은 줄어든다. 대신 1차 배우 검증의 failure mode를 더 선명하게 볼 수 있다.

### ADR-007: before/after 비교는 후속 범위로 미룬다
**결정**: 첫 촬영 잠금, 같은 장면 재촬영, 전/후 비교, 변화 지표, 보호자 결제 설득용 결과는 MVP에서 제외한다.

**이유**: 전/후 비교는 장기적으로 유용하지만, 알파에서는 질문형 대화 자체의 안전성과 유용성을 먼저 검증해야 한다.

**트레이드오프**: 사용자에게 개선 결과를 시각적으로 보여주는 힘은 약하다. 대신 MVP 구현 범위와 검증 범위를 작게 유지한다.

### ADR-008: DB를 세션/대화 상태의 정본으로 삼는다
**결정**: 세션 상태, 영상 분석 상태, 관찰 확인 상태, turn 로그, 종료 자기 정리는 DB에 저장하고 DB를 정본으로 삼는다.

**이유**: 질문 대화는 여러 turn에 걸친 상태ful 경험이다. 새로고침, 이어하기, 분석 대기, 관찰 거절 반영, 검증 로그를 안전하게 다루려면 서버 메모리나 클라이언트 state만으로는 부족하다.

**트레이드오프**: 초기 mock 구현보다 데이터 모델을 더 신중히 설계해야 한다. 하지만 이 결정은 AI 질문 품질과 안전 가드레일을 검증하기 위한 최소 기반이다.

### ADR-009: 영상은 세션 시작 시 한 번 분석한다
**결정**: 영상은 세션 시작 시 한 번 분석하고 관찰 결과를 저장한다. 이후 질문 turn은 저장된 관찰, 사용자가 확인한 상태, 대화 이력을 바탕으로 생성한다.

**이유**: 매 turn마다 영상을 다시 읽으면 비용, 지연, 결과 불안정성이 커진다. 저장된 관찰을 정본화하면 rejected observation exclusion, source-required question, validation logging을 구현하기 쉽다.

**트레이드오프**: 초기에 분석 품질이 낮으면 이후 질문 품질도 제한된다. 이를 보완하기 위해 low/medium confidence 관찰은 확인 질문을 거치고, 사용자가 거절한 관찰은 폐기한다.

### ADR-010: 초기에는 멀티모달 파인튜닝을 하지 않는다
**결정**: MVP에서는 멀티모달 파인튜닝을 하지 않는다. API 모델, 프롬프트/컨텍스트 설계, guardrail, 비동기 처리, 클립/STT/IR 실험을 우선한다.

**이유**: 멀티모달 파인튜닝은 비용과 리소스 부담이 크고 초기 검증의 핵심 병목이 아니다. 먼저 한 바퀴 도는 제품 흐름과 질문 안전성을 검증해야 한다.

**트레이드오프**: 특정 연기 도메인에 최적화된 모델 성능은 초기부터 확보하기 어렵다. 대신 제품/데이터/검증 루프를 먼저 만든 뒤 실제 데이터로 필요한 개선 방향을 판단한다.

### ADR-011: YouTube 참고 영상은 공식 임베드만 허용한다
**결정**: MVP에서 YouTube 참고 영상은 공식 YouTube iframe 또는 IFrame Player API로만 보여준다. 영상 원본, 오디오, 프레임, 자막은 저장, 캐싱, 백업, 자체 서버 보관, RAG 인덱싱하지 않는다.

**이유**: 저작권과 플랫폼 정책 리스크를 줄이기 위해 YouTube와 권리자의 통제 범위 안에서만 참고 영상을 보여준다.

**트레이드오프**: YouTube 콘텐츠를 직접 분석하거나 검색 품질을 높이는 기능은 제한된다. 표현도 “비슷한 프로 배우 영상”이 아니라 “참고할 수 있는 장면 예시”로 낮춰야 한다.

### ADR-012: UI 레퍼런스는 Toss 디자인 문서를 기준으로 삼는다
**결정**: UI 구현은 `docs/Toss-DESIGN.md`를 상세 레퍼런스로 삼고, `docs/UI_GUIDE.md`에서 Acttub 전용 적용 규칙을 관리한다.

**이유**: Acttub MVP는 신뢰감, 명료함, 모바일 사용성, 한국어 가독성이 중요하다. Toss 스타일의 흰 배경, 강한 타이포 위계, 파란 액션 컬러, 절제된 shadow, 명확한 컴포넌트 상태는 질문형 연습 도구와 잘 맞는다.

**트레이드오프**: Toss 브랜드를 그대로 복제하면 Acttub만의 정체성이 약해질 수 있다. 따라서 색상과 컴포넌트 규칙은 레퍼런스로 사용하되, 카피와 제품 표면은 연기 연습 도메인에 맞춘다.

### ADR-013: 내부 용어 사전을 문서와 UI 카피의 기본 기준으로 사용한다
**결정**: 제품 문서, 티켓, 프롬프트, UI 카피는 내부 용어 사전의 표현을 우선 사용한다.

**이유**: “피드백”, “평가”, “약점”, “진단 결과” 같은 단어는 제품을 평가 서비스처럼 보이게 한다. “질문”, “관찰”, “질문 초점”, “다시 생각해볼 지점”, “내가 놓친 생각”처럼 낮춘 표현을 쓰면 제품 정체성과 안전성이 유지된다.

**트레이드오프**: 일부 용어는 아직 v0.1 검토 상태이므로 확정 표현처럼 과도하게 반복하면 나중에 수정 비용이 생긴다. 미확정 용어는 문서에서 열린 결정으로 표시한다.
