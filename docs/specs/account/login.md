# account.login 로그인·자동 가입

[공통 규칙](../common.md) · [영역 개요](README.md)

- 도입: 1.0.0
- 화면: A0, A0.1
- 테이블: users, user_identities, refresh_tokens, consent_documents, user_consents

## 기능
구글·애플·카카오·네이버 간편 로그인만 제공하며 로그인은 앱에만 있다. 웹은 로그인 없이 게스트로
쓴다. (account.guest) 별도 회원가입 화면은 없다. 처음 로그인한 사람은 같은 흐름 안에서 동의 화면을
거치고, 동의를 제출하는 순간 계정이 만들어진다. 다음부터는 같은 계정으로 들어온다. 이미 있는 계정도
아직 결정하지 않은 동의 문서가 있으면 로그인 응답에 실리고, 필수·선택 동의를 모두 결정할 때까지
보호 기능은 막힌다.

## 의도
가입 절차가 있으면 첫 화면에서 이탈한다. 배우가 촬영까지 가는 길을 버튼 하나로 줄인다. 국내
사용자 대부분이 쓰는 카카오·네이버를 더해 구글·애플 계정이 없는 사람도 막히지 않게 한다.

## 목적
어떤 제공자로 들어와도 한 사람은 한 계정이고, 두 번째 로그인부터는 자기 연습·노트·기억이 그대로
보인다.

## 규칙·제약
- 계정을 찾는 순서가 계약이다. ① 제공자와 제공자 ID로 찾는다. ② 없으면 제공자가 검증했다고
  알린 이메일로 기존 계정을 찾아 그 계정에 새 신원을 붙인다. ③ 그것도 없으면 새 계정을 만든다.
  이메일은 신원이 아니라 부가 정보다. 제공자에서 이메일을 바꿔도 같은 계정이다.
- 검증 안 된 이메일이 기존 계정과 겹치면 로그인을 막고 이미 쓰는 방식으로 안내한다. 검증 안 된
  주소만 대고 남의 계정에 들어가는 것을 막기 위해서다.
- 제공자별 이메일 검증 근거: 구글·애플은 ID 토큰의 email_verified. 카카오는 ID 토큰에 검증
  여부가 없어 사용자 정보 API의 is_email_verified로 확인한다. 네이버는 검증 표시가 없다. 주소가
  @naver.com이면 그 계정의 메일함이므로 검증된 것으로 보고, 외부 메일이면 검증되지 않은 것으로
  본다. 네이버가 준 표시가 아니라 계정 구조에 따른 우리 판단이다.
- 이메일은 앞뒤 공백을 떼고 소문자로 맞춘다. 검증된 이메일만 저장한다. 이메일 없는 계정도
  정상이며 그때 email은 빈 문자열이 아니라 NULL이다. 탈퇴로 지운 이메일도 NULL이다.
- 서버는 제공자가 발급한 OpenID Connect ID 토큰을 제공자 공개키로 검증한다. 구글·애플·카카오는
  앱이 ID 토큰을 서버에 넘긴다. 카카오는 개발자 콘솔에서 OIDC를 켜야 한다. 네이버는 앱이 인가 코드
  (authorization code)를 넘기고 서버가 교환해 받은 ID 토큰을 검증한다. 네이버의 앱 SDK는 앱에 비밀을
  넣어야 하고 ID 토큰을 주지 않기 때문이다. 애플 로그인 요청에는 authorization code를 함께 보낸다.
  서버는 이를 애플 토큰으로 바꿔 user_identities에 암호화해 저장하고, 탈퇴 때 폐기 API에 쓴다.
  네이버도 교환으로 받은 토큰을 같은 방식으로 저장해 탈퇴 때 연결 해제에 쓴다.
- provider 허용값은 google, apple, kakao, naver, 웹 게스트용 guest, 개발용 development다.
- users.status 허용값은 active와 deactivated다. 계정 정지는 1.0.0에 없다.
- 제공자 제공 범위: iOS는 넷 다. 안드로이드는 애플을 뺀 셋. 웹에는 로그인이 없다.
- iOS와 안드로이드 앱은 제공자마다 같은 애플리케이션 등록을 쓴다. 네이버와 카카오의 사용자 ID는
  애플리케이션 단위로 발급되므로 등록을 나누면 같은 사람이 다른 신원이 된다.
- 디자인의 로그인 화면(A0)에는 구글·애플 버튼만 있어 카카오·네이버 버튼을 더해야 한다.
- 카카오·네이버는 검수 승인 뒤에만 운영에서 켠다. 승인 전에는 등록한 테스트 계정만 로그인된다. 운영
  배포 체크리스트에 넣는다.
- 앱은 서버가 알려 주는 켜져 있는 제공자 목록으로 로그인 버튼을 그린다. 승인 뒤 서버 설정만 바꾸면
  버튼이 나오고 앱을 다시 배포하지 않는다.
- 같은 신원으로 동시에 두 요청이 오면 하나만 계정을 만들고 다른 하나는 그 계정을 쓴다.
- 로그인과 가입 제출은 각각 IP별로 분당 60회까지다. 넘으면 429.
- 로그인 응답은 어느 쪽이든 200이고 본문의 result로 가른다. 이미 있는 계정은 signed_in과 토큰을, 처음
  온 신원은 signup_required와 가입 토큰·동의 문서를 받는다.
- 계정 행은 가입 제출이 통과한 순간 만든다. 제출은 필수 문서 셋의 동의와 선택 문서의 결정을 모두
  담는다. 그 전에는 제공자 신원과 이메일을 저장하지 않고, 동의 화면을 위한 짧은 가입 토큰만
  발급한다. 동의 화면에서 나가면 아무것도 남지 않는다. 동의 없이 개인정보를 갖고 있지 않기 위해서다.
- 가입 토큰은 30분 유효하다. 만료하면 로그인 버튼부터 다시 시작한다.
- 가입 토큰은 서버가 저장하지 않는 암호화 토큰이다. 제공자, 제공자 ID, 검증된 이메일, 그리고 애플이면
  로그인 때 바꿔 온 애플 토큰을 담으며 앱은 내용을 읽을 수 없다. 애플 authorization code는 5분 동안
  한 번만 쓸 수 있어 동의 화면을 기다리지 않고 로그인 요청에서 바로 바꾼다. 프로필은 담지 않는다.
  계정이 생긴 뒤에 입력하므로 맡아 둘 것이 없다.
- 동의 화면의 저장 버튼은 필수 문서 셋에 동의하고 선택 문서마다 동의·거절 중 하나를 고른 뒤에야
  켜진다. 선택 문서 줄은 기본값 없이 동의·거절 두 버튼이다. 그래서 선택 미결정은 새 판을 발행할
  때만 생긴다. 서버도 가입 제출에 현재 판 모든 문서의 결정이 담기지 않으면 422로 거절한다. 버튼
  문구는 "동의하고 계속하기"다. 디자인의 "결정 저장하기"를 바꾼다.
- 동의 게이트는 요청마다 DB의 동의 상태로 판정한다. 로그인을 다시 하거나 토큰을 갱신해도 결정하지
  않은 문서가 하나라도 있으면 보호 기능은 막힌다. 필수 문서는 동의만 할 수 있고 화면에 거절이
  없다. 선택 문서는 동의와 거절 중 하나를 고르며, 거절도 결정이다. 갱신 응답에는 동의 목록이
  없으므로 앱은 시작할 때 미결정 동의를 조회한다. 동의 다음에는 프로필 입력이 같은 게이트로
  이어진다. (account.profile)
- 게이트에 막힌 요청은 403이다. 동의 미결정이면 사유 consent_required와 미결정 문서 목록을, 프로필
  미완이면 사유 profile_required를 함께 준다. 탈퇴한 계정의 403(account_deactivated)과는 사유로
  구분한다.
- 폰에 마지막 로그인 제공자를 기억해 두고 로그인 화면에서 그 버튼을 강조한다. 앱을 지우면 기억도
  사라진다. 서버는 관여하지 않는다.
- 로그인 때 제공자가 검증된 이메일을 주면 users.email을 그 값으로 갱신한다. 다른 계정이 이미 쓰는
  주소면 그대로 둔다.
- 액세스 토큰은 30분, 리프레시 토큰은 30일이다. 갱신할 때마다 리프레시 토큰을 새로 주고 옛 것은
  소진된다. 소진된 토큰이 다시 오면 탈취로 보고 그 회원의 세션을 전부 끊는다.
- 액세스 토큰이 만료되면 앱이 리프레시로 한 번 갱신하고 요청을 다시 보낸다. 서버가 리프레시를
  거부하면 기기의 토큰을 지우고 로그인 화면으로 보낸다. 네트워크 오류는 로그아웃 사유가 아니다.
- 30일 동안 앱을 한 번도 열지 않으면 다시 로그인해야 한다.
- 만료되거나 폐기된 지 30일이 지난 refresh_tokens 행은 하루 한 번 지운다. 그 전까지는 소진된
  토큰의 재사용 탐지와 문제 추적에 쓴다.

## 예외
- 제공자 토큰이 잘못됐거나 만료됐으면 401. 지원하지 않는 제공자는 400. 제공자 설정이 없으면 503.
  운영에서 꺼 둔 제공자(검수 승인 전의 카카오·네이버)도 400이다. 꺼 둔 것은 의도한 상태이고 설정이
  빠진 503은 운영 사고라 구분한다.
- 애플 로그인 요청에 authorization code가 없으면 422.
- 서버가 제공자에 물어야 하는데(카카오 사용자 정보 API, 애플 토큰 교환, 네이버 코드 교환) 제공자가
  답하지 않으면 502이고 계정을 만들지 않는다. 제공자 ID로 찾아지는 기존 회원은 이메일 검증 확인이 필요
  없으므로 묻지 않고 로그인된다. 제공자 장애는 처음 온 사람에게만 닿는다. 네이버만 예외다. 네이버는
  로그인할 때마다 코드 교환이 필요해 기존 회원도 502를 받는다. 1.0.0은 이를 받아들인다.
- 이메일 겹침은 409. 화면 문구는 "이미 OO로 가입한 이메일이에요". 응답에 기존 계정의 제공자 이름을 함께
  싣는다.
- 애플 '이메일 가리기'로 가입한 사람이 나중에 다른 제공자로 들어오면 계정이 둘이 된다. 1.0.0은
  이를 받아들인다.
- 애플로만 가입한 사람은 안드로이드에서 로그인할 수 없다. 1.0.0은 이를 받아들인다.
- 카카오·네이버는 이메일을 선택 동의로 받으므로 사용자가 동의하지 않을 수 있다. 그 계정은 이메일
  없이 만들어지고, 나중에 다른 제공자로 들어와도 이어지지 않는다.
- 제공자가 준 이름은 이름 칸을 미리 채우는 값으로만 쓰고, 이름은 가입 게이트의 프로필 입력 화면에서
  직접 받는다. 애플은 이름을 첫 로그인 한 번만 주므로 앱이 들고 있다가 프로필 화면까지 넘긴다. 동의
  화면에서 나가면 그 이름도 사라지고 이름 칸은 빈 채로 시작한다. (account.profile)
- 첫 로그인의 동의 화면에서 나가면 계정이 만들어지지 않는다. 다시 로그인하면 동의 화면부터
  시작한다. 이미 있는 계정에 새 필수 문서가 생기면 동의할 때까지 보호 기능만 막히고 계정은
  그대로다. 동의하지 않았다는 이유로 계정을 지우지 않는다.
- 탈퇴한 계정으로 다시 로그인하면 새 계정이 된다. 이전 연습·노트·기억은 보이지 않고 이전 계정에 관해
  아무것도 묻지 않는다.
- 제공자 쪽에서 연결을 끊거나 제공자 회원을 탈퇴하면 그 신원만 지운다. 네이버와 카카오는 연결 끊기
  콜백으로 알려 준다. 보낸 쪽을 확인하지 못하면(네이버는 서명, 카카오는 어드민 키) 401로 거절하고
  아무것도 지우지 않는다. 애플과 구글의
  알림은 1.0.0에서 받지 않으며 그쪽에서 끊긴 신원은 탈퇴 전까지 남는다. 1.0.0은 이를 받아들인다.
  계정은 남으므로 검증된 이메일이 있으면 다른 제공자로 이어질 수 있다. 마지막
  신원이 끊기고 검증된 이메일도 없으면 아무도 닿을 수 없는 계정으로 남는다. 1.0.0은 이를 받아들인다.
- 탈취 탐지의 부작용: 앱이 갱신 중에 죽어 새 토큰을 저장하지 못하고 옛 토큰으로 다시 시도한 정상
  회원도 세션이 전부 끊긴다. 보안을 위해 감수하며, 다시 로그인하면 된다.
- 기기마다 리프레시 토큰이 따로 있어 한 기기의 로그아웃이나 만료는 다른 기기에 영향이 없다. 탈취
  탐지로 전부 끊길 때만 예외다.

## 검증 방법
- 제공자 넷 각각 첫 로그인: 응답에 동의 문서와 가입 토큰이 실리고 users·user_identities 행은 아직
  없다. 동의를 제출하면 행이 하나씩 생기고 액세스·리프레시 토큰이 발급된다. 두 번째 로그인: 행이
  늘지 않고 같은 계정이다.
- 구글로 만든 계정과 같은 검증된 이메일로 애플 로그인: 같은 계정으로 들어가고 user_identities 행이
  하나 더 생긴다. users 행은 늘지 않는다.
- 구글로 만든 계정과 같은 @naver.com 주소로 네이버 로그인: 위와 같다.
- 외부 메일로 바꾼 네이버 계정이 기존 계정과 같은 주소로 로그인: 409와 안내 문구. 응답에 기존 계정의
  제공자가 실려 있고 계정은 늘지 않는다.
- 이메일 동의 없이 카카오로 로그인해 동의를 제출하면: users.email이 NULL인 계정이 생긴다.
- 탈퇴 뒤 같은 제공자로 로그인: 동의 화면부터 나온다. 동의를 제출하면 새 users 행이 생기고 이전
  데이터가 보이지 않는다.
- 잘못된 토큰은 401, 지원하지 않는 provider는 400. 한 IP에서 1분에 61번째 로그인: 429. 61번째 가입
  제출: 429.
- 운영에서 꺼 둔 제공자로 로그인: 400. 제공자 목록 조회: 켜 둔 제공자만 나온다.
- 애플 로그인에 authorization code 없이 요청: 422.
- 카카오 사용자 정보 API가 답하지 않을 때 처음 온 카카오 신원으로 로그인: 502이고 행이 없다. 같은 때
  기존 카카오 회원의 로그인: 된다.
- 가입 토큰을 디코드해 보면: 제공자 ID와 이메일이 보이지 않는다.
- 선택 문서의 새 판에 아직 답하지 않은 상태에서 연습 API 호출: 403과 미결정 문서 목록이 온다. 거절을
  고르면 허용된다.
- 필수 문서에 거절을 보내면: 422. 화면에는 거절 버튼이 없다.
- 첫 로그인의 동의 화면에서 나간 뒤 DB: users·user_identities 행이 없다. 다시 로그인하면 동의
  화면이 나온다.
- 기존 계정에 필수 문서의 새 판이 발행된 뒤 로그인: 로그인은 되고 연습 API는 403과 미결정 문서
  목록이다. 동의하면 같은 토큰으로 허용된다.
- 미결정 동의가 있는 채로 토큰을 갱신한 뒤 연습 API 호출: 여전히 403이다. 모두 결정하면(선택 문서는
  거절해도 된다) 같은 토큰으로 허용된다.
- iOS에서 만든 계정으로 안드로이드에서 같은 제공자로 로그인: 구글·카카오·네이버 각각 같은 계정이다.
- 카카오로 로그인한 뒤 로그아웃하고 앱을 다시 열면: 카카오 버튼이 강조돼 있다.
- 제공자에서 이메일을 바꾼 뒤 로그인: 같은 계정이고 users.email이 새 주소다. 새 주소를 다른 계정이
  쓰고 있으면 옛 주소가 남는다.
- 만료된 액세스 토큰으로 보호 API 호출: 갱신 뒤 요청이 성공하고 새 리프레시 토큰이 온다. 옛
  리프레시 토큰으로 다시 갱신: 401이고 그 사용자의 다른 기기도 다음 갱신 때(최대 30분 안) 로그인
  화면으로 돌아간다.
- 리프레시 토큰이 만료되거나 폐기된 상태에서 앱을 열거나 API 호출: 기기의 토큰이 지워지고 로그인
  화면이 뜬다.
- 갱신 요청이 네트워크 오류로 실패: 로그아웃되지 않고 오류가 표시되며 다음 요청에서 다시 갱신한다.
- 만료된 지 31일 된 refresh_tokens 행: 정리가 돈 뒤 없다. 29일 된 행: 남아 있다.
- 같은 신원으로 가입 제출 둘을 동시에: users 행이 하나이고 둘 다 같은 계정의 토큰을 받는다.
- 발급 31분 뒤 가입 제출: 401이고 행이 없다. 선택 문서 결정을 빼고 제출: 422.
- 네이버·카카오 연결 끊기 콜백 수신: 각각 그 신원 행만 없고 users 행은 그대로다. 보낸 쪽을 확인하지
  못한 콜백(틀린 서명, 틀린 어드민 키): 401이고 신원 행이 그대로다.

## 범위 밖
- 설정에서 로그인 방식 연결. 로그인한 상태에서 두 번째 제공자로 인증해 같은 계정에 신원을 붙이는
  기능. 폰을 바꿔 마지막 로그인 방식 기억이 사라진 경우와 애플 이메일 가리기로 갈린 계정까지
  해결한다. 후속.
- 안드로이드의 애플 로그인.
- 애플 서버 알림과 구글 계정 보호 알림 받기. 제공자 쪽에서 끊긴 애플·구글 신원을 바로 지우는
  기능이다. 후속.
- 웹 로그인. (account.guest)

  테이블도 만들지 않는다.
