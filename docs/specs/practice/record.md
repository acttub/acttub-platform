# practice.record 촬영·보관

[공통 규칙](../common.md) · [영역 개요](README.md)

- 도입: 1.0.0
- 화면: A0.3(촬영 권한), A0.4(카메라), A2.1(촬영 완료·보관함 자동 저장), A8(영상 선택), D4, W4, M4(워크스페이스 영상 올리기)
- 테이블: videos, video_transcripts

## 기능
배우가 앱에서 촬영하거나 앱·웹에서 파일을 고르면 영상이 배우의 보관함에 독립 자산으로 저장된다. 그 영상으로 코칭을 시작하거나
챌린지에 올리거나 그냥 보관할 수 있고, 어느 길을 골라도 같은 영상을 가리킨다.

## 의도
지금 앱은 기본 촬영만 기기 보관함에 두고 코칭 촬영은 곧바로 업로드로 넘어가며, 웹은 연습을 시작할 때 업로드를 확정한다. 영상이
연습에 묶여 있으면 촬영해 두고 나중에 코칭·챌린지로 보내는 흐름(A2.1 "지금 안 골라도 괜찮아요")이 성립하지 않는다. 영상을
자산으로 독립해야 이어하기(같은 영상으로 다음 회차)와 챌린지 참여(보관함에서 올리기)가 같은 파일을 쓴다.

## 목적
배우가 찍은 영상이 어디로 보낼지 정하지 않아도 보관함에 남고, 뒤에 코칭·챌린지로 이어진다.

## 규칙·제약
- 권한은 촬영 화면에 들어갈 때 카메라·마이크를 받는다(A0.3). 거절하면 갤러리에서 고르는 길로 돌아간다.
- 촬영이 끝나면 기기에 먼저 안전하게 저장하고 서버로 올린다. 서버 확정 전에는 "기기에 저장 · 업로드 대기"로, 확정 뒤에는
  "보관함 저장"으로 구분해 보여 준다(A2.1). 앱은 업로드 대기 큐를 두어 앱을 다시 열어도 이어 올리고, 웹은 확정 전 탭을 닫으면
  알린다.
- 올리기는 지금의 세 단계(올릴 자리 받기 · 올리기 · 마무리)를 유지한다. 예약 장부(upload_intents)가 request_id·본문 지문·객체 키·
  만료 시각·확정 video_id를 보존하고, 마무리가 videos 행을 만든다. 마무리 재전송은 같은 영상을 돌려준다. 만료된 미확정 객체는 삭제
  장부로 지운다. 형식은 MP4·MOV, 길이 5분, 서버에 올리는 파일은 100MiB 이하다(720px로 줄인 업로드본, 압축 결과 크기를 기기가
  검사, 서버도 실제 바이트·길이를 검사). 원본은 서버에 두지 않는다. 총량 검사와 영상 확정은 사용자 행을 잠근 채 같은 트랜잭션에서
  한다(동시 업로드 둘이 함께 한도를 넘지 못한다). 바깥 호출(객체 저장소) 동안 DB 트랜잭션을 잡지 않는다.
- 총량은 계정당 회원 5GiB, 게스트 500MiB(videos.byte_size 합)이고 넘으면 새 업로드만 422 video_quota, 기존은 보존한다. 이관으로
  넘어도 보존한다. 숫자는 사용량 근거 없는 초기 한도다.
- 코칭·챌린지·보관은 같은 video_id를 참조한다. 보내기는 복사가 아니라 참조다.
- 받아쓰기(video_transcripts)는 영상당 전사 묶음 하나(순서 있는 행들, 원문·단어 시각·간격·처리 구간)이며 첫 분석 때 만들고 같은
  영상의 다음 회차가 재사용한다. 같은 영상의 첫 분석이 두 묶음에서 동시에 시작돼도 생성 예약을 공유해 하나만 만들고, 확정된
  묶음만 재사용한다. 보관만 하면 만들지 않고 AI 분석 횟수를 쓰지 않는다.
- 게스트도 웹에서 영상을 보관한다. 첫 업로드 때 연습 동의 셋(이용약관·개인정보 수집·이용·AI 분석)을 시트로 받는다(account.guest).
  보관만 하는 데 AI 분석 동의가 필요한 이유는 보관함의 다음 길이 분석이기 때문이며 1.0.0은 이를 받아들인다.
- 옛 앱의 기기 보관함(계정 구분 없는 목록)은 1.0.0 첫 실행 때 "이 영상들을 지금 계정의 보관함으로 옮길까요?"를 한 번 묻고
  확인한 것만 올린다. 확인하지 않으면 기기에 남기고 다음 실행에 다시 묻는다.

## 예외
- 업로드 실패(오프라인): 기기 파일과 같은 요청 id를 들고 다시 시도한다. 7일 지난 대기 파일은 버리고 알린다.
- 압축 결과가 100MiB를 넘음: 올리지 않고 "영상이 너무 커요(100MB 이내)". 5분을 넘음: "영상이 너무 길어요(5분 이내)". 서버도 같은
  값을 검사해 422 video_too_large·video_too_long.
- 총량 초과: 422 video_quota, 화면은 보관함 정리(영상 삭제 또는 "파일만 파기", practice.library)로 안내한다.
- 마무리 전에 앱이 죽음: 올릴 자리는 30분 뒤 만료되고(422 upload_expired) 기기는 처음부터 다시 올린다. 확정되지 않은 것은
  보관함에 없고 미확정 객체는 만료 뒤 장부가 지운다.
- 마무리 응답만 유실: 같은 request_id로 다시 마무리하면 같은 영상이다.
- 카메라 권한 거절: 갤러리 선택은 된다.

## 검증 방법
- 온라인에서 촬영 → 마무리 성공 → 아무것도 고르지 않음: videos 1행, practices·ai_jobs 행 없음, 보관함에 "보관함 저장"으로 보인다.
- 마무리 전(업로드 대기)의 영상: videos 행 없음, 화면은 "기기에 저장 · 업로드 대기".
- 같은 영상으로 코칭 시작 뒤 챌린지에 올림: practices와 challenge_entries가 같은 video_id를 가리키고 객체는 하나다.
- 압축 결과 100MiB + 1바이트: 기기가 올리지 않고 "너무 커요". 5분 1초: 기기가 올리지 않고 "너무 길어요".
- 서버에 100MiB + 1바이트 메타: 422 video_too_large. 5분 1초 메타: 422 video_too_long. 실제 바이트가 메타와 다름: 마무리 실패.
- 총량 5GiB를 넘긴 회원의 업로드: 422 video_quota, 기존 행 그대로. 게스트 500MiB: 같다.
- 이관으로 총량을 넘긴 회원: 기존은 모두 보이고 새 업로드만 422.
- 한도 직전에 동시 업로드 둘: 하나만 확정되고 다른 것은 422 video_quota.
- 보관만 한 영상: video_transcripts 없음. 첫 분석 성공 뒤: 전사 묶음 하나. 같은 영상의 두 번째 회차 분석: 묶음이 늘지 않는다. 같은
  영상의 첫 분석 둘이 동시에: 묶음 하나.
- 새 게스트의 첫 업로드: 시트에 문서 셋. 동의 없이 마무리 API: 403 consent_required.
- 올릴 자리만 받고 31분 뒤 마무리: 422 upload_expired, videos 행 없음, 미확정 객체가 장부에 들어간다.
- 마무리 응답 유실 뒤 같은 request_id 재전송: 같은 video_id, 행 하나.
- 옛 보관함 영상 셋이 있는 기기에서 1.0.0 첫 실행: 확인 팝업이 뜬다. 확인: videos 3행. 취소: 기기에 남고 행 없음, 다음 실행에 다시 묻는다.
- 오프라인에서 촬영 뒤 연결: 큐가 올리고 같은 요청 id라 행은 하나다. 앱을 다시 열어도 큐가 남아 이어 올린다. 7일 지난 대기 파일: 버리고 알린다.
- 카메라 권한 거절: 갤러리 선택 화면으로 간다. 웹에서 마무리 전 탭 닫기: 경고가 뜬다.
