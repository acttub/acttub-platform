# practice.note 연습 노트

[공통 규칙](../common.md) · [영역 개요](README.md)

- 도입: 1.0.0
- 결정 기록: ADR-027
- 화면: A12(코칭 결과), A13(연습 노트), D7.2.2(결과 영역), M9, W9-R, M7.3·M7.3-b(다음 연기·내 문장으로 남기기)
- 테이블: coach_notes, note_ratings(노트 평가, SOMA-558)

## 기능
대화가 끝나면 그 회차의 연습 노트를 한 번 만든다. 짧은 요약, 다음 촬영에서 해볼 한 가지(없을 수 있음), 배우가 남긴 문장, 응원
문구 순서로 보여 주고, 지난 노트 목록에서 다시 본다.

## 의도
노트 생성 조건과 형식은 PRD와 아래 「3층 촬영 노트 (SOMA-531)」가 정한다. 나눈 이야기가 짧으면 노트를 만들지 않고(기존 갈래), 신형은 조기 종료에도
근거 수준에 맞는 기록(record_only)을 남긴다. 노트는 그 회차만 말하고 이전 연습과 견주지 않는다. 저장은 대화와 1:1인 coach_notes로
바꾸고 대화 상태를 복제하지 않는다.

## 목적
배우가 대화에서 스스로 말한 것이 가장 크게 보이는 기록을 얻고, 다음에 해볼 한 가지를 가져간다.

## 규칙·제약
- 노트는 대화가 닫힌 뒤 한 번 만든다. 고정된 종료 revision(source_revision)으로 만들고 이미 있는 노트를 다시 만들지 않는다. 생성
  실패는 한 번 재시도하고 그래도 실패하면 확인된 내용만 담은 폴백을 저장한다(fallback 표시).
- 노트도 format으로 갈린다. 기존 갈래(legacy)는 현행 종류(analysis·expression)와 응답 모양을 유지하고, 신형(v2)은 아래 규칙이다.
- 기존 갈래: 초기 폼·종료어·도움말을 뺀 배우 답이 2개 미만이면 노트를 만들지 않는다. 종료 응답 생성이 거듭 실패해 폴백으로 닫힌
  대화도 만들지 않는다. 신형: 조기 종료에도 기록을 남긴다. 제안이 없으면 초점이 남았을 때 observation, 초점도 없으면 record_only다.
  신형의 종료 생성 실패(system_failure)는 확인된 내용만 남기고 제안을 만들지 않는다.
- 종류는 action(다음 촬영 제안 있음)·observation(초점만 있음)·record_only(초점 없이 종료)다. 성공·실패 표시가 아니다.
- 제목은 초점 문구 원문이다(신형 v2 노트의 "연습 노트" 고정 제목은 없앤다). 초점이 없는 record_only의 제목은 NULL이고 목록은 묶음의 대체
  제목 규칙(상황 문장, 없으면 "제목 없는 연습")을 쓴다. 요약은 배우 말·관찰의 원문 발췌 최대 둘이다. 다음 촬영 제안은 배우 방향이나 장면
  목표와 실제 근거가 있을 때 하나만, 없으면 없음이다. "배우님이 고른 한 문장"으로 자동 표시하지 않고 제안은 선택·실행으로 바뀌지 않는다.
- 노트가 소유하는 것은 제목·요약 인용·제안·종류·배우 문장·정정·태그·폴백 여부·source_revision이다. 방향·초점·출처는 대화 상태에서
  읽는다. practice_id는 두지 않고 대화를 거친다.
- 화면 순서는 짧은 대화 요약 → 다음 촬영에서 해볼 한 가지 → 응원 문구다(PRD). 비교 기준·내부 출처 카탈로그는 기본 화면에서 빼고 기존
  공개 필드는 호환 응답으로 남긴다. A12의 "분석 확정 · 배우님과 맞춘 내용"처럼 확인·비교를 강제하는 옛 카피는 고친다. (디자인에 반영할 것)
- 영상이 파기된 뒤에도 노트와 대화는 열린다.
- 노트 목록(연습 기록)의 회차 제목이 여기서 나온다(practice.library).
- 노트 평가: 방금 끝난 노트(A13)와 지난 노트(A12) 맨 아래에서 "이 코칭 어땠어요? / 도움 됐어요 / 아쉬웠어요" 를 받는다. 누르는
  순간 서버에 노트 단위로 저장하고(helpful·not_helpful), 한 줄(선택, 앞뒤 공백을 걷은 1~100자)은 같은 평가에 덧붙는다. 같은 노트에
  다시 누르면 덮어써 행은 하나다. 화면의 초기값은 노트 조회의 my_rating 이다. 못 보낸 요청은 기기가 같은 요청 id 로 들고 있다가 다시
  보내고(노트마다 마지막 것 하나), 같은 id 에 다른 본문은 422 request_fingerprint_mismatch 다. 평가는 노트·대화·기억을 바꾸지 않고
  구글 시트로 보내지 않는다. 유저 문구에 "평가·점수" 같은 말을 쓰지 않는다.

## 예외
- 신형에서 첫 응답 직후 종료, 배우 방향 없음, 초점 있음: observation, 제안 없음. 초점도 없음: record_only, 제목 NULL. attempts 비어
  있음. 촬영 과제를 만들어 넣지 않는다.
- 기존 갈래에서 "모르겠어요 → 그만": 노트 없음, 연습 기록에 "아직 정리 없음".
- 신형 노트 생성 두 번 실패: 폴백 노트(fallback = true), 재생성 요청은 같은 노트를 돌려준다. 기존 갈래에서 종료 폴백: 노트 없음.
- 종료 요청과 노트 생성이 겹침: 노트 하나.
- 노트 평가: 남의 노트·없는 회차·노트가 아직 없는 회차는 같은 404 note_not_found. 아직 옮기지 않은 옛 노트(practice_reports)는
  읽을 수는 있지만 평가는 404 이고 기기는 그 요청을 버린다. 한 줄 101자는 422 comment_too_long.

## 검증 방법
- 기존 갈래 유효 답 2개 뒤 종료: coach_notes 1행(format legacy, 종류 analysis 또는 expression). 유효 답 1개: 행 없음.
- 신형 유효 대화 뒤 종료(근거 있음): format v2, action, 제안 하나, source_revision = 종료 revision, 제목 = 초점 원문, 요약 인용 ≤ 2이고
  각 인용에 출처(배우 말·관찰)가 있다.
- 신형 조기 종료, 초점 있음: observation, 제안 null. 초점 없음: record_only, 제목 NULL, 목록 제목은 상황 문장.
- 신형 생성 실패 2회: fallback true인 행 하나. 재생성: 같은 id. 기존 갈래 종료 폴백: 행 없음.
- 노트 조회: 순서가 요약·다음 촬영·응원이고 비교 기준이 없다. 옛 공개 필드가 그대로 온다. 제안을 선택·실행으로 바꾸는 API: 없다.
- 파일만 파기한 영상의 노트 조회(활성 소유자): 200, 영상 재생만 불가.
- 종료 요청 동시 재전송: 노트 하나.
- 노트 평가: 도움 됐어요 → note_ratings 1행(helpful). 아쉬웠어요로 다시 누름 → 같은 행이 not_helpful. 같은 요청 재전송 → 200 같은
  응답, 행 그대로. 같은 요청 id 에 다른 값 → 422. 노트 조회 → my_rating 이 그 값. 탈퇴 → 한 줄 NULL, 값은 남음. 게스트 이관 → 회원
  것.

## 3층 촬영 노트 (SOMA-531)


### 2→3 전달
서버가 종료 직후 생성한다. 모델에게 별도 장문의 handoff 요약을 만들게 하지 않는다.

```json
{
  "schema_version": "acttub.coach_handoff.v2",
  "session_id": "session",
  "state_revision": 3,
  "end_reason": "actor_finished",
  "record_ref": {"record_id": "record", "version": 1, "duration_ms": 8000},
  "context": {
    "direction": {"text": "상대의 대답을 기다리고 싶었어요", "origin": "actor_stated", "source_refs": ["m1"]},
    "scene_context": {"situation": null, "character_goal": null, "partner_action": null},
    "focus": {"label": "대사가 끝난 뒤 시선", "utterance_ref": null, "evidence_refs": ["e1"]},
    "reading": null,
    "open_points": []
  },
  "conversation": [
    {"id": "m1", "role": "actor", "text": "상대의 대답을 기다리고 싶었어요"},
    {"id": "c1", "role": "ai", "text": "지금까지 이야기한 내용으로 정리할게요."}
  ],
  "source_catalog": [
    {"id": "m1", "kind": "actor_message", "text": "상대의 대답을 기다리고 싶었어요", "record_id": null, "record_version": null, "start_ms": null, "end_ms": null},
    {"id": "c1", "kind": "coach_message", "text": "지금까지 이야기한 내용으로 정리할게요.", "record_id": null, "record_version": null, "start_ms": null, "end_ms": null},
    {"id": "e1", "kind": "video_observation", "text": "대사가 끝난 뒤 시선이 아래로 내려간다.", "record_id": "record", "record_version": 1, "start_ms": 6000, "end_ms": 7000}
  ]
}
```

위 내용은 가상 예시다. 실제 전달에는 현재 대화 원문 전체와 사용한 근거·조회한 한계를 담는다.
배우의 최종 정정도 대화와 출처 목록에 포함한다. 코치 메시지를 배우 의도의 증거로 바꾸지 않는다.
과제·선택·실행 이력을 새로 생성해 전달하지 않는다.

### 3층 입력과 모델 출력
입력은 `{coach_handoff: 위 객체, controls: {can_propose: boolean, max_next_takes: 1}}`이다.
현재 배우 방향과 함께 논의한 실제 관찰이 있어야 can_propose=true다. 모름만 남았거나,
방향/관찰이 부족하거나, 코치 생성 실패로 끝났으면 촬영 과제를 억지로 만들지 않는다.

```json
{
  "summary": [
    {"source_ref": "m1", "quote": "상대의 대답을 기다리고 싶었어요"},
    {"source_ref": "e1", "quote": "대사가 끝난 뒤 시선이 아래로 내려간다."}
  ],
  "next_take": {
    "instruction": "대사가 끝난 뒤에도 상대의 반응을 기다리는 동안 시선을 그대로 두고 찍어보세요.",
    "comparison": "같은 대목에서 시선이 내려가는 시점을 비교해보세요.",
    "basis_refs": ["m1", "e1"]
  }
}
```

- summary는 최대 두 개, 각각 원문 50자 이내다. 배우의 현재 발화 한 부분과 현재 관찰 한 부분을
  선택하며 서버가 짧은 요약으로 연결한다. 관련 출처 ID만 붙인 새 해석을 요약에 섞지 못한다.
- next_take는 **단일 객체 또는 null**이다. 지시 120자, 비교 기준 100자 이내이며 현재 방향의 배우
  출처와 현재 초점의 실제 관찰을 함께 참조해야 한다. 비교 기준은 저장하되 기본 화면에 추가 항목으로 펼치지 않는다.
- 생성·검증 실패는 한 번 재시도하고, 실패가 계속되면 확인된 관찰만 남긴다. 생성 실패는 계측한다.
- 응원은 모델 출력이 아니라 웹·앱의 고정 문구다: “오늘 촬영도 수고했어요. 다음 촬영도 응원할게요.”
- 출처 검증은 처방의 효과를 증명하지 않는다. 실제 모델의 관련성·말투·제안 적절성은 별도 검수한다.

### 저장·공개 응답·화면
저장 정본은 기존 `acttub.practice_note.v1`을 유지한다. 새 필드나 DB 컬럼을 추가할 필요가 없다.
새 제안은 항상 `practice.selection=proposed`, `selection_refs=[]`, `attempts=[]`다.
3층 제안 문장은 별도 coach_message 출처로 남기고 실제 관찰과 혼동하지 않는다.

| 내용 | 기존 공개 필드 | 화면 |
|---|---|---|
| 짧은 대화 요약 | `summary` | 이번 대화 요약 |
| 다음 촬영 제안 하나 | `practice.instruction` | 다음 촬영에서 해볼 것 |
| 근거와 비교 기준 | `evidence`, `practice.comparison` | 데이터 보존, 기본 화면에서는 생략 |
| 응원 | UI 고정 문구 | 제안 아래 작은 본문 |

제안이 없으면 “이번에는 촬영 아이템을 정하지 않았어요.”라고 표시한다.
기존 공개 필드와 OpenAPI 모양은 줄이거나 바꾸지 않는다. 원문 대화·비공개 출처 목록은 공개하지 않는다.
웹 `PracticeNoteCards`, 앱 `PracticeNoteBody`(완료 및 지난 기록 화면 공용)에 같은 배치를 적용한다.
기존 색상·서체·구분선·버튼·화면 이동을 사용한다.

### 적용 범위와 호환
- 기존 `three_layers_v1` 경험의 다음 코치 호출부터 v2 내부 응답을 사용한다. 원래의 1층 기록은 그대로 쓴다.
- 이미 끝난 v1 handoff의 재생성은 이전 편집 프롬프트를 사용하고 저장된 노트를 다시 생성하지 않는다.
- 신규 경험 선택의 서버 플래그·클라이언트 헤더·빈 입력 조건은 기존 규칙대로다. 이 변경 자체는 플래그를 켜지 않는다.
- 내부 handoff v2는 구버전 API가 생성할 수 없으므로 코드 롤백 때 열린 v2 세션/미완료 노트 작업을
  확인한다. 기존 저장 노트와 공개 응답은 구형 클라이언트에서도 같은 v1 형식이다.
- DB·SQL·마이그레이션 및 1층 추출 프롬프트는 바꾸지 않는다.

### 검증 경계
실행 테스트는 직전 답변 연결, 잘못된 인용·출처, 중간 과제 거부, 짧은 답·정정·종료,
3층 첫 제안 생성과 선택/실행 불변, 실패 폴백, 공개 응답의 비공개 필드 제외, 웹·앱의 세 부분 배치를 확인한다.
실모델에 대해 “ㅁㄹ”, “그 말이 아니야”, “무슨 뜻이야”, “그만”, 지시문 탈취 요청을 이어 보내며
답변 의미와 제안 적절성을 별도로 확인해야 한다. 테스트 스텁 통과는 실제 코칭 품질 검증과 다르다.

## 대화 연속성: 장면 분석을 노트로 잇기

2층은 장면 전체의 말하는 이유·목표를 `focus.basis=scene`으로 다룰 수 있지만,
3층은 영상의 표현 관찰과 별도의 배우 방향이 있어야 연습을 제안할 수 있었다.
장면 분석을 마친 대화가 노트에서 표현 교정으로 바뀌거나 연습 없이 끝나는 불일치를 수정한다.

### 3층 규칙
- 장면 분석은 현재 배우 방향 또는 배우가 직접 정리한 인물 목표와 대사/관찰로 연습을 만든다.
- 표현 연습은 여전히 실제 영상 관찰을 요구한다. 대사나 확인 한계만으로 표현을 평가하지 않는다.
- 2층의 유효한 제안을 이어가고 배우가 거절·정정한 방법은 되살리지 않는다.
- 아직 뜻을 모르거나 방법 제안을 원하지 않으면 연습 없이 확인된 내용만 남긴다.
- 인물 대사는 `장면 대사`로 표시한다. 배우 경험·성과로 바꾸지 않는다.
- 전체 초점의 연습 근거는 앞뒤 구간을 유지하며 공개 노트의 구간도 단일 대사로 줄이지 않는다.
- 모델 실패 시 현재 배우 목표를 보존하고 과제를 지어내지 않는다.
- 과거 기록은 `basis`가 없으면 기존 표현 기준을 적용한다. 공개 응답 필드는 유지한다.
