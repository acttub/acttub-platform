# practice.coach 코치 대화

[공통 규칙](../common.md) · [영역 개요](README.md)

- 도입: 0.1.0
- 결정 기록: ADR-027
- 화면: A11(질문 대화), A11.1(영상과 장면 펼침), D7.1.1, W7-R, W7-R-b, M7. D7.1.2·M7.1·M7.2(분석 확인 대화·확정)는 기존 갈래 전용이며 신형에는 확인·후보 선택을 강제하지 않는다
- 테이블: coach_conversations, coach_messages

## 기능
분석이 끝난 회차에서 코치와 대화한다. 코치는 영상 관찰과 배우의 답을 근거로 질문을 이어 가고, 배우는 답하거나 되묻거나 "그만"으로
마친다. 회차에 대화는 하나다.

## 의도
코치의 행동 규칙(아래 「규칙·제약」과 「2층 대화 (SOMA-531)」 이하 절)은 0.1.0에서 바꾸지 않는다. 바꾸는 것은 저장이다. 회차와 1:1인 대화, 쌓이기만 하는
메시지, 낙관적 잠금과 request_id 멱등이다. 현행은 한 연습에 대화를 여럿 만들 수 있어 ERD와 어긋난다.

## 목적
배우가 대화를 끊고 돌아와도 같은 대화를 이어 가고, 재전송해도 같은 답을 받는다.

## 입력·출력
| 입구 | 입력 | 출력 | 오류 |
|---|---|---|---|
| `POST /v2/coach/start` | 필수 `practice_id`·`request_id` (`CoachStartRequest`) | `CoachTurnResult` 200(`{conversation, message, note}`), 이미 열린 대화면 같은 대화 | `analysis_not_ready` 409, `conversation_closed` 409, `practice_not_found` 404, `coach_response_unavailable` 502, `account_deactivated` 403, `request is still processing` 409 |
| `POST /v2/coach/reply` | 필수 `conversation_id`·`request_id`, `text`(300자까지)·`revision` (`CoachReplyRequest`) | `CoachTurnResult` 200, 닫히면 `note` 포함 | `conversation_closed` 409, `conversation_conflict` 409, `request_fingerprint_mismatch` 422, `practice_not_found` 404, `coach_response_unavailable` 502, `account_deactivated` 403, `request is still processing` 409, 301자 422(배열) |
| `GET /v2/coach/conversations/{conversation_id}` | conversation_id | `CoachConversation` 200(`reply_limit` 포함) | `conversation_not_found` 404 |
| `POST /v2/coach/direct-video`, `GET·DELETE /v2/coach/direct-video/{id}`, `POST /v2/coach/direct-video/{id}/messages` (dev 전용, openapi 밖) | 영상 파일(50MiB까지), 메시지 2,000자까지 | 아래 「Gemini 직접 영상 코칭」 | `unsupported_media_type` 415, `upload_too_large` 413, `empty_video` 422, `direct_video_session_limit` 429, `direct_video_turn_limit`·`direct_video_not_ready` 409, `direct_video_not_found` 404 |

## 상태
coach_conversations.status — 회차의 코치 대화.

| 상태 | 들어오는 전이(조건) | 일으키는 기능 |
|---|---|---|
| open | 회차 stage가 conversing일 때 시작 | practice.coach |
| closed | 코치가 마무리하거나 응답 상한·"그만"·종료 생성 실패로 닫힘. close_reason은 gap_stated·exhausted·limit·user_ended·system_failure 중 하나 | practice.coach |

- 불변 조건: 회차당 대화 하나(`uq_coach_conversations_practice`). 저장 때 state_revision이 읽은 값과 다르면 쓰지 않는다(409
  conversation_conflict). closed는 open으로 돌아가지 않고 다시 코칭은 새 회차다.
- 끝 상태: closed. 닫히면 회차가 closed/conversation_closed가 되고(정본: [practice.start](start.md#상태)) 노트를 한 번 만든다(practice.note).

## 규칙·제약
- 열린 대화는 같은 id로 재개하고, 닫힌 뒤 다시 코칭하려면 새 회차(practice.resume)다. 옛 자료의 복수 대화는 옛 읽기 경로로만
  본다([「0.1.0 스키마 전환」](README.md#010-스키마-전환)).
- 시작 요청의 request_id는 대화의 start_request_id이고(영상만 올린 첫 시작에는 배우 메시지가 없다), 배우 메시지는
  (conversation_id, request_id) 유일이다. 재전송은 [공통 규칙 「요청 재전송」](../common.md#요청-재전송)을 따르고, 대화를 닫은 답장의
  재전송도 그 요청이 만든 코치 응답·종료·노트 결과를 그대로 돌려준다.
- 코치 응답 상한은 시작 응답을 포함한 코치 응답 수로 기존 갈래 8개, 신형 16개다. 기존 갈래는 코치 응답 7개가 저장된 열린
  대화에 답이 오면 8번째 응답으로 마무리하고, 신형은 15개 뒤 다음 응답으로 마무리한다. 종료 뒤 답은 409 conversation_closed다.
- 응답의 `conversation`에는 status·revision·coach_reply_count·reply_limit·messages가 있어 화면이 남은 응답 수와 마무리 예고를 그린다.
  reply_limit은 저장된 경험 판을 읽은 응답 상한이고 시작·답장·대화 조회가 같다. 대화 조회는 409 뒤 최신 상태를 다시 읽는
  자리이자 회차의 이전 대화를 펼치는 자리다.
- 첫 응답은 코칭 경로마다 다르고, 경로는 회차의 경험 판과 서버 설정이 고른다. dev·운영 배포는 직접 영상 코칭을 켠다
  ([DEPLOY-HOME §3](../../deploy/DEPLOY-HOME.md#3-actions와-일상-배포)). "모든 첫 응답은 질문"이라고 적지 않는다.

  | 경험 판 | 서버 설정 | 경로와 첫 응답 |
  |---|---|---|
  | legacy | — | 질문 하나(「첫 질문 개정」) |
  | three_layers_v1 | 직접 영상 켬, 연습 루프 켬(기본) | 「연습 루프」 |
  | three_layers_v1 | 직접 영상 켬, 연습 루프 끔 | 「응답 분류와 지침 선택」의 opening |
  | three_layers_v1 | 직접 영상 끔, 라우팅 켬(기본) | 「2층 대화 동작 분류와 코드 기반 프롬프트 선택」의 첫 응답 |
  | three_layers_v1 | 직접 영상 끔, 라우팅 끔 | 질문 하나(「첫 질문 개정」) |

  직접 영상은 `ACTTUB_DIRECT_VIDEO_ENABLED`, 연습 루프는 `ACTTUB_DIRECT_VIDEO_PRACTICE_LOOP`, 라우팅은
  `acttub.coaching.routed-enabled`이고 기본값은 각 절에 있다.
- 도움 버튼("잘 모르겠어요", "제가 되물을게요", "나중에 연습")은 입력을 준비만 하고 배우가 보내야 전송된다. 버튼만으로 응답 횟수를
  쓰지 않는다.
- 배우 답은 300자까지다. "그만"·"종료"·"끝"·"여기까지"라고 쓰면 언제든 마친다. "끝"·"여기까지"는 발화 전체가 그 말일 때만
  종료다(`ClosingIntent`). 화면의 "연습 마치기"는 연습을 끝내고 나가는 버튼이다.
- 동시 요청은 state_revision으로 가른다. 코치 응답을 만드는 사이 다른 요청이 먼저 저장했으면 409 conversation_conflict이고,
  화면은 입력을 보존하고 최신 대화를 다시 읽는다.
- 상태 json에는 배우의 말·정정·영상 근거·코치 제안·실행 보고를 출처별로 나눠 두고, 동의·종료를 실행·효과로 승격하지 않는다. lookup은
  화면 턴이 아니라 상태에만 남긴다.
- 프로필을 모델에 싣는 조건과 방식은 [account.profile 「규칙·제약」](../account/profile.md#규칙제약)이 정본이다.
- 기존 갈래·이전 경로의 응답 규칙(2026-09-10):
  - 배우의 최신 말이 코치에게 하는 질문이나 설명·기술적 도움·영상 피드백 요청이면 먼저 답한다. 한 응답의 질문은 최대 하나이고,
    설명만으로 충분하면 질문이 없어도 된다(ADR-004 개정).
  - 반복해서 막히면 선택지와 자기 정리 요구를 늘리지 않고 근거가 있는 설명·예시로 바꾼다.
  - 1층 관찰·받아쓰기와 현재 대화 원문을 함께 쓰고, 배우의 정정이 이전 요약보다 우선한다.
  - 채팅은 텍스트 입력이다. 모바일의 음성 입력은 받아쓰기이며 음색 분석용 첨부가 아니다.
  - 코칭 문장에서는 관찰 근거를 설명하는 강점·개선점 같은 말을 쓸 수 있다(ADR-005 개정). 점수·등급·합격 가능성·재능·성격 판정은
    하지 않는다(「범위 밖」). 관찰과 연습 노트의 문장 검사는 그대로다.
  - 막힘을 건너뛴 `그 외`는 영상 우선 기본 코치를 쓴다. 장면 맥락이 모두 비어도 첫 1~2회 장면 질문이나 고정된 질문 구간을 붙이지
    않는다. 시작·후속 응답·재생성 모두 같은 기본 코치를 쓴다.
  - 재생성 사유는 빈 응답, 화면에 그대로 노출될 Markdown 강조·제목·코드 기호와 `JSON need` 형태의 내부 형식 메모, 도움 요청 뒤
    직전 응답의 완전 반복, 영어 대화에서 완전히 한국어로 돌아온 설명, 종료 요청이나 응답 상한에 닿은 응답의 continue다. 두 번 실패하면 확인하지
    못한 결론을 만들지 않는 대체 응답을 쓴다.
  - 표면적인 뜻으로 충분한 장면에 숨은 심리를 강제하지 않는다. 모름 응답을 설명할 때도 새 관계 갈등·과거사·심리 원인을 추가하지
    않으며, 불확실하다는 단서를 붙인 것만으로 근거 없는 해석을 허용하지 않는다.
- 코치 응답을 기다린 뒤의 대화 저장은 [공통 규칙 「저장 직전 재확인」](../common.md#저장-직전-재확인)을 따른다.

## 예외
- 회차 stage가 conversing이 아닌 채 시작(분석 전·분석 실패): 409 analysis_not_ready.
- 닫힌 대화에 답: 409 conversation_closed.
- revision 충돌: 409 conversation_conflict, 입력 보존.
- LLM 실패: 바깥 의존 실패로 다시 시도를 안내하고 revision·메시지는 늘지 않는다. 종료 응답 생성이 거듭 실패하면 신형은
  system_failure로 닫는다. 그때 노트는 [practice.note 「규칙·제약」](note.md#규칙제약)대로다.
- 같은 요청 id·다른 본문: 422 request_fingerprint_mismatch.

## 검증 방법
- 분석 완료 회차에서 시작: coach_conversations 1행(start_request_id), 시작 재전송: 같은 대화, 행 하나.
- 답 하나 보내기: coach_messages에 배우 1·코치 1, turn_index 순. 같은 요청 id 재전송: 메시지가 늘지 않고 같은 코치 응답.
- 종료(노트 포함) 요청 재전송: 대화·노트 행이 늘지 않고 최초 결과.
- 두 요청 동시: 하나만 반영, 다른 것은 409 conversation_conflict.
- 기존 갈래에서 코치 응답 7개가 저장된 대화에 답: 8번째 코치 응답이 마무리이고 대화가 닫힌다. 신형에서 15개 뒤 답: 16번째가 마무리. 그 뒤
  답: 409 conversation_closed, 응답이 늘지 않는다.
- 300자 답: 200. 301자: 422. 같은 요청 id·다른 본문: 422 request_fingerprint_mismatch.
- 이전 경로 회차의 첫 응답: 질문 하나로 시작. 기본 라우팅 회차: 제공 가능한 도움을 우선한다. 응답에 lookup 턴이 없고 상태에만 있다.
- 프로필을 바꾼 뒤 다음 턴: 새 값이 입력에 들어가고 대화 행에 프로필 스냅샷이 없다.
- 옛 자료의 복수 대화 회차 조회: 가장 최근 대화가 "대화", 나머지가 "이전 대화" 목록으로 보인다.
- 도움 버튼만 누름: 메시지 행 없음.
- 닫힌 대화에 답: 409 conversation_closed. 닫힌 뒤 "다시 코칭": 새 회차가 만들어진다(practice.resume).
- 게스트 대화: 프로필이 없어도 200.
- 대화 중 탈퇴: 그 뒤 도착한 코치 응답이 저장되지 않고 403 account_deactivated.

## 범위 밖
- 점수·등급·레벨·랭킹·평가표(PRD 「지금 하지 않는 것」, ADR-005). 합격 가능성·재능·성격 판정.
- 대화 중 새 영상·음성을 첨부해 비교하는 기능 안내.
- 배우 개인 심리·트라우마·치료적 영역을 파고드는 질문(PRD).
- 관찰 확인(맞음/아님/모르겠음) 화면과 배우가 직접 쓰는 자기 정리 문장(PRD, ADR-014). 신형에는 확인·후보 선택을 강제하지 않는다.
- 대화 도중 재분석(PRD).

## 2층 대화 (SOMA-531)


### 첫 질문 개정
이 절은 legacy와 `acttub.coaching.routed-enabled=false` 롤백 경로의 첫 질문이다. `three_layers_v1`의 기본 경로는 아래
「2층 대화 동작 분류와 코드 기반 프롬프트 선택」을, 직접 영상 코칭이 켜진 환경은 「Gemini 직접 영상 코칭」을 따른다.
이 첫 질문 정책은 새 구조화 코치와 기존 영상 우선 코치가 함께 쓴다(실행 파일은 [CONTRACT §8-5](../../../apps/api/CONTRACT.md#8-5-영상만-올리는-새-코칭-계약-soma-526)).

- “이 답을 알면 영상의 무엇을 더 정확하게 볼 수 있는가?”를 판단하고 질문을 선택한다.
- 전체 대사·흐름, 배우가 이미 적은 방향, 장면에서 중요한 발화·반복·변화를 함께 본다.
  눈에 띄는 고개 움직임·멈춤이나 confidence만으로 첫 주제를 정하지 않는다.
- 배우가 자기 말로 답할 수 있고 답에 따라 살펴볼 기준이 달라지는 미확인 하나를 묻는다.
  이미 받은 목표를 되묻거나 AI가 만든 해석에 동의하게 하지 않는다.
- 새 경로의 첫 `continue`는 질문 하나, 실제 대사/관찰 참조, 해당 참조를 포함하는 `context_update.focus`를 요구한다.
  `controls.min_questions`는 현재 전달된 영상 근거에 따라 갱신되며 조회 후에도 적용된다.
- 근거가 있는 첫 응답은 질문 누락·중복과 대표적인 모호한 해석 문구를 재생성 사유로 삼는다. 새 경로는 근거 참조·focus 저장·즉시
  종료도 검증한다.
- 대사 인용의 물음표는 질문 개수에 넣지 않는다. 인용만 물음표이고 배우에게 묻는 말은 없으면 거부한다.
- 모델 응답을 반복해 검증해도 실패하면 그 해석을 보여주지 않는다. 영상 근거는 있지만 첫 질문 생성이
  실패한 경우 실패 사실을 알리고 배우가 원한 모습을 묻는 단순 대체 질문을 쓴다. 자료 자체가 없으면 의도를 강제로 묻지 않는다.
- 서식·질문 수·근거 참조 검증은 의미적 관련성이나 한국어 자연스러움을 증명하지 않는다.
  영상별 실제 모델 대화 검토에서 질문의 중요성과 다음 답변의 연결을 별도로 확인해야 한다.

신형은 사용자가 첫 질문에 답하기 전에 종료해도 노트를 만든다([practice.note 「예외」](note.md#예외)의 조기 종료). 턴 수만으로
코칭의 충분함이나 개선을 판정하지 않는다. 이미 생성된 대화·노트의 원문을 소급해서 바꾸지 않는다.

### 2층 입력과 응답
기존 request/session ID, actor_context, record_view, state_sources, recent_messages, controls를 유지한다.
`last_exchange`가 직전 코치 발화와 이번 사용자 답변을 함께 제공한다. 첫 사용자 발화는 만들지 않는다.
`coaching_state`는 revision, context, response_style, 선택적으로 last_reply만 모델에 보여준다.
예전 상태에 저장된 proposals/attempts는 DB에 보존하되 새 대화의 과제로 사용하지 않는다.

```json
{
  "action": "respond",
  "base_state_revision": 2,
  "message": "상대가 대답하기를 기다리고 싶었군요. 그때 상대는 어떤 반응을 하고 있었어요?",
  "reply_link": {
    "user_message_id": "turn:session:4",
    "actor_quote": "상대의 대답을 기다리고 싶었어요",
    "move": "clarify",
    "evidence_refs": []
  },
  "context_update": null,
  "style_update": null,
  "flow": "continue"
}
```

`context_update=null`은 유지다. 객체를 주면 direction/scene_context/focus/reading/open_points를 모두 준다.
direction과 장면 설정은 배우 원문 인용 및 actor 출처가 필요하다. reading은 null이다.
직전 답변 인용은 해당 메시지에 실제로 있어야 한다. 예전 답변 ID로 다음 질문을 만드는 응답은 거부한다.
move는 open/clarify/explain/correct/acknowledge/close이며 질문 횟수·성격 유형·내부 추론을 뜻하지 않는다.
이 필드는 대화 연결을 추적하는 근거이지 의미적 관련성을 자동 증명하지는 않는다.

`proposal_changes`, `attempt_changes`는 새 출력에서 허용하지 않는다. 재연·촬영·변경 과제를 중간에
시키지 않는다. 대표적인 과제 문구, 추상적 심리 표현, 직전 발화 완전 반복도 검증 단계에서 거부한다.
금지 표현 검사는 보조 장치다. 한국어 자연스러움과 질문의 실제 관련성은 실대화 검토가 필요하다.

`lookup`은 기존 형식 그대로다. 저장된 텍스트를 최대 두 번 조회할 수 있고 원본 영상을 다시 분석하지 않는다.
기본 120자·2문장·질문 최대 하나, 간결 모드 80자·1문장, 요청한 상세 설명은 300자·4문장이다.
응답 상한(「규칙·제약」)까지이며 충분하면 먼저 끝낸다. 동의·연습 실행을 종료 조건으로 요구하지 않는다.

## 2층 대화 동작 분류와 코드 기반 프롬프트 선택


### 목적과 적용 범위
`three_layers_v1` 세션의 시작·후속 응답에 적용한다(직접 영상 코칭이 꺼진 서버, 「규칙·제약」의 경로 표). 기존 legacy 세션의 공개 계약은 유지한다.
하나의 생성 프롬프트가 대화 분류와 코칭을 동시에 결정하던 경로를 분리한다.

1. **분류**: Luna가 영상 기록·이전 대화·현재 발화·현재 맥락·직전 교환을 받아 다음 코치의 동작을 route 하나로 반환한다.
2. **생성**: Java가 시작·종료 여부를 먼저 확인하고, 후속 턴은 enum/switch로 분류 지침을 선택한다. 공통 지침 + 해당 목적 지침 하나 + 저장 형식을 조합한다.

생성된 응답을 그대로 전달한다. 별도의 한국어 스킬 검토·문장 다듬기 호출은 없다.

별도의 LLM 가드레일 검토나 ML 분류기를 호출하지 않는다. JSON 형식·근거 참조·원문 인용·길이·revision 검사는 저장 무결성 검사로 유지한다.
문장 수는 인용 대사 안의 문장 부호를 빼고 코치가 배우에게 건네는 문장으로 센다. 인용을 포함한 전체 글자 수 제한은 유지한다. 종료 요청·턴 한도는 코드가 먼저 처리하며, 종료할 때에는 분류를 생략한다.

### 네 가지 분류
| route | 생성 목적 |
|---|---|
| advance | 사용자 답을 반영해 이해나 연기 선택을 발전시킨다 |
| scaffold | 현재 답하거나 실행하기 어려운 지점에 단서·설명·선택을 제공한다 |
| repair | 코치의 잘못된 전제 또는 이해되지 않는 설명을 바로잡는다 |
| respond | 사용자가 요청한 해석·방법·피드백에 직접 답한다 |

정정·설명 이해 실패는 repair가 우선한다. 새 요청은 respond, 직전 질문에 답하지 못해 발판이 필요하면 scaffold,
활용할 답이 생기면 advance다. "모르겠어요"·"?"·"아닌데요"는 직전 질문·설명과 연결해서 판단한다.
시도 이후라는 이유만으로 별도 분류를 선택하지 않는다.
첫 영상만 있고 발화가 없으면 분류는 respond이며, 코드가 `opening.txt`를 선택한다. 새 분류나 추가 모델 호출은 아니다.
첫 응답의 목적은 **배우가 자기 영상에서 함께 풀 가치가 있는 지점을 발견하고 대화를 이어갈 이유를 느끼게 하기**다.
전체 흐름에서 중요한 지점 하나를 골라 구체적인 영상 피드백 한 문장과 질문 한 문장으로 시작한다.
근거에서 가능한 의도 두 가지를 유추해 번호 없이 자연스럽게 묻는다. 답에 따라 다음 코칭이 달라져야 하며
다른 해석도 받아들인다. 근거가 부족하면 선택지를 만들지 않고 필요한 사실 하나를 확인한다.
이미 받은 의도는 활용하고, 결점을 억지로 만들지 않으며 잘된 선택의 발전도 돕는다.
첫 focus는 함께 풀 주제이며 인물의 의도·결점에 대한 확정 진단이 아니다. 후속 응답은 답을 활용한 도움을
먼저 제공하며 모든 분기를 선택형 질문으로 끝내지 않는다.
단순 수락에는 새 과제나 질문을 붙이지 않아도 된다. 네 분류는 연기 주제가 아니라 다음 응답의 주목적이다.
첫 응답용 지침은 후속 요청이나 종료 지침에 섞지 않는다.

### 입력과 출력
분류 입력은 `video_record`, `conversation_history`, `user_message`, `actor_context`, `coaching_state`, `last_exchange`다.
영상 파일·다운로드 주소가 아니라 기존 1층의 텍스트 기록만 사용한다. 첫 발화는 null이며 가짜 배우 메시지를 만들지 않는다.
`coaching_state.context`는 기존 저장된 배우 발언·초점·미해결 지점을, `last_exchange`는 직전 코치 문장과 현재 답을 제공한다.
새로운 의미 요약이나 거부 해석 전용 DB 필드를 추가하지 않는다. 정정은 원문 대화에 남고 수정된 맥락은 기존 context_update로 보존한다.
이전 저장 행에 옛 분류 이름이 있어도 최신 발화로 다시 분류한다. 저장된 분류를 그대로 답으로 복사하지 않는다.

분류 출력:

```json
{"route":"repair"}
```

생성에는 같은 영상 기록·원문 대화·현재 발화와 기존 맥락, 허용 근거 ID, 길이 제한을 전달한다.
Luna의 판단 이유나 다른 세 분류의 지침은 전달하지 않는다. 질문·종료·실행을 사용자 발화와 혼동하지 않는다.
배우 프로필은 생성 입력에만 싣고 분류 입력에는 싣지 않는다([account.profile](../account/profile.md#규칙제약)).

생성 출력:

```json
{"message":"배우에게 보여줄 응답", "context_update":null, "evidence_refs":[]}
```

`context_update`는 기존 dialogue_context 스키마를 유지하고 배우의 실제 원문과 영상 근거를 저장한다(출처 구분은 「규칙·제약」).
revision, reply_link, flow는 코드가 조립한다.

생성 원문을 대화·출처·3층 handoff에 동일하게 저장한다. 정정으로 무효가 된 맥락과 focus는 context_update에서 지우거나 바꾼다.
공통 프롬프트는 역할·근거 구분·언어를 짧게 정의하고, 줄 도움과 질문의 필요성은 각 분류 프롬프트가 정한다.
서적 본문 검색이나 새로운 지식 저장소는 이번 변경에 포함하지 않는다. 프롬프트 변경만으로 전문 자료가 연결되었다고 간주하지 않는다.

### 실패 처리와 호출 수
정상 대화는 분류 1회 + 생성 1회다. 첫 대화도 동일하며 종료는 생성 1회다.
분류 결과가 유효하지 않거나 호출이 실패하면 임의의 분류로 대체하지 않고 기존 재시도 가능한 오류 계약을 따른다.
생성 출력의 형식·근거·맥락 저장 검사가 실패하면 같은 route에서 최대 한 번 재생성한다.
기존의 키워드 기반 코칭 분기, 손 관찰용 고정 답변, 다단계 모델 조회는 새 경로에서 호출하지 않는다.
기존 레코드 조회 기능과 단일 프롬프트 경로는 롤백용으로 유지한다.

새 경로의 각 HTTP 호출 제한은 20초이며 SDK 내부 재시도를 중첩하지 않는다.
사용자에게 실패 턴을 저장하지 않으며, 종료 생성이 실패하면 기존 종료 대체 문구와 handoff 계약을 유지한다.

### 설정과 관측
- `acttub.coaching.routed-enabled`: 기본 true. false로 이전 2층으로 복귀할 수 있다.
- 분류 모델: `gpt-5.6-luna`, reasoning low. 분류는 엄격한 JSON Schema 출력이다.
- 생성 모델: 기존 `OPENAI_CHAT_MODEL` 설정을 사용한다(미설정 시 Luna).
- 관측 단계: `coach.route`, `coach.turn`, `coach.regeneration`. 과거 `coach.polish` 기록은 남지만 새 편집 호출은 없다.
- 모델 호출 메타데이터에 `contract=dialogue_actions_v2`와 선택된 route를 남긴다. 사용자 화면에는 노출하지 않는다.
- 기존 `acttub.coach_handoff.v2`로 3층에 연결한다.

### 검증
`CoachingPipelineTest`는 네 갈래 선택·2회 호출·생성 원문 저장·직전 교환 전달·정정 맥락의 후속 전달·기본 Spring 연결·첫 응답·긴 발화·분류 실패·영상 부재·종료·근거 오류를 검사한다.
`OpenAiResponsesClientTest`는 분류 전용 모델과 strict schema, 불완전 응답, 재시도 상한을 검사한다.

합성 데이터 실모델 테스트는 기본 비활성이다. API 키가 제공된 환경에서만 명시적으로 실행한다:

```sh
ACTTUB_ROUTE_LIVE_TEST=1 OPENAI_CHAT_MODEL=gpt-5.6-luna ./gradlew test --tests '*CoachingPipelineLiveTest'
```

합성 대화 결과는 `apps/api/build/route-eval/`에 남는다. 성공 여부와 코칭 품질은 별도로 검토한다.

첫 응답의 의미 검토 기준:

| 상황 | 기대 행동 | 실패 사례 |
|---|---|---|
| 상황 입력 없이 영상만 올림 | 전체 흐름의 중요한 지점에 피드백하고 근거에 맞는 두 해석을 자연스럽게 묻는다 | 건조함·시선 변화만 요약하고 끝냄 |
| 의도·관계가 이미 제공됨 | 그 정보를 활용해 아직 풀리지 않은 선택을 묻는다 | 누구에게 왜 말하는지 처음부터 다시 조사함 |
| 이야기의 목적을 설명함 | 답을 바탕으로 가능한 해석·선택을 발전시킨다 | 첫 질문을 반복하거나 곧바로 말투 교정으로 넘어감 |
| 질문에 모르겠다고 답함 | 같은 지점을 풀 대사 단서나 잠정 해석을 제공한다 | 관계 등 다른 항목으로 질문을 돌림 |
| 대사 없는 장면·기록 한계 | 실제 행동 기록에 연결해 필요한 정보 하나를 묻는다 | 상대·사건·발화를 지어냄 |

단위 테스트는 첫 응답·재생성·후속 분류의 프롬프트 분리를 검증한다. 이 검증만으로 실제 모델이 위 의미 기준을 충족한다고 판단하지 않는다.

추가 의미 검토: 짧게 선택한 답에도 도움을 제공하는지, 다른 의도를 받아들이는지, 두 해석의 근거가 부족할 때 억지 선택지를 만들지 않는지, 좋은 연기에 결점을 강요하지 않는지 확인한다.

## 2층 응답 선택 (`reply_link.selection`)


### 변경 목적
배우가 요청한 도움에 답한다. 질문을 이어가는 것 자체가 목표가 아니다. 첫 응답의 목적은 위 「네 가지 분류」에 있다.

### 서비스 계약
`reply_link.selection`은 현재 요청, 막힌 부분, 이미 확인한 근거, 질문이 필요한 경우 그 정보와 쓰임을 담는다. 장황한 사고 과정이나 예상 정답은 저장하지 않는다. 선택 정보는 서버 상태의 `last_reply`에 남고, 사용자 응답 `CoachReply`에는 메시지·상태·종료 시 노트용 인계만 전달한다. 기존 세션은 다음 응답부터 선택 정보를 기록하므로 별도 데이터 변환은 없다.

`move`는 기존 open/clarify/explain/correct/acknowledge/close에 simplify/suggest/assess/extend를 추가한다. `suggest`의 제안은 proposal/attempt 이력으로 만들지 않는다.

서버가 확인하는 것은 구조적 조건이다: 질문의 정보·쓰임 누락, 없는 근거 참조, 관찰 없는 전달 평가, 종료와 추가 질문의 충돌. 질문의 유용성, 이미 답한 내용의 의미상 반복, 해석의 적절성을 완전히 판정하는 장치는 아니다. 이 부분은 실제 모델 대화 평가가 필요하다.

## Gemini 직접 영상 코칭

`ACTTUB_DIRECT_VIDEO_ENABLED=true`(기본 false)인 서버의 신형(`three_layers_v1`) 회차에 적용한다. 분석은 1층을 건너뛰고
([practice.analyze](analyze.md#규칙제약)), 코치가 소유한 원본 영상과 현재 세션 대화 원문을 Gemini에 직접 전달한다.
응답 프롬프트는 공통 원칙과 서비스가 고른 작업 지침으로 조합한다.

API와 화면, 대화 저장·재개·멱등 요청·응답 상한·종료·3층 노트는 기존 것을 사용한다.
별도 실험 페이지는 배포하지 않는다. 임시 세션 API(`/v2/coach/direct-video/**`)는 dev(`SITE_URL=https://dev.acttub.com`)에서 직접
영상 플래그가 켜졌을 때만 열린다(공개 스키마 밖). 임시 세션의 명시적 종료는 `finished`다.
구조화된 영상 관찰은 생성하지 않는다(코치 응답을 배우 의도·실행 기록으로 바꾸지 않는 것은 「규칙·제약」).
프로필([account.profile](../account/profile.md#규칙제약))과 같은 묶음의 이전 맥락은 생성 호출에만 별도 블록으로 싣고 분류에는 싣지 않는다.
코칭 출력은 평문이다. 서버는 모델 응답에서 Markdown 제목·강조·목록 기호·표·코드 블록 기호를 걷어 낸 평문을 대화
턴·handoff·응답에 같은 값으로 저장하고, 걷은 뒤 비어 있으면 빈 응답과 같은 생성 실패로 처리한다.
매 요청의 Gemini 파일과 로컬 임시 파일은 성공·실패 모두 정리한다. 원본 재전송으로 지연이 추가될 수 있다.
legacy 연습과 직접 영상 플래그가 꺼진 환경은 기존 모델 경로를 유지한다.

### 응답 분류와 지침 선택 (2026-09-22)
첫 응답은 전체 인상 → 가장 크게 보완할 점과 영상 속 근거 → 개선 방향으로 제공한다.
장면 전체의 자연스러움·전달력에 영향을 주는 문제를 최대 두 개 우선하며, 부족함을 억지로 만들지 않는다.
반복되는 문제는 여러 구간으로 뒷받침하고 화면 밖 상대의 답변·표정을 사실이나 진단 근거로 지어내지 않는다.
기본은 서너 개의 짧은 문단이며 공통의 한두 문장 제한을 없앴다. 끝의 질문은 필요한 경우에만 한다.
후속 분류와 각 작업 지침은 유지하며, 기존 진단과 배우의 최신 말을 이어서 다룬다.
기초 연기 용어는 사용하되 이해하기 쉬운 문장으로 설명하고, 근거 없이 새 결점을 늘리지 않는다.

첫 응답은 코드에서 `opening`을 선택한다. 후속 답은 별도 Gemini 텍스트 호출이
직전 코치 발화와 실제 대화 원문을 보고 `intention`, `correction`, `unsure`, `method`,
`acknowledgement`, `other` 신호로 분류한다. 분류에는 영상을 보내지 않는다.
분류 JSON과 지침 목록은 코칭 모델·사용자 대화에 섞지 않는다.

`DirectVideoRouting`이 선택하고 `coaching/direct-video/` 아래 텍스트 파일을 조합한다.
정정, 이해 어려움, 방법 요청, 의도, 수긍 순서로 우선하며 정정+이해 어려움 또는
정정+방법 요청에는 두 작업만 붙인다. 예상 밖의 질문·사실·감정·화제 전환이나 확신하기 어려운 답은
명시적인 기타(`other`)로 받아 최신 말에 직접 답하고 기존 대화 흐름에 억지로 맞추지 않는다.
빈 신호 배열도 `other`로 받는다. `other`가 다른 신호와 함께 오면 구체적인 신호를 우선하되 단순 수긍보다 우선한다.
기타는 정상 분류이며, 분류 실패 시 사용하는 `general` 및 실패 기록과 구분한다.
‘응’도 직전 의도 확인 질문에 대한 답이면 의도 정보로 분류할 수 있게 문맥을 전달한다.

단순 수긍은 `acknowledgement`로 짧게 받아주되 세션을 닫지 않는다.
기존 종료 판정과 응답 상한만 `closing`을 선택하고 세션 종료를 결정한다.

분류 호출 제한은 15초, 출력 제한은 1024토큰이다. 후속 응답에는 분류 호출 비용과 지연이 추가된다.
모르는 라벨·중복·잘못된 형식 또는 제공자 실패는 원인을 보고하고 `general`로 답한다.
취소·작업 점유권 상실은 기본 답변으로 숨기지 않는다. `coach.route`와 `coach.turn`을
별도로 기록하며 실제 선택과 폴백 여부는 내부 코칭 호출 메타데이터에 남긴다.

검증은 실제 SDK 요청의 텍스트 전용 분류, 선택된 지침만 전달됨, 복합 응답 우선순위,
잘못된 분류의 폴백, 수긍과 종료 구분, 대화 저장·실패 시 보존을 대상으로 한다.
스텁 테스트는 실제 모델의 한국어 분류 정확도를 보장하지 않으므로 실사용 대화로 별도 확인한다.

애플리케이션은 직접 영상 플래그가 명시되지 않으면 기존 경로를 유지한다. 배포 환경의 플래그 값은
[DEPLOY-HOME §3](../../deploy/DEPLOY-HOME.md#3-actions와-일상-배포), 롤백은 [§4](../../deploy/DEPLOY-HOME.md#4-코드-배포-복구)에 있다.
기존 GEMINI_API_KEY와 GEMINI_MODEL을 사용하며 새 계정용 키나 SITE_URL 설정을 요구하지 않는다.
플래그를 끄면 분석을 건너뛴 회차는 기존 코치 경로로 이어갈 수 없으므로 새 영상을 올린다.

### 연습 루프 (2026-09-24, SOMA-508)
직접 영상 코칭(영속 코칭)은 분류·지침 조합 대신 `coaching/direct-video/practice-loop.txt` 하나로 대화 전체를 이끈다.
환경과 무관하게 기본이다(`ACTTUB_DIRECT_VIDEO_PRACTICE_LOOP` 기본 true, 운영도 핫픽스 #388로 켜져 있다).
false를 명시하면 위의 분류·지침 경로로 돌아간다(롤백). dev 임시 세션 API는 연습 루프를 쓰지 않는다.

코치는 이 테이크에서 두 곳 이상 반복된 배우 자신의 버릇 하나를 비춰 주고(소리 쪽 — 빠르기·말끝·크기·쉬는 곳 — 을
먼저, 혼자 찍은 영상에서 흔한 시선은 뒷순위), 질문으로 배우가 그 버릇을 들여다보게 한다.
비추기 → 파고들기(언제·왜 나오는지) → 이어보기(이 인물에게 맞는지) → 마무리(배우 자신에 대한 한 줄 →
다음 테이크에서 해 볼 한 가지 제안) 순서다. 대화 중에는 연기·재촬영 같은 과제를 시키지 않는다.
배우에게 보이는 말은 쉬운 말로, 한 줄 40자 이내다.

모델은 첫 응답에 `<설계>`·`<코치>`를, 이후 응답마다 맨 앞에 `<상태>` 한 줄을 쓴다.
`DirectVideoPracticeLoop`가 코치 본문만 대화에 저장·표시하고, 설계와 상태는 `coaching_state.practice_loop`
(`design`, 코치 턴 순서의 `statuses`)에 둔다. 다음 턴에는 모델에 넘기는 기록에만 둘을 다시 붙인다.
상태 줄의 칸 중 이번 응답이 하는 일이 `마무리2`·`끝`이면 세션을 닫는다(`interrupted`). 줄 끝에 붙은 날 자모(예: "요.ㄴ")는 저장 전에 지운다. 배우의 종료 요청과 응답 상한은
기존 판정을 따르되 응답은 연습 루프 프롬프트가 쓴다. 루프 이전에 열린 세션은 위 「응답 분류와 지침 선택」으로 이어간다.
세션이 닫히면 노트(3층)는 모델을 부르지 않고 연습 루프가 남긴 것으로 채운다(`DirectVideoPracticeLoop.note`).
제목은 설계의 버릇, 요약은 배우가 쓴 자기에 대한 한 줄과 버릇이 나온 이유에 대한 배우의 답(원문), 다음 촬영은
설계의 다음 테이크 한 가지다. 기존 노트 생성기는 영상 직접 코칭이 구조화된 방향·초점을 만들지 않아 record_only 로 떨어졌다.
프롬프트 실험 기록은 SOMA-508 코멘트에 있다.

#### 배우가 적은 것도 새 코치로 (2026-09-25, SOMA-508 hotfix)

새 연습은 배우가 상황·인물·목표나 막힘을 적어도 `three_layers_v1`(새 코치)로 연다([practice.start](start.md#규칙제약)).
연습 루프는 적은 것을 `## 배우가 적은 것`(상황·인물·목표·막힌 곳·막힌 곳 설명) 칸으로 프로필·지난 연습 칸 뒤,
루프 프롬프트 앞에 붙인다(`DirectVideoPracticeLoop.actorMaterial`). 빈 칸과 건너뛴 막힘(`그 외`)은 싣지 않으므로
영상만 올린 연습의 프롬프트는 그대로다. 버릇은 계속 영상에서만 고른다. 적은 인물·상황은 `<설계>`의 인물 칸과
코치의 말에, 목표는 이어보기에, 소리·몸 표현의 막힘은 첫 코치에, 인물·대사 뜻의 막힘은 이어보기에 쓴다.
지난 연습에 같은 버릇이 있으면 `<설계>`의 `지난번: 같음`을 거쳐 첫 코치가 "지난번에도"로 시작한다.
대화 중 배우가 대본이나 설명을 붙여 넣으면 `답하기`로 받아 이어간다.

#### 배우의 말부터 고르는 여러 줄 상태 칸 (2026-10-01, SOMA-508 hotfix)

이후 응답의 `<상태>`는 여러 줄이다. 모델은 `배우의 말`(그만·자기 한 줄·반박·평가 요청·선택 설명·스스로 알아챔·짧은 답·
질문·설명·답) → `지금까지`(같은 버릇 질문·짚어주기·응답 번호) → `피할 것` → `할 일` → `물을 것` 순서로 채우고,
할 일은 프롬프트의 할 일 표에서 고른다. 배우가 코치의 생각(장점·단점·분석)을 물으면 `짚어주기`로 영상에서 본 것을 먼저
말하고, 코치가 보는 방식에 반박하면 `짚어주기(다른 쪽)`으로 그 버릇 주제를 내려놓고 소리가 아닌 쪽의 장점을 짚는다.
배우가 버릇을 인물을 위한 선택이라고 설명하면 다시 묻지 않는다. `<설계>`에는 `살아 있는 곳`·`다른 쪽 살아 있는 곳`·
`버릇이 가리는 것` 칸이 더해졌다.
`DirectVideoPracticeLoop`는 `할 일:` 줄이 있으면 그 값으로 종료(`마무리2`·`끝`)와 노트용 단계를 판정하고, 없으면 예전 한 줄 해석을
쓴다. 노트의 자기 문장은 마무리1 다음 답에 더해, 다음 상태의 `배우의 말`이 `자기 한 줄`인 답(배우가 청하기 전에 먼저
말한 한 줄)도 받는다. 실험 근거: 운영 대화에서 뽑은 배우 유형 5개(평가 요청·반박·의도 설명·단답·협조)를
실험실에서 재현해 기존 판과 비교했다(기존 판 5명 중 1명 완주 → 이 판 5명 완주, 배우 답은 시뮬레이션).

#### 말 빠르기 쏠림과 예시 베끼기 (2026-10-01, SOMA-508 hotfix)

운영 최근 20세션의 첫 버릇 중 11건이 말 빠르기였다. 프롬프트는 소리 칸을 쉬는 곳·말끝·크기·강조·빠르기
순으로 보고 칸마다 뚜렷함(0~3)을 매기며, 빠르기는 다른 네 칸이 모두 없거나 뚜렷함 1 이하일 때만 고른다.
지난 버릇과 같은 쪽은 다른 소리 칸이 뚜렷하면 고르지 않는다. 모델이 맨 위 칸을 고르는 쪽으로 쏠리므로(순서를 고정하면
맨 위 칸 73%) `DirectVideoPrompts.practiceLoop(연습 id)`가 연습마다 소리 네 칸의 순서를 섞는다(같은 연습은 늘 같은
순서, 빠르기는 늘 마지막). 프롬프트에는 대사가 든 예시를 두지 않는다 — 예시 대사나 빈칸 표시를 다른 배우의
영상에 그대로 쓴 일이 있었다. 마무리2의 상태 칸에는 `다음 테이크:`("지키며: …" 또는 "반대로: …") 줄이
더해져, 배우의 한 줄이 그 버릇을 지키는 쪽이면 줄이라는 제안을 하지 않는다. 노트의 다음 촬영은 이 줄이 있으면 이 줄을
쓴다(`DirectVideoPracticeLoop.closingNextTake`). 실제 배우 영상 11개 재현: 첫 버릇 말 빠르기 13/33 → 1/22.

#### 소리·템포 대신 네 쪽을 본다 (2026-10-01, SOMA-508 hotfix)

빠르기를 뒤로 미뤄도 첫 버릇이 쉬는 곳·말끝·끊어 말하기 같은 템포 계열에 머물렀다(제품 판단: "템포밖에 안 본다").
버릇 후보는 이제 소리가 아니라 네 쪽이다: 감정의 변화, 상대와 주고받기, 원하는 것과 행동, 몸·시선·표정.
`<설계>`는 이 네 칸에 뚜렷함(0~3)을 매기고 가장 높은 것을 고른다. 소리와 템포는 버릇으로도, 이유로도 꺼내지 않는다.
`DirectVideoPrompts.practiceLoop(연습 id)`는 이 네 칸의 순서를 연습마다 섞는다. 실제 배우 영상 19개 재현에서
몸·시선·표정 14, 주고받기 3, 감정 2, 원하는 것 0으로 몸 쪽 쏠림이 있다(후속 과제).

#### 배우가 쓰는 말로 답한다 (2026-10-02, SOMA-508 hotfix)

연습 루프는 한국어 전용이었다. 영어로 상황을 적은 배우(9/30)는 한국어 첫 질문에 답하지 않고 떠났고, 영어로 묻는 배우(9/7)에게도
한국어로 답했다. 답할 말은 분류(코드)가 정하고 프롬프트는 그 말로 쓰인 것을 고른다 — 프롬프트 안에서 언어를 가르지 않는다.
- 분류(`DirectVideoPracticeLoop.replyLanguage`): 앱 요청 말(Accept-Language, `OutputLanguage`)이 한국어가 아니면 그 말. 한국어면
  배우가 쓴 말(`actorLanguage`: 이번 답 → 지난 답 → 연습 메모 순, 종료 말은 건너뜀, 한글이 있으면 한국어·가나는 일본어·로마자 단어가
  충분하면 영어, "한국어로"/"in English" 요청 우선).
- 선택(`DirectVideoPrompts.practiceLoop(연습 id, 말)`): 한국어는 `practice-loop.txt` 그대로, 그 밖의 말은 `practice-loop.en.txt`.
  영어가 아닌 말(일본어 등)은 영어판 끝에 `OutputLanguage` 지시를 붙인다. 두 판 모두 숨은 칸 이름·할 일 이름·배우의 말 분류 이름은
  한국어라 상태 칸 해석과 노트는 같다. 한국어판을 고치면 영어판도 같이 고친다.
- 한국어판 프롬프트 끝에 영어 지시만 붙였을 때는 영어 메모 세션 첫 질문이 0/4 영어였고, 영어판은 4/4 영어였다(실제 배우 영상).

#### 연기 영상이 아니면 코칭하지 않고 끊는다 (2026-10-02, SOMA-508 hotfix)

운영에서 1.3초 영상과 6.6초 검은 화면 영상에 코치가 없는 대사를 인용하며 버릇을 지어냈고, 배우는 "나 아무말도 안 햇는데"라고 답한 뒤
떠났다. 판정은 둘이다.
- 길이(서버): 첫 응답 전에 영상이 3초 미만이면(`DirectVideoPracticeLoop.MIN_ACTING_MS`, 길이를 모르면 건너뜀) 영상을 올리거나 모델을
  부르지 않고 끊는다. 1.3초 영상은 모델이 연기라고 판정하고 장면을 지어냈으므로(실험 2/2) 모델 판정에 맡기지 않는다.
- 내용(모델이 분류, 서버가 끊음): 첫 응답 `<설계>` 첫 칸 `영상: 연기 / 연기 아님: 이유`. 화면 유무와 연기 여부는 분리한다.
  검은 화면이어도 음성 연기는 허용하고, 화면에서 확인하지 못한 표정·시선·몸은 추측하지 않는다. 잡담·정보 설명·뉴스·강의·음악·잡음처럼
  명백한 비연기만 끊고 애매하면 연기다. 연기 아님이면 서버가 코치 문장을 버린다.
끊을 때는 고정 문구("이 영상에서는 연기 장면을 찾지 못했어요. 연기한 장면이 담긴 영상을 다시 올려 주세요.", 영어 배우는 영어)로 답하고
`interrupted`로 닫으며 `coaching_state.practice_loop.not_acting`(`too_short`/`model`)을 남기고 노트를 만들지 않는다(`NoteWriter`).
실험(실제 배우 영상): 검은 화면 2/2 끊음, 정상 연기 영상(17초 포함) 8/8 코칭.

첫 비연기 안내의 종료 상태는 메시지와 같은 트랜잭션에서 저장한다. 대화와 회차는 closed, 노트는 없으며 뒤에 답을 보내도 409 conversation_closed다. 비연기 입력을 완료한 연습으로 집계하는 종료 후속 처리는 호출하지 않는다.


#### 음성 없는 영상의 대사를 추측하지 않는다 (2026-10-02, SOMA-508)

운영 검증에서 오디오 트랙이 없는 10초 연기 영상에 코치가 구체적인 대사를 인용했다. 영상의 연기 여부와 대사 확인 여부는 별개다. 무언 연기는 허용하되 들리지 않은 말은 코칭 근거로 쓰지 않는다.

- 한국어·영어 연습 루프는 첫 숨김 설계에서 버릇 후보보다 먼저 `대사 확인`(확인됨 / 확인 안 됨)과 `확인된 대사`를 작성한다. 실제 말소리가 들리고 내용까지 명확할 때만 확인됨이며, 음성 없음·불명확·불확실은 확인 안 됨이다.
- 확인 안 됨이면 확인된 대사는 없음이다. 필수 대사 두 곳을 채우지 않고, 보이는 표정·시선·몸·구간 두 곳으로 관찰을 뒷받침한다. 입모양·배경 음악·장면 설명·이전 코치의 추측으로 대사나 정확한 시각을 복원하지 않는다.
- 후속 상태에도 대사 확인 값을 유지하여 이어보기·짚어주기에서 같은 제한을 적용한다. 예전 설계에 칸이 없으면 실제 영상 음성으로 다시 판단하며 이전 인용은 증거가 아니다. 배우가 작성한 대본은 작성한 글로만 다룬다.
- 분류·지침 선택 경로의 공통·opening 프롬프트에도 같은 규칙을 적용한다. API 요청·응답·DB 상태 전이는 바꾸지 않는다.
- Gemini 원본 업로드 전에 기존 `VideoRecordChunks.hasAudio`의 ffprobe 검사로 오디오 트랙 유무를 확인하여 내부 Video 메타데이터로 전달한다. 오디오 트랙이 없으면 서버 확정 정보(`no-audio.txt`)가 이전 설계·상태의 대사 주장보다 우선한다. 검사 실패를 거짓 무음으로 바꾸거나 무시하지 않고, 외부 업로드 전에 실패시킨다.
- 오디오 트랙이 없는 영상에서 모델이 대사를 확인했다고 주장하거나, 배우가 직접 작성하지 않은 대사를 인용하면 기존 코칭 실패 경로로 거절한다. 본문뿐 아니라 노트의 근거로 흘러갈 숨김 설계·상태도 저장 전에 검사한다. 배우가 작성한 자기 문장은 작성한 글로만 되짚을 수 있다. 예전의 근거 없는 숨김 설계는 히스토리·새 노트에서 폐기하되 원본 메시지는 지우지 않는다.
- 오디오 트랙 존재는 실제 발화나 명료한 대사의 증명이 아니다. 아래 로컬 오디오 검사로 완전 무음·디코딩 실패를 먼저 막는다. 소리 신호가 있는 불명확한 영상은 보수적인 대사 확인 지침을 따른다. 이 검사는 ASR이나 사람의 발화 판별이 아니며, 실제 모델 사례·프롬프트 구조·SDK 메타데이터 전달·코칭 저장 전 회귀 검증과 구분한다.

#### 오디오 없음＋전체 검은 화면은 AI 호출 전에 종료한다 (2026-10-02, SOMA-508)

- 연습 루프 첫 응답에서 원본을 내려받고 etag를 확인한 뒤 로컬 입력 검사를 한다. Gemini 파일 업로드·준비 확인·응답 생성 이전이다.
- 오디오 트랙이 없을 때만 모든 영상 프레임을 디코딩한다. 밝기 범위를 8-bit full range로 정규화한 뒤 모든 프레임의 최대 밝기(YMAX)가 정확히 0일 때만 전체 검은 화면으로 확정한다. 샘플 프레임·평균 밝기·어두운 화면이라는 이유만으로는 끊지 않는다.
- 오디오 없음과 전체 검은 화면이 모두 확정되면 기존 비연기 안내로 정상 종료한다. `interrupted`와 `coaching_state.practice_loop.not_acting=empty_input`을 남기며 노트·완료 후속 처리는 만들지 않는다. 존재하지 않는 호흡·신음·대사를 모델이 생성할 기회가 없다.
- 검은 화면＋실제로 디코딩 가능한 소리 신호는 음성 전용 연기를 보존하기 위해 통과한다. 트랙 존재만으로 통과시키지 않는다. 오디오 없는 배우 영상도 검지 않은 프레임이 하나라도 있으면 통과한다. 이후 실제 연기 여부와 음성 근거는 기존 모델 판정·서버 검증을 따른다.
- ffprobe/ffmpeg 실패·디코딩 프레임 없음·불완전한 측정은 빈 입력으로 간주하지 않는다. 업로드·AI 호출 없이 기존 코칭 불가 오류를 반환하고 로컬 검사 실패로 보고한다. 입력에 대한 거짓 비연기 판정을 저장하지 않는다.
- 검사한 오디오 사실을 업로드에 재사용한다. 기존 직접 영상 임시 API·롤백 경로·루프 이전 세션의 계약은 변경하지 않는다.
- 오디오 트랙 내부의 완전 무음·디코딩 실패는 아래 검사로 막는다. 음악·잡음과 사람의 발화를 구분하지는 않는다. ASR, MP3/WAV 업로드, 환경변수·배포 설정·DB·웹/모바일 응답 스키마는 추가하거나 변경하지 않는다.

#### 오디오 트랙이 있어도 완전 무음·검사 실패는 AI에 보내지 않는다 (2026-10-02, SOMA-508)

- 오디오 트랙이 있으면 기존 미디어 처리와 같은 첫 오디오 트랙을 원본에서 끝까지 디코딩한다. `astats`의 누적 샘플 수·모든 채널의 최대 신호를 모든 프레임에서 검증한다. mono downmix·샘플 구간·평균 크기로 판단하지 않는다.
- 전체 녹음의 최대 신호가 정확히 0(`Peak_level=-inf`)인 경우에만 완전 무음으로 확정한다. 크기 기준선을 두지 않으므로 속삭임·작은 소리·짧은 발화·앞뒤 긴 침묵을 무음으로 오판하지 않는다. 스테레오 역상 채널도 섞어 상쇄하지 않는다.
- 연습 루프 첫 응답에서 완전 무음을 확인하면 `영상의 소리가 녹음되지 않았어요.\n소리가 들리는 영상으로 다시 올려 주세요.`라고 안내하고 `interrupted`로 닫는다. `coaching_state.practice_loop.input_issue=silent_audio`를 남기며 비연기라고 판정하지 않는다. 기존 입력 거절과 마찬가지로 노트·완료 후속 처리를 만들지 않는다.
- FFmpeg 오류·90초 제한·디코딩 프레임 없음·불완전 측정·비정상 수치(NaN/Inf)는 완전 무음으로 바꾸지 않는다. AI 업로드·모델 호출 없이 기존 `coach_response_unavailable` 오류로 막고 로컬 검사 실패로 보고한다. 손상된 입력에서 일부 앞쪽 소리가 디코딩됐어도 통과시키지 않는다.
- 정상 소리의 검사 결과는 업로드에 재사용한다. 결과를 받지 않는 기존 upload 호출도 소리 검사를 수행해서 직접 영상 임시 API·롤백·이전 세션이 이 검사를 우회하지 못하게 한다. 트랙 없는 시각 연기는 기존 정책대로 허용한다.
- 이 검사는 들을 수 있는 사람의 발화나 대사 명료성을 증명하지 않는다. 잡음·음악·클리핑·불명확한 발화의 내용 판별과 ASR은 추가하지 않으며, 소리 신호가 존재하면 기존 모델의 연기 판정과 보수적인 대사 근거 검증을 따른다.

#### 정정·방법 요청과 배우가 지난 연습에서 직접 한 말 (2026-10-05, SOMA-508)

운영 대화(9/28~10/5, 팀 제외 33세션)에서 배우가 평가·방법·예시를 직접 청한 14번 대부분에 코치가 관찰을 조금 말한 뒤
다시 질문했고, "카메라 렌즈 봤어용"처럼 관찰을 바로잡아도 같은 해석이 돌아왔다. 같은 장면을 일곱 번 올린 배우는 새 연습마다
같은 진단을 들었고, 코치가 쉬어 보라고 한 제안을 따른 테이크를 버릇으로 지적받았다.

- `배우의 말`에 `정정`(코치가 본 것이 사실과 다르다)과 `방법 요청`(방법·예시·장면을 청한다)이 더해졌다. 할 일은 `내려놓기`
  ("그러면 제가 잘못 봤어요."로 받고 그 주제를 `피할 것`에 넣은 뒤 다른 쪽의 살아 있는 곳과 고르기 쉬운 질문)와
  `방법 주기`(구간 하나 · "다음 테이크에서는 ~해 봐도 좋아요." · 그러면 어떻게 보이는지, 질문 없음)다. `짚어주기`는 더 이상
  되묻지 않고 "제일 아쉬운 건 ~"과 "먼저 볼 건 ~"으로 끝낸다. "지금은 연습하기 어려워요. 다음에 해볼 방법을 설명해 주세요."는
  끝이 아니라 마무리2다. 상태 칸의 `지금까지`에 `방법 주기 [p]번`이 더해졌고, `<설계>`에 `버릇 쪽:` 줄이 더해졌다.
- 연습 루프는 `## 배우가 지난 연습에서 직접 한 말`(배우.md) 칸을 프로필·지난 연습 칸 뒤에 받는다(`PracticeLoopMemory`).
  같은 배우의 최근 연습 루프 대화 5개(이번 연습·숨긴 연습·배우가 한 마디도 하지 않은 대화 제외, 묶음 무관)에서 배우가 쓴 말을
  원문 그대로 `배우가 바란 것`(평가 요청·방법 요청·반박, 옛 대화는 요청 낱말) → `배우가 아니라고 한 것`(정정과 그때 코치가 본 것,
  `피할 것`) → `배우가 자기에 대해 한 말`(자기 한 줄·선택 설명·스스로 알아챔) → `코치가 지난번에 짚은 것`(버릇과 노트의 다음 촬영)
  순으로 싣는다. 분류는 그 대화의 상태 칸이 이미 정해 둔 것을 읽을 뿐 모델을 부르지 않고, 900자에서 뒤부터 자른다.
  배우가 이 기억을 고치는 화면은 두지 않는다 — 요약하지 않고 원문만 옮기며, 대화 안의 정정이 다음 연습의 금지 주제가 되고,
  최근 5개만 읽어 오래된 것은 저절로 빠진다. 새로 저장하는 값은 없다.
- 프롬프트는 이 칸을 버릇을 고르기 전에 읽는다. 봐 달라고 한 쪽을 막힌 곳 다음으로 먼저 보고, 평가·방법을 청했던 배우에게는
  응답 2번째에 짚어주기를 하며, 아니라고 한 주제는 고르지도 꺼내지도 않고, 지난 제안대로 해 온 모습은 버릇으로 짚지 않는다.
- 연습 루프에 넘기는 기억(`priorContextBlock`)에서는 화법 두 칸(`speech_self`·`speech_actual`)을 뺀다(소리·템포를 보지 않는다).
  구조화 코치의 `prior_context` 입력은 바뀌지 않는다(지난 연습 루프는 직렬화하지 않는다).
